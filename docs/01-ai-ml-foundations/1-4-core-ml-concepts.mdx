## TL;DR

A model isn't graded on how well it fits the data it trained on. It's graded on how well it
performs on data it has never seen, and those two numbers can be wildly different. This chapter
covers the vocabulary for managing that gap: features (the inputs a model actually sees),
train/validation/test splits (how you get an honest read on unseen-data performance before it
matters), and the bias-variance tradeoff (the mathematical reason a model can fail in two opposite
directions, underfitting or overfitting, and why fixing one risk tends to worsen the other).

## High-Level Explanation

**Features** are the inputs a model actually consumes: a fixed-length numeric representation of
whatever real-world thing is being predicted. A house isn't fed to a model as a house; it's fed in
as a vector like [square footage, bedroom count, year built, distance to city center]. Choosing and
constructing that representation is called feature engineering, covered in full in chapter 1.7;
this chapter treats features as already-built and focuses on what happens once training starts.

**Train/validation/test splits.** Training a model on a dataset and then reporting its accuracy on
that same dataset is close to meaningless: a sufficiently flexible model can simply memorize the
answers. The standard fix splits the available labeled data into three disjoint pieces before
training starts. The training set is what the model actually learns from. The validation set is
used repeatedly during development to compare candidate models and tune hyperparameters (settings
chosen by the practitioner, like a regularization strength, rather than learned from data), because
using it this way still risks quietly fitting to it over many rounds of tuning. The test set is
touched exactly once, at the very end, to report a final, honest estimate of how the model performs
on data it has never influenced in any way. A common split ratio is 70/15/15 or 80/10/10, though
the right ratio depends on how much labeled data exists at all; with very little data, k-fold
cross-validation (covered in the Deep-Dive) is used instead of a single static split.

**Underfitting and overfitting** are the two ways a model can fail to generalize, in opposite
directions. An underfit model is too simple to capture the real pattern in the data: it performs
poorly on the training set itself, because it lacks the flexibility to represent the relationship
at all (fitting a straight line to a curved relationship, for example). An overfit model is
flexible enough to fit not just the real pattern but the training set's own noise and quirks: it
performs very well on the training set and considerably worse on new data, because part of what it
learned was specific to that particular sample rather than the underlying relationship. Comparing
training performance to validation performance is the standard way to tell which failure mode, if
either, is happening.

**The bias-variance tradeoff** is the formal explanation for why those two failure modes trade off
against each other rather than being independently fixable. A model's error on new data decomposes
into three sources: bias (error from a model too simple to represent the true relationship, which
is what underfitting looks like), variance (error from a model so sensitive to the specific
training sample that a different training sample would have produced a meaningfully different
model, which is what overfitting looks like), and irreducible noise (error no model can remove,
because the data itself is noisy). Increasing a model's flexibility typically lowers bias but
raises variance, and vice versa; the practical goal is finding the point on that tradeoff that
minimizes their sum, not driving either one to zero.

## Deep-Dive Explanation

**Features, formally.** An example is represented as a feature vector x, an element of ℝᵈ (a
list of d real numbers), and a dataset is a matrix X with one row per example and one column per
feature (see the Notation conventions in the
[glossary](../00-orientation/0-5-glossary-notation-conventions.md#notation)). Features fall into a
few common types that determine how they must be prepared before training: numeric features (age,
transaction amount) are often scaled so no single feature dominates a distance calculation purely
because of its units; categorical features (a customer's plan tier, a diagnosis code) are typically
one-hot encoded, turned into a separate binary column per category, because most algorithms expect
numeric input and have no notion of category order; ordinal features (a risk tier of Low/Medium/High)
preserve their order as integers rather than being one-hot encoded, since the order itself carries
information a one-hot encoding would discard.

**Cross-validation.** A single train/validation split gives one estimate of validation performance,
and that estimate is itself noisy: a different random split could rank two candidate models
differently, especially with a small dataset. K-fold cross-validation reduces that noise by
partitioning the training data into k equal folds, training k separate times, each time holding out
a different fold as the validation set and training on the remaining k − 1, then averaging the k
validation scores into a single estimate. k = 5 or k = 10 are the most common choices, trading
compute cost (k full training runs instead of one) for a more stable performance estimate. The test
set is still held out entirely from this process; cross-validation only changes how the
training/validation portion is used. Stratified k-fold, a variant that preserves each fold's class
proportions to match the full dataset (important when one class is rare, like fraud), was found to
give the more reliable estimate for classification problems (Kohavi,
[*A Study of Cross-Validation and Bootstrap for Accuracy Estimation and Model Selection*](https://www.ijcai.org/Proceedings/95-2/Papers/016.pdf),
IJCAI, 1995), and has since become the default behavior in common tooling such as scikit-learn's
cross-validation utilities.

**The bias-variance decomposition, formally.** For a model f̂ trained to predict a true function
f(x) plus irreducible noise (y = f(x) + ε, where the noise ε has mean zero and variance σ²), the
expected squared error on a new point x decomposes as:

Expected test error at x = Bias[f̂(x)]² + Variance[f̂(x)] + σ²

where Bias[f̂(x)] is the difference between the model's average prediction (averaged over many
independently drawn training sets) and the true value f(x), and Variance[f̂(x)] is how much the
model's prediction at x fluctuates across those different training sets. This decomposition, a
classical identity from estimation theory popularized for machine learning audiences by Geman,
Bienenstock, and Doursat
([*Neural Networks and the Bias/Variance Dilemma*](https://direct.mit.edu/neco/article-abstract/4/1/1/5622/Neural-Networks-and-the-Bias-Variance-Dilemma),
*Neural Computation*, 1992), is why the tradeoff is unavoidable rather than a sign of doing
something wrong: σ² cannot be reduced by any choice of model, and reducing bias by adding
flexibility (more parameters, deeper trees, fewer simplifying assumptions) mechanically increases
how sensitive the fitted model is to which specific training sample it happened to see, which is
variance.

**Regularization** is the standard technique for controlling variance directly, by penalizing model
complexity during training rather than by strictly limiting the model's raw capacity. L2
regularization (also called ridge or weight decay) adds a term proportional to the sum of the
squared model weights to the loss function being minimized: instead of minimizing loss(w) alone,
the model minimizes loss(w) + λ·Σwᵢ², where λ (a hyperparameter, a setting chosen by the
practitioner rather than learned from data) controls how strongly large weights are penalized. This
shrinks weights toward zero without
necessarily eliminating them, which reduces the model's sensitivity to any single feature or
training example. L1 regularization (lasso) uses the sum of absolute weights instead of squared
weights, and tends to drive some weights to exactly zero, effectively performing feature selection
as a side effect. Early stopping is a different regularization strategy that doesn't touch the loss
function at all: it monitors validation error during training and halts once validation error
starts rising even though training error is still falling, which is the empirical bias-variance
turn described above happening in real time rather than being predicted from theory in advance.

**Learning curves** are the standard diagnostic for distinguishing bias-dominated from
variance-dominated error without invoking the formal decomposition directly. Plotting training and
validation error against training set size reveals the failure mode: if both curves converge to a
similarly high error, the model is underfitting (more data will not help; the model needs more
capacity or better features), while if training error stays low but a persistent, large gap remains
between training and validation error even as more data is added, the model is overfitting (more
data, more regularization, or fewer features will help). A model with the same behavior evaluated
against complexity instead of dataset size produces the U-shaped validation curve shown above.

**Data leakage is a related but distinct failure from overfitting, and the two are easy to
conflate.** Overfitting means the model learned real patterns in the training data too specifically,
including its noise. Data leakage means the model had access, during training or validation, to
information that will not be available at prediction time in production: a feature computed using
the label itself, data from after the event being predicted, or a validation split that shares
duplicated or correlated records with the training set (two transactions from the same customer
landing on opposite sides of the split, for instance). A leaked model can show excellent, even
suspiciously good, validation performance and still fail in production, because the validation
estimate itself was never honest. This is the same underlying shape of error as chapter 1.3's
distinction between reward hacking and label leakage: a model or an evaluation can look correct by
every measurement being taken and still be wrong, because what was measured wasn't what would
actually be faced in deployment.
