## TL;DR

Every framework in chapter 2.7 ultimately runs its forward pass, backward pass, and optimizer step
(2.2) as matrix multiplications on physical hardware, and the choice of hardware changes what a
model costs to train and to run. **GPUs**, originally built for graphics, became the default deep
learning accelerator because their thousands of simple parallel cores suit the same matrix
operation repeated across many data points at once; modern GPUs also add dedicated Tensor Cores for
fast mixed-precision matrix multiply-accumulate. **TPUs** are Google's custom chips, built around a
systolic array purpose-designed for matrix multiplication, trading general-purpose flexibility for
efficiency on exactly the operations deep learning needs most. Training and inference stress this
hardware differently: large-batch training tends to be compute-bound, while small-batch inference
tends to be memory-bandwidth-bound, and because inference runs continuously against live traffic
while training is a comparatively bounded, front-loaded cost, inference typically dominates a
widely-deployed model's total lifetime compute cost.

## High-Level Explanation

The forward and backward passes chapter 2.2 derived by hand are, at scale, overwhelmingly matrix
multiplications: a layer's weighted sum is a matrix-vector or matrix-matrix product, and
backpropagation's chain rule steps are more matrix multiplications. A CPU has a small number of
complex cores, each optimized to run one instruction stream with branches and varied logic as fast
as possible, which suits general-purpose code but wastes most of a chip's area on control logic that
a repetitive matrix multiply does not need. A GPU instead packs thousands of much simpler cores that
all execute the same instruction across many data elements at once, a design called SIMT
(single instruction, multiple threads), which is a close match for applying the same multiply-add
operation across every element of a large matrix. This raw parallelism, not a higher clock speed, is
why a GPU can train a neural network far faster than a CPU running the identical arithmetic.

The frameworks from chapter 2.7 all target this same underlying hardware through different paths:
PyTorch and TensorFlow dispatch tensor operations to GPU kernels through NVIDIA's CUDA platform, and
TensorFlow and JAX can also compile through XLA, the same linear-algebra compiler that targets both
GPUs and TPUs. Understanding the hardware underneath explains why some choices in chapter 2.7,
such as JAX's tight fit with TPUs or mixed-precision training's popularity on modern GPUs, exist in
the first place.

## Deep-Dive Explanation

**GPU architecture for deep learning.** A modern NVIDIA GPU combines general-purpose CUDA cores,
which handle ordinary floating-point arithmetic, with dedicated Tensor Cores, introduced with the
Volta architecture, which perform a fused multiply-accumulate on small matrix tiles directly in
hardware at much higher throughput than the same operation run on CUDA cores. Tensor Cores are
built to run fastest in reduced precision (FP16 or BF16) rather than full FP32, which motivated
**mixed-precision training**: keeping a master copy of the weights in FP32 for numerical stability
while running the forward and backward pass in FP16, and using loss scaling, multiplying the loss by
a constant before the backward pass and dividing it back out afterward, to keep small gradient
values from underflowing to zero in FP16's narrower range (Micikevicius, Narang, Alben, Diamos,
Elsen, Garcia, Ginsburg, Houston, Kuchaiev, Venkatesh, and Wu,
[*Mixed Precision Training*](https://arxiv.org/abs/1710.03740), ICLR, 2018). A GPU's memory
hierarchy matters just as much as its cores: high-bandwidth memory (HBM) holds the full model and
activations but is comparatively slow to access relative to the GPU's on-chip SRAM and cache, so a
model's speed is often limited by how fast data can move from HBM to the cores rather than by how
fast the cores can compute, a distinction the roofline model below makes precise. Multiple GPUs are
connected by a high-speed interconnect (NVLink, or Ethernet/InfiniBand across machines) that carries
the gradient synchronization chapter 2.7's `pmap` and other distributed-training tools rely on.

**TPU architecture.** A Tensor Processing Unit is an application-specific integrated circuit (ASIC):
a chip designed for one job rather than general-purpose parallel compute. That job is matrix
multiplication, implemented as a large **systolic array**, a grid of simple processing elements
where each element holds one value, multiplies it against a value flowing through, and passes a
partial sum to its neighbor, so an entire matrix multiplication flows through the grid in a tightly
pipelined wave rather than being orchestrated instruction by instruction the way a GPU's cores are
(Jouppi, Young, Patil, Patterson, and 71 further co-authors,
[*In-Datacenter Performance Analysis of a Tensor Processing Unit*](https://arxiv.org/abs/1704.04760),
ISCA, 2017). Because the systolic array is fixed in hardware for matrix multiplication specifically,
a TPU is less flexible than a GPU (it is a poor fit for code that is not dominated by matrix
multiplies), but it can be substantially more efficient per watt and per dollar on the workload it
was built for. TPUs are typically deployed in large interconnected clusters called pods, and are
tightly integrated with XLA, which is why JAX, itself built around XLA, is a common choice for
large-scale TPU training.

**The roofline model: compute-bound versus memory-bound.** A workload's **arithmetic intensity** is
the number of floating-point operations it performs per byte moved from memory: FLOPs / bytes
moved. The roofline model plots achievable performance against arithmetic intensity: at low
arithmetic intensity, performance is capped by how fast bytes can be moved from memory (the
memory-bound region, a rising diagonal line), and at high arithmetic intensity, performance is
capped by the hardware's peak compute throughput (the compute-bound region, a flat ceiling); the
point where these two lines meet is the hardware's ridge point (Williams, Waterman, and Patterson,
[*Roofline: An Insightful Visual Performance Model for Multicore Architectures*](https://dl.acm.org/doi/10.1145/1498765.1498785),
Communications of the ACM, 52(4), 2009). This directly explains a practical difference between
training and inference: training processes a large batch of examples through the same weights, so
the cost of moving those weights from memory is amortized (spread) across many examples, pushing
arithmetic intensity up toward the compute-bound region. A single inference request, especially at
batch size 1, reuses those same weights for comparatively little computation, keeping arithmetic
intensity low and the workload memory-bound, meaning inference speed is often limited by how fast
weights can be read from memory rather than by how many multiply-adds the hardware could otherwise
perform per second.

```python
# Illustrative: arithmetic intensity of the same linear layer (y = Wx from chapter 2.1)
# at two different batch sizes, showing why batching raises arithmetic intensity.
d_in, d_out = 4096, 4096          # a fixed weight matrix W of shape (d_out, d_in)
bytes_per_value = 2               # FP16/BF16, this chapter's mixed-precision Deep-Dive

def arithmetic_intensity(batch_size):
    flops = 2 * d_out * d_in * batch_size            # multiply-add per output, per example
    weight_bytes = d_out * d_in * bytes_per_value     # W is loaded once, reused across the batch
    io_bytes = batch_size * (d_in + d_out) * bytes_per_value
    bytes_moved = weight_bytes + io_bytes
    return flops / bytes_moved

print(arithmetic_intensity(1))     # low: weight-loading cost dominates a single request
print(arithmetic_intensity(128))   # much higher: the same weight load is amortized over 128 examples
```

**Training versus inference compute economics.** Training a large model is a large but comparatively
bounded, front-loaded cost: it happens some finite number of times, on hardware chosen and
provisioned in advance for maximum throughput at large batch size. Inference, by contrast, runs
continuously for as long as a model stays deployed, once per user request, so its total cost scales
with usage rather than with training runs; for a model serving meaningful production traffic over
its deployment lifetime, cumulative inference cost commonly exceeds the one-time training cost.
Because inference is often memory-bound at low batch size, the standard levers for controlling its
cost target arithmetic intensity and memory footprint directly: batching multiple requests together
before running them raises arithmetic intensity the same way a larger training batch does, and
**quantization**, representing weights in an even lower-precision integer format (INT8 or INT4)
than mixed-precision training's FP16, shrinks the bytes that must move from memory per request,
directly increasing arithmetic intensity and throughput at some cost to numerical precision. Sizing
hardware to the workload matters too: a data-center training GPU provisioned for a low-traffic
inference endpoint is typically far more capacity, and cost, than that workload needs.
