## TL;DR

An LLM's **context window** is the maximum number of tokens, input and output combined, it can
process at once, bounded both by its positional encoding scheme and by the raw compute and memory
cost of self-attention (2.5), which scales quadratically with sequence length. Processing the prompt
(**prefill**) is compute-bound and grows quadratically; generating each new token afterward
(**decode**, 4.3) instead requires reading a **KV cache**, the stored keys and values for every prior
token, whose memory footprint grows linearly with sequence length and whose repeated reads make
decode memory-bandwidth-bound rather than compute-bound. Longer context is therefore never free: it
raises prefill latency, decode latency, and, on a hosted API, dollar cost, all at once. FlashAttention
computes the exact same attention output with far less memory traffic; RoPE and ALiBi extend how well
a model generalizes to sequences longer than it was trained on; grouped-query attention shrinks the
KV cache itself; and retrieval, previewed here and covered fully in Phase 6, sidesteps the problem
entirely by fetching only the relevant material instead of lengthening the context at all.

## High-Level Explanation

Picture someone reading a long document to answer a question about it. If the document is short,
they hold the whole thing in their head at once. As it gets longer, they start needing a growing
stack of sticky notes summarizing everything they have already read, so they do not have to
re-read from the beginning every time they turn a new page; that stack of notes is the KV cache, and
it takes up more desk space the longer the document gets. A faster reader does not understand the
document any differently, they just get through the same material with less wasted effort, the way
FlashAttention computes the identical result more efficiently. A reader who trained mostly on short
documents can sometimes still muddle through a much longer one if given a good general sense of "how
far back" something was relative to where they are now, which is what RoPE and ALiBi provide, though
only up to a point. And rather than trying to hold an entire library in their head at once, a smarter
approach is to have a librarian hand over only the specific pages that are actually relevant to the
question, which is the idea behind retrieval, covered fully in Phase 6.

## Deep-Dive Explanation

**Why self-attention is quadratic, and what that costs during prefill.** Standard self-attention
(2.5) computes an attention score between every pair of tokens in a sequence, so a sequence of length
n requires on the order of n-squared score computations, and naively, n-squared memory to hold the
full attention score matrix. This is the direct cost of prefill, the phase where the model processes
the entire input prompt before generating anything, and it is compute-bound: the GPU is doing genuine
arithmetic work proportional to the square of the prompt length, and that work parallelizes well
across the prompt's tokens since they are all already available at once.

**FlashAttention: the exact same output, computed far more efficiently.** Materializing the full
n-by-n attention score matrix in a GPU's slower main memory, then reading it back for the subsequent
softmax and weighted sum, wastes enormous memory bandwidth. FlashAttention (Dao et al.,
[*FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness*](https://arxiv.org/abs/2205.14135),
2022) restructures the computation using tiling, processing the attention calculation in blocks small
enough to stay in the GPU's much faster on-chip memory, and recomputing certain intermediate values
during the backward pass rather than storing them. Critically, this is an exact algorithm, not an
approximation, the same mathematical result as standard attention, produced with dramatically less
memory traffic and higher throughput, the same "identical output, cheaper to produce" idea speculative
decoding (4.3) applies to the decoding loop, applied here to the attention computation itself.

**The KV cache and why decode has a different cost profile than prefill.** Once the prompt has been
processed, generating each new token autoregressively (3.3, 4.3) requires that new token's query
vector to attend back over every prior token's key and value vectors. Recomputing those key and value
vectors for the entire sequence at every single new token would be wasteful, so they are cached, the
KV cache, and reused. This cache must be stored per layer and per attention head, and its size grows
linearly with sequence length. Because decode generates one token at a time, largely sequentially,
and each step must read the full, ever-growing KV cache from memory, decode is memory-bandwidth-bound
rather than compute-bound: at long context lengths, the cost of simply reading the cache, not the
arithmetic itself, becomes the dominant driver of decode latency and, on a hosted API, of per-token
cost.

**Positional encoding and generalizing beyond the trained length.** A model's understanding of token
position is tied to whatever positional encoding scheme it was trained with, and performance can
degrade sharply once a sequence exceeds the lengths seen during training. RoPE (Su et al.,
[*RoFormer: Enhanced Transformer with Rotary Position Embedding*](https://arxiv.org/abs/2104.09864),
2021) encodes position by applying a rotation to query and key vectors as a function of their
relative position, rather than adding a fixed positional vector, which gives models meaningfully
better ability to generalize to longer sequences than absolute positional encodings typically allow.
ALiBi (Press et al.,
[*Train Short, Test Long: Attention with Linear Biases Enables Input Length Extrapolation*](https://arxiv.org/abs/2108.12409),
2021) takes a different approach, directly biasing attention scores based on the distance between
positions rather than modifying the query and key vectors themselves, and reports strong extrapolation
to sequences considerably longer than the model was trained on. Neither technique makes context length
unlimited; both extend how gracefully a model degrades past its trained length, rather than removing
the limit outright.

**Where in the context matters too, not only how long.** Even within a model's supported context
length, Liu et al. ([*Lost in the Middle: How Language Models Use Long Contexts*](https://arxiv.org/abs/2307.03172),
2023) find that model performance on retrieving a piece of information is often strongest when that
information sits near the beginning or end of the context and measurably weaker when it sits in the
middle, a distinct finding from the length-extrapolation question above: this degradation shows up
even on sequences comfortably within the model's supported length, meaning where the relevant
information sits within the context matters, not only how much total context is used.

**Grouped-query attention: shrinking the cache itself.** In standard multi-head attention, every
attention head maintains its own separate keys and values, multiplying the KV cache's size by the
number of heads. Grouped-query attention (Ainslie et al.,
[*GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints*](https://arxiv.org/abs/2305.13245),
2023) has multiple query heads share one set of key/value heads, a middle ground between standard
multi-head attention and the more extreme multi-query attention design that shares a single key/value
head across all queries. This directly cuts the KV cache's memory footprint and the memory-bandwidth
cost of reading it during decode, and existing multi-head checkpoints can be adapted into this
structure without training an entirely new model from scratch.

**Putting the cost picture together.** Prefill latency mainly reflects quadratic attention compute
over the prompt, which FlashAttention reduces without changing the result. Decode latency and
per-token cost mainly reflect the linear, memory-bandwidth-bound cost of reading an ever-growing KV
cache once per generated token, which grouped-query attention reduces by shrinking that cache. Both
map directly to a hosted API's billable resource usage, which is why a longer context or a longer
multi-turn conversation costs more, not just runs slower. Retrieval, previewed here and covered fully
in Phase 6, offers a different strategy than optimizing any of these costs directly: instead of
lengthening the context to include everything that might be relevant, retrieve only the specific
passages that are, keeping context length, and therefore both cost profiles, bounded regardless of
how much total source material exists.
