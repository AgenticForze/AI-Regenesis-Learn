# Glossary & Notation Conventions

A living reference for terms and notation used consistently across the site. Individual
chapters don't redefine these — they link back here.

## Conventions used throughout the site

- **Chapter IDs** are written `phase.chapter`, e.g. `10.4` means Phase 10, chapter 4. The flight
  label at the top of every page (e.g. `Chapter 10.4 · Phase 10`) uses this same numbering.
- **`[v3]` / `[v4]` / `[v5]` tags** on a chapter title mark content added or expanded in that
  review pass — see the site's Changelog for what each pass covered.
- **"HL survey"** on a chapter marks it as using the lighter four-section landscape template
  (Phases 9 and 14 only) rather than the full seven-section Content Standard.
- Code blocks use language-tagged fencing (` ```python `, ` ```bash `, etc.) and are always
  runnable/copy-pasteable as written — no partial snippets presented as complete.
- Mermaid diagrams are used for anything architectural that will change over time (flow charts,
  sequence diagrams); static SVG illustrations are used for anything conceptual/decorative.

## Core terms

| Term | Definition |
|---|---|
| **Agent** | A system that uses an LLM to decide its own sequence of actions (tool calls, sub-tasks) toward a goal, rather than following a fixed, human-authored control flow. See 8.1 and 8.8 for the full agent-vs-workflow-vs-copilot distinction. |
| **AI Winter** | A period of collapsed funding and research interest following an era of AI overpromising relative to what the era's compute/data could deliver. Two are widely recognized: roughly 1974–1980 (the US 1966 ALPAC report and 1969 Mansfield Amendment, plus the UK's independent 1973 Lighthill Report) and roughly 1987–1993 (the Lisp-machine market collapse and a second DARPA funding cut). See 1.1. |
| **AI Effect** | The tendency for a task to stop being called "AI" once it's reliably automated (chess engines, OCR, spam filters), so the term keeps shifting to whatever capability is still unsolved. See 1.1. |
| **Narrow AI (ANI) / AGI / ASI** | A capability-*generality* spectrum, not a "smartness" spectrum. Narrow AI (all systems built to date, including current LLM agents) is competent at specific tasks without that competence transferring to unrelated ones. AGI (not yet achieved) would generalize across essentially any cognitive task the way a human does. ASI is a hypothetical further step beyond AGI. See 1.1. |
| **Discriminative model** | A model that predicts P(label \| input) directly, drawing a decision boundary between fixed classes rather than modeling how the input itself was produced (logistic regression, an SVM, most classifiers). Contrast with generative model. See 1.2. |
| **Generative model** | In classical statistics, a model that learns the joint distribution of inputs and labels, P(input, label), and can sample new inputs from it (Naive Bayes is the standard textbook example). "Generative AI" narrows this further: an industry term for models that sample new content, usually from a distribution conditioned on an input, P(output \| input), rather than the unconditional or joint form the classical term describes. See 1.2. |
| **Markov Decision Process (MDP)** | The standard formalization of a reinforcement learning problem: a set of states, actions, a transition function, and a reward function, with a policy learned to maximize expected cumulative reward over time rather than a single labeled correct action. See 1.3. |
| **Self-supervised learning** | Training where the label for each example is generated automatically from the data itself (the next token in a sequence, a masked-out word) rather than assigned by a human annotator. Mechanically identical to supervised learning; it just doesn't require human labeling. See 1.3. |
| **Reward hacking** | When a reinforcement learning agent optimizes its reward function exactly as designed, but the reward function was an imperfect proxy for the outcome its designers actually wanted. Distinct from label leakage, which is a supervised-learning failure. See 1.3. |
| **Feature / Feature vector** | The fixed-length numeric representation a model actually consumes, built from raw data (a house's square footage and bedroom count rather than the house itself). Constructing this representation is feature engineering, covered in full in 1.7. See 1.4. |
| **Hyperparameter** | A model or training setting chosen by the practitioner before or during training (a regularization strength, the number of folds in cross-validation) rather than learned from data the way model weights are. Tuned against a validation set, never the test set. See 1.4. |
| **Regularization** | A family of techniques that penalize model complexity during training to control variance, rather than by strictly limiting the model's raw capacity. L2 (ridge) shrinks weights toward zero; L1 (lasso) can drive some weights to exactly zero, acting as implicit feature selection; early stopping halts training once validation error starts rising. See 1.4. |
| **Bias-variance tradeoff** | The decomposition of a model's expected error into bias (error from a model too simple to represent the true relationship), variance (error from sensitivity to which specific training sample was used), and irreducible noise. Increasing model flexibility typically lowers bias but raises variance. See 1.4. |
| **Overfitting / Underfitting** | Overfitting: a model fits training-set noise as well as signal, showing low training error but much higher validation error (high variance). Underfitting: a model lacks the capacity to represent the real pattern, showing high error on both training and validation data (high bias). See 1.4. |
| **Data leakage** | When information that would not be available at prediction time (label information, future data, or duplicated records across a train/test split) reaches a model during training or validation, producing an evaluation that looks good but does not hold in production. Distinct from overfitting, which is a modeling failure rather than an evaluation-integrity failure. See 1.4. |
| **Cross-validation (k-fold)** | Partitioning training data into k folds, training k times with a different fold held out as validation each time, and averaging the k scores into one performance estimate, to reduce the noise of a single train/validation split. See 1.4. |
| **Inductive bias** | The structural assumption a learning algorithm makes about the shape of the relationship it is fitting (a straight line for linear regression, axis-aligned splits for a decision tree), which determines what patterns it can represent at all before it ever sees data. See 1.5. |
| **Ensemble learning (bagging / boosting)** | Combining many individual models into a stronger predictor. Bagging trains many models independently on bootstrap-resampled data and averages their predictions to reduce variance (Random Forest); boosting trains models sequentially, each correcting the ensemble's remaining errors, to reduce bias (gradient boosting, AdaBoost). See 1.5. |
| **Curse of dimensionality** | The tendency for distance-based methods (like k-nearest neighbors) to degrade as the number of features grows, because in high-dimensional space the distance to the nearest point and the distance to a typical random point converge, making "nearest" less informative. See 1.5. |
| **Confusion matrix** | A table of a classifier's predictions at a fixed threshold, broken into true positives, false positives, false negatives, and true negatives; every classification metric in this curriculum is a ratio computed from these four counts. See 1.6. |
| **Precision / Recall** | Precision is the fraction of predicted positives that were actually positive (TP / (TP + FP)); recall is the fraction of actual positives the model found (TP / (TP + FN)). Computed over different denominators, so a model can score high on one and low on the other. See 1.6. |
| **F1 score** | The harmonic mean of precision and recall, 2 · (Precision · Recall) / (Precision + Recall), used as a single balanced metric when neither false positives nor false negatives are clearly more costly. See 1.6. |
| **ROC-AUC** | The area under the ROC curve (true positive rate vs. false positive rate across every decision threshold); equals the probability that a randomly chosen actual positive scores higher than a randomly chosen actual negative. See 1.6. |
| **RMSE / MAE** | Root mean squared error and mean absolute error, two ways of summarizing regression error. RMSE squares each residual before averaging, so it penalizes large errors more heavily than MAE does. See 1.6. |
| **Missing data (MCAR / MAR / MNAR)** | A taxonomy of why a value is missing, which determines which handling strategy is valid. MCAR: missingness is unrelated to any variable, so dropping rows adds no bias. MAR: missingness depends on other observed variables, which model-based imputation can account for. MNAR: missingness depends on the missing value itself, which no imputation method can fully correct. See 1.7. |
| **Target / mean encoding** | Replacing a categorical value with a statistic (typically the mean) of the target variable observed for that category. Compact and often effective, but leaks label information unless computed out-of-fold, with rare categories smoothed toward the global mean. See 1.7. |
| **Learned embeddings** | Low-dimensional dense vectors trained alongside a model to represent a categorical value, letting the model discover which categories behave similarly rather than requiring that structure to be hand-specified. A common alternative to one-hot or target encoding for very high-cardinality categoricals. See 1.7. |
| **Feature store** | A shared feature-computation layer used by both a training pipeline and a live serving system, so a feature is guaranteed to mean the same code in both places rather than two independently maintained implementations. See 1.7. |
| **Training-serving skew** | When a feature is computed one way during offline model training and a subtly different way during live serving, so a model receives inputs at serving time that don't match what it learned from. Not detectable by offline evaluation metrics, because they run entirely inside the training-side code path. See 1.7. |
| **Dot product / Cosine similarity** | The dot product of two vectors, x . y = Σ xi yi, is large when they point in similar directions but also grows with each vector's magnitude. Cosine similarity, x . y / (‖x‖‖y‖), divides that out to measure direction alone, which is why it is the standard similarity measure for embeddings. See 1.8; applied to word and token embeddings specifically in 3.1. |
| **Bayes' theorem** | P(A given B) = P(B given A) · P(A) / P(B): the probability of A given evidence B, weighted by how likely A was before any evidence (the prior) and normalized by how likely the evidence is overall. The low prior in a rare-event estimate can dominate the result even when a test or model is highly accurate. See 1.8. |
| **p-value / Confidence interval** | A p-value is the probability of observing a difference at least this extreme if there were truly no effect; a small p-value is evidence against "no difference," not proof of a large or important effect. A confidence interval gives a range of plausible values for the true effect size and is often more informative than a p-value alone. See 1.8. |
| **Gradient descent / Learning rate** | The standard training procedure: θ ← θ − η∇L(θ), stepping parameters θ in the direction that most reduces the loss L, scaled by the learning rate η. Too high a learning rate can cause the loss to oscillate or diverge; too low converges reliably but slowly. See 1.8. |
| **Convex / Non-convex loss surface** | A convex loss surface has exactly one minimum, so gradient descent is guaranteed to reach it regardless of starting point. A non-convex surface, typical of deep neural networks, can have many local minima and saddle points, so the starting point and optimizer choice affect where training ends up. See 1.8. |
| **Demographic parity / Equalized odds / Predictive parity** | Three distinct, individually reasonable fairness definitions that do not all agree. Demographic parity requires the same positive prediction rate across groups. Equalized odds requires the same true and false positive rate across groups, conditioned on the actual outcome. Predictive parity (calibration) requires the same actual outcome rate among people who received the same score. When group base rates genuinely differ, equalized odds and predictive parity cannot both hold except for a perfect classifier. See 1.9. |
| **LIME (Local Interpretable Model-agnostic Explanations)** | A post-hoc explanation method that samples points near one input, observes how a black-box model's output changes, and fits a simple, interpretable surrogate model to that local neighborhood; the surrogate's coefficients become the explanation for that one prediction. See 1.9. |
| **SHAP (SHapley Additive exPlanations)** | A post-hoc explanation method that adapts the Shapley value from cooperative game theory, distributing a prediction's difference from a baseline across features so that a feature contributing nothing gets zero credit and all contributions sum exactly to the total difference. Local per-prediction SHAP values can also be aggregated into a global feature-importance summary. See 1.9. |
| **Feedback loop (bias)** | When a deployed model's own decisions shape which outcomes get observed, and those observed outcomes then become training data for the next model version, compounding an initial bias each retraining cycle rather than merely repeating it. See 1.9. |
| **Perceptron** | A single unit that computes a weighted sum of its inputs plus a bias, then applies an activation function; can only separate its input space with one straight line/hyperplane. See 2.1. |
| **Multilayer Perceptron (MLP) / Hidden layer** | A network of perceptron-like units arranged in fully connected layers, with one or more hidden layers between the input and output layer where the network's actual computation happens. See 2.1. |
| **Activation function** | The nonlinear function (sigmoid, tanh, ReLU) applied to a unit's weighted sum; without it, any depth of stacked layers collapses algebraically to one linear transformation. See 2.1. |
| **Universal Approximation Theorem** | The result (Cybenko 1989; Hornik, Stinchcombe, and White 1989) that a feedforward network with one hidden layer and enough units can approximate any continuous function on a bounded region to arbitrary precision. An existence proof, not a training or efficiency guarantee. See 2.1. |
| **Backpropagation** | The algorithm that computes the gradient of the loss with respect to every weight by applying the chain rule backward through the network, from the loss to the input layer, reusing forward-pass computations layer by layer rather than re-deriving each weight's gradient independently. See 2.2. |
| **Vanishing / Exploding gradient** | Because the chain rule multiplies one factor per layer, a deep network's earliest-layer gradients can shrink toward zero (vanishing, common with sigmoid/tanh) or grow unboundedly (exploding) as depth increases, stalling or destabilizing training. See 2.2. |
| **Momentum (optimization)** | An optimizer technique that keeps a running exponentially-weighted average of past gradients and updates weights using that average rather than the raw current gradient, smoothing noisy per-batch updates and accelerating convergence along consistently downhill directions. See 2.2. |
| **Adam (Adaptive Moment Estimation)** | An optimizer that combines momentum (a first-moment gradient estimate) with a second-moment estimate (an exponentially-weighted average of squared gradients) to give every parameter its own adapted effective learning rate. See 2.2. |
| **Learning rate schedule** | A rule that changes the learning rate over the course of training rather than fixing one value for the whole run: step decay, cosine annealing, and warm-up are the standard forms. See 2.2. |
| **Convolution (CNN)** | An operation that slides a small filter of learned weights across an input, multiplying and summing at each position to produce a feature map; the same filter weights are reused at every position (parameter sharing). See 2.3. |
| **Feature map / Channel** | The 2D grid of outputs produced by sliding one filter across an input; a convolutional layer's output stacks one feature map per filter as separate channels. See 2.3. |
| **Pooling (max / average)** | An operation that downsamples a feature map by summarizing each small region with one value (the maximum, for max pooling), reducing computation and adding some tolerance to small spatial shifts. See 2.3. |
| **Stride / Padding** | Stride is how many positions a filter shifts between applications; padding adds pixels (typically zero) around an input's border. Both control a convolutional layer's output size: out = floor((W - F + 2P) / S) + 1. See 2.3. |
| **Receptive field** | The region of the original input that a specific unit's value depends on; each additional convolutional or pooling layer expands the receptive field of the units that follow it. See 2.3. |
| **Residual / Skip connection** | A connection that adds a block's input directly to its output (output = F(x) + x), letting the block learn only the residual F(x) rather than the full mapping, which lets very deep networks (100+ layers) keep training effectively. See 2.3. |
| **Recurrent Neural Network (RNN) / Hidden state** | A network that processes a sequence one element at a time, reusing the same weights at every step and carrying a hidden state forward as a running summary of everything seen so far. See 2.4. |
| **Backpropagation through time (BPTT)** | Training an RNN by unrolling its recurrence across all T steps of a sequence and applying backpropagation through the resulting T-step computation graph, which inherits the vanishing/exploding gradient problem (2.2) stretched across time steps. See 2.4. |
| **LSTM (Long Short-Term Memory)** | A recurrent cell with a largely additive cell state controlled by three gates (forget, input, output), giving gradients a more direct path across long sequences than a plain RNN's hidden state provides. See 2.4. |
| **GRU (Gated Recurrent Unit)** | A recurrent cell with two gates (update, reset) and no separate cell state, using fewer parameters than an LSTM of the same size while often reaching comparable accuracy. See 2.4. |
| **Bidirectional RNN** | An architecture that runs two separate RNNs, one forward and one backward over a sequence, and concatenates their hidden states at each position, so every position's representation reflects context from both directions; usable only when the whole sequence is available at once. See 2.4. |
| **Self-attention / Query, Key, Value (Q, K, V)** | A mechanism where every position in a sequence is linearly projected into a query, a key, and a value vector, and each position's new representation is a weighted sum of all value vectors, weighted by the similarity between its query and every key. Lets any two positions connect in one step, unlike an RNN's step-by-step hidden state. See 2.5. |
| **Scaled dot-product attention** | The specific attention formula Attention(Q, K, V) = softmax(QK^T / √d_k)·V, where dividing by the square root of the key dimension keeps similarity scores in a range where softmax gradients stay informative. See 2.5. |
| **Multi-head attention** | Running several attention computations in parallel, each with its own learned projections into a smaller subspace, then concatenating the results; lets different heads specialize in different kinds of relationships. See 2.5. |
| **Positional encoding** | A position-dependent signal added to each token's embedding so a Transformer, whose self-attention has no inherent sense of order, can recover word order and relative position. See 2.5. |
| **Causal mask** | A mechanism that sets a decoder's attention score to negative infinity for any position after the current one, before the softmax, so a position cannot attend to tokens not yet generated, matching what is actually available at inference time. See 2.5. |
| **Layer normalization** | A normalization technique that normalizes across a single position's feature dimensions rather than across a batch, making it independent of batch size and well suited to sequences of varying length; used throughout the Transformer's encoder and decoder blocks. See 2.5. |
| **Transfer learning** | Using a model already trained on a large source task as the starting point for a new target task, instead of training from randomly initialized weights, dramatically reducing the data and compute needed to reach good target-task performance. See 2.6. |
| **Feature extraction (transfer learning)** | An adaptation strategy that freezes every pretrained weight and trains only a newly added task-specific output layer on the target data. See 2.6. |
| **Fine-tuning** | An adaptation strategy that unfreezes some or all of a pretrained model's weights and continues training them on a smaller, task- or domain-specific target dataset, typically at a smaller learning rate than the original training used. See 2.6; elaborated further in Phase 7. |
| **Catastrophic forgetting** | The collapse of a model's performance on a previously learned task after it continues training on a new task, because gradient descent has no built-in mechanism to preserve weights that mattered for a task it is no longer being trained on. See 2.6. |
| **Domain adaptation vs. Task adaptation** | Domain adaptation addresses the same task under a different data distribution (e.g. daytime vs. nighttime photos); task adaptation addresses a different task within the same general domain (e.g. classification vs. detection). Real transfer problems often combine both. See 2.6. |
| **Automatic differentiation (autodiff)** | A framework mechanism that computes exact gradients of arbitrary differentiable code without a human hand-deriving them, by recording every operation performed during a forward pass and applying the chain rule backward across that record (reverse-mode autodiff). A direct, generalized implementation of backpropagation (2.2), not an approximation of it. See 2.7. |
| **Computation graph** | The record an autodiff system builds as a forward pass executes: a node for every operation and an edge for every tensor flowing between them, each node also carrying its local derivative rule. Built dynamically each forward pass in PyTorch and JAX's tracing, or compiled ahead of time under TensorFlow's classic graph mode or @tf.function. See 2.7. |
| **Vector-Jacobian product** | The chain-rule step reverse-mode autodiff computes at each computation-graph node: combining the gradient flowing in from later in the graph with that node's local derivative, accumulating the result at every parameter that fed into the computation. See 2.7. |
| **Eager execution vs. Graph (compiled) execution** | Eager execution runs each operation immediately as ordinary Python, favoring debuggability at some cost to raw speed. Graph or compiled execution (classic TensorFlow, @tf.function, JAX's jit) traces or compiles the computation before running it, allowing operations to be fused and scheduled efficiently at the cost of a compilation step. See 2.7. |
| **Tensor Core** | Dedicated hardware on NVIDIA GPUs from the Volta architecture onward that performs a fused multiply-accumulate on small matrix tiles directly in hardware, at much higher throughput than the same operation run on general-purpose CUDA cores, fastest in reduced precision (FP16/BF16). See 2.8. |
| **Mixed-precision training** | Training with a master copy of the weights kept in FP32 for numerical stability while the forward and backward pass run in FP16 on Tensor Cores, using loss scaling (multiplying the loss by a constant before the backward pass and dividing it back out afterward) to keep small gradient values from underflowing to zero in FP16's narrower range. See 2.8. |
| **Systolic array (TPU)** | The architecture at the core of a TPU: a grid of simple processing elements where a value and a running partial sum flow through the grid in a tightly pipelined wave, so an entire matrix multiplication is computed by the flow itself rather than being orchestrated instruction by instruction the way a GPU's cores are. See 2.8. |
| **Arithmetic intensity / Roofline model** | Arithmetic intensity is the number of floating-point operations performed per byte moved from memory (FLOPs / bytes moved). The roofline model plots achievable performance against arithmetic intensity: performance is capped by memory bandwidth at low intensity (memory-bound) and by peak compute throughput at high intensity (compute-bound), with the ridge point marking where the two limits meet. See 2.8. |
| **Quantization** | Representing a trained model's weights (and often activations) in a lower-precision integer format, typically INT8 or INT4, than the FP16/BF16 used during mixed-precision training, shrinking the bytes that must move from memory per inference request at some cost to numerical precision. See 2.8. |
| **RAG (Retrieval-Augmented Generation)** | Augmenting an LLM's response with content retrieved from an external knowledge source at inference time, rather than relying solely on what the model learned during training. See Phase 6. |
| **SLM (Small Language Model)** | A language model deliberately sized down from frontier-scale LLMs for cost, latency, privacy, or on-device deployment reasons. See 13.11–13.13. |
| **Tool / Function Calling** | A model's ability to emit a structured request to invoke an external function/API, whose result is then fed back into the model's context. See 5.3, 5.4, 8.4. |
| **Trajectory (agent eval)** | The full sequence of an agent's tool calls and intermediate reasoning steps toward an answer — evaluated separately from whether the final answer was correct. See 15.2. |
| **OBO (On-Behalf-Of) flow** | An OAuth pattern where an agent acts using a token scoped to a specific human user's permissions, rather than a standing service-account identity. See 15.5. |
| **Autonomy Level (L0–L5)** | A framework for describing how much of a task an agent is trusted to complete without human approval, from L0 (no autonomy) to L5 (fully autonomous). See 10.8. |
| **Landing zone** | The pre-configured, governed cloud environment (network, IAM, guardrails) an enterprise agent platform is deployed into. See 15.10. |
| **Tokenization** | The process of splitting raw text into a sequence of discrete units (tokens) drawn from a fixed vocabulary, the first step in turning text into the numeric input a model consumes. See 3.1; the specific segmentation algorithms (BPE, WordPiece, SentencePiece) are covered in 3.5. |
| **Token ID / Vocabulary** | A tokenizer's fixed, closed set of recognized tokens (the vocabulary), each assigned a unique integer index (its token ID) used to retrieve that token's row in an embedding matrix. See 3.1. |
| **Embedding / Embedding matrix** | A dense, low-dimensional vector representation of a token (an embedding), retrieved by indexing into a learned V x d embedding matrix by token ID. Contrast with a one-hot vector, which uniquely identifies a token but encodes no relationship to any other token. See 3.1. |
| **Distributional hypothesis** | The linguistic claim, associated with J.R. Firth (1957), that a word's meaning is characterized by the contexts it tends to occur in; the theoretical basis for learning embeddings from co-occurrence statistics rather than from explicit, hand-written definitions. See 3.1; operationalized into a concrete training objective by Word2Vec in 3.2. |
| **Static embedding** | A word representation that assigns exactly one fixed vector per token regardless of the surrounding sentence, so the same token has an identical vector in every context it appears in. Contrast with a contextual embedding, covered in 3.2. See 3.1. |
| **Word2Vec (skip-gram / CBOW)** | A method for training static word embeddings from raw text by predicting nearby context words from a center word (skip-gram) or predicting a center word from its averaged context (CBOW), turning the distributional hypothesis (3.1) into a trainable objective. See 3.2. |
| **Negative sampling** | A training shortcut that replaces an expensive full-vocabulary softmax with binary classification of a true center/context word pair against a handful of randomly sampled negative words, making large-vocabulary embedding training computationally tractable. See 3.2. |
| **Contextual embedding** | A token representation computed fresh for each occurrence from its surrounding sequence (via a bidirectional LSTM as in ELMo, or a bidirectional Transformer encoder as in BERT), rather than retrieved from a fixed per-token lookup table. Contrast with a static embedding. See 3.2. |
| **Causal (autoregressive) language modeling** | A training objective that predicts each token using only the tokens before it, enforced by a causal mask (2.5) that blocks attention to future positions. The natural objective for open-ended generation (GPT family). See 3.3. |
| **Masked language modeling (MLM)** | A training objective that hides a subset of input tokens and predicts them from the full bidirectional context. BERT's specific recipe masks about 15% of positions, replacing 80% with `[MASK]`, 10% with a random token, and leaving 10% unchanged. Has no natural mechanism for open-ended generation. See 3.3. |
| **Seq2seq (encoder-decoder)** | An architecture pairing a bidirectional encoder that reads a full input sequence with a causal decoder that generates a separate output sequence, connected by cross-attention. The natural fit for transformation tasks like translation and summarization (T5, BART). See 3.3. |
| **Cross-attention** | An attention mechanism where one sequence's positions (a decoder's) attend over a different sequence's output (an encoder's) as keys and values, rather than attending over positions within the same sequence as in self-attention (2.5). See 3.3. |
| **Teacher forcing / Exposure bias** | Teacher forcing feeds the ground-truth previous token into a decoder during training regardless of the model's own prediction, which trains efficiently but creates exposure bias: a mismatch where the model never practices recovering from its own mistakes, since at inference it must feed back its own, possibly incorrect, predictions instead. See 3.3. |
| **Perplexity** | A standard language model evaluation metric, the exponential of the average per-token cross-entropy loss over a held-out set. Lower perplexity means the model assigned higher probability to the actual held-out tokens on average. See 3.3. |
| **Zero-shot / few-shot task transfer** | Zero-shot: a model performs a new task from a natural-language instruction alone, with no labeled examples and no weight updates. Few-shot (in-context learning): a handful of input-output examples are placed directly in the prompt, letting the model adapt its output format to a new task with no weight updates either. Both rely on scale; GPT-2 demonstrated zero-shot transfer, GPT-3 demonstrated strong few-shot in-context learning. See 3.4. |
| **Span corruption (T5)** | T5's pretraining objective: contiguous spans of the input are replaced with a single sentinel token, and the decoder must generate only the missing spans, not reconstruct the whole input. Contrast with BART's denoising autoencoder objective. See 3.4. |
| **Denoising autoencoder (BART)** | BART's pretraining objective: the input is corrupted with a mix of noise functions (token masking, token deletion, text infilling, sentence permutation, document rotation), and the decoder must reconstruct the entire original, uncorrupted document. Contrast with T5's span corruption, which generates only the missing spans. See 3.4. |
| **Disentangled attention (DeBERTa)** | An attention variant that represents each token with two separate vectors, one for content and one for relative position, computing attention weights from both separately rather than from a single combined vector. Lets the model capture how much a word's relevance depends on relative position versus content more precisely than standard self-attention (2.5). See 3.4. |
| **Byte Pair Encoding (BPE)** | A subword tokenizer algorithm that starts from individual characters (or bytes) and repeatedly merges whichever adjacent pair occurs most frequently in the training corpus into a new vocabulary entry, until reaching a target vocabulary size. Purely frequency-driven. Byte-level BPE (GPT-2 onward) runs this over raw UTF-8 bytes, guaranteeing any input string is encodable with no unknown-token fallback needed. See 3.5. |
| **WordPiece** | A subword tokenizer algorithm (used by BERT) with the same bottom-up merge structure as BPE, but that scores each candidate merge by how much it increases the training data's likelihood rather than by raw frequency, a criterion closer to pointwise mutual information. Falls back to `[UNK]` for input it cannot encode. See 3.5. |
| **SentencePiece** | A language-independent tokenizer framework that treats input as a raw character stream, replacing whitespace with a reserved meta-symbol rather than pre-splitting on it, making tokenization fully reversible and usable on languages without whitespace-delimited words. Can run BPE-style merging or the Unigram algorithm internally. Used by T5, mT5, ALBERT, and XLNet. See 3.5. |
| **Unigram language model tokenizer** | A subword algorithm (used inside SentencePiece) that works top-down: starting from a large candidate vocabulary and iteratively pruning whichever tokens contribute least to the training corpus's likelihood via expectation-maximization, the opposite structural direction from BPE and WordPiece's bottom-up merging. Assigns probabilities to multiple valid segmentations of the same string, enabling subword regularization. See 3.5. |
| **Subword regularization** | Training on multiple different valid segmentations of the same input example, sampled according to a probabilistic tokenizer's assigned probabilities, rather than always using one fixed segmentation, which can improve robustness to unusual or noisy input at inference time. Requires a probabilistic algorithm like Unigram; BPE and WordPiece produce one deterministic segmentation per string. See 3.5. |
| **Scaling laws** | Empirical power-law relationships describing how a language model's test loss falls as model size, training data size, or total compute independently increase, holding smoothly across many orders of magnitude. First characterized by Kaplan et al. (2020). See 3.6. |
| **Compute-optimal scaling (Chinchilla)** | The corrected finding that, for a fixed training compute budget, model size and training data size should scale roughly in proportion to each other, rather than favoring model size the way the earlier Kaplan-era heuristic suggested. Demonstrated by Chinchilla (70B parameters, 1.4 trillion tokens) outperforming Gopher (280B parameters, roughly 300 billion tokens) at equal training compute. See 3.6. |
| **Emergent ability** | A capability not present in smaller models, present in larger models, and not predictable by extrapolating the performance trend observed at smaller scales, such as certain multi-step arithmetic tasks that stay near random chance until a scale threshold, then rise sharply. Distinct from the smooth power-law curves scaling laws describe. See 3.6. |
| **Emergent abilities mirage (critique)** | The argument that at least some observed emergent-ability jumps result from using a discontinuous evaluation metric (such as exact-match accuracy, where any single wrong token fails the whole answer) rather than a genuine change in the underlying model; switching to a continuous metric on the same models can turn some apparently sharp jumps into smooth curves. Does not settle the question for every documented case. See 3.6. |
| **Open-weight vs. open-source (model)** | A model is open-weight when its trained parameter values are published for download; this alone does not mean the training data, training code, or full methodology is also published, which a stricter open-source definition would require. Most models marketed as "open" release only weights and inference code. See 3.7. |
| **Size class (frontier / mid-size / small-edge)** | A model's broad capability-versus-deployability tier. Frontier or flagship models offer the highest capability at the highest cost, latency, and hardware requirement. Mid-size models trade some capability for lower cost and feasible self-hosting on a few GPUs. Small or edge models (SLMs) trade further capability for the ability to run on a single consumer GPU or on-device. See 3.7. |
| **Explicit-density / implicit-density (generative model)** | A further split among generative models. An explicit-density model computes a real, well-defined probability for each output it could produce (an autoregressive LLM, whose perplexity, 3.3, is a direct summary of those probabilities). An implicit-density model never computes any such probability, learning only to produce samples that are hard to distinguish from real data (a GAN). Only an explicit-density model's output can be interrogated for how confident it was. See 4.1. |
| **Generative learning trilemma** | The observation, named by Xiao, Kreis, and Vahdat (2022), that high sample quality, full coverage of the data distribution's diversity, and fast sampling are three goals no single generative model family achieves simultaneously with methods available today: GANs sacrifice diversity, VAEs sacrifice quality, diffusion models sacrifice speed. See 4.1. |
| **Mode collapse** | A GAN failure mode where the generator learns to reliably produce only a narrow subset of the true data's variety rather than covering its full diversity, while still reliably fooling the discriminator. A specific risk of implicit-density training rather than of generative models generally. See 4.1. |
| **Variational Autoencoder (VAE)** | A generative model that encodes an input into the parameters of a latent distribution, samples a latent vector from it, and decodes that vector back into a reconstruction. Trained by maximizing the evidence lower bound (ELBO), a lower bound on the true data likelihood rather than the exact likelihood itself, making it explicit-density in spirit but only approximately so. Its structured, smooth latent space supports meaningful interpolation between samples. See 4.2. |
| **Evidence lower bound (ELBO)** | The training objective a VAE actually maximizes: a reconstruction term (the decoder should recover the original input from its latent code) plus a term pulling the encoder's output distribution toward a simple prior. A provable lower bound on the true data likelihood, not the likelihood itself. See 4.2. |
| **GAN minimax game** | The adversarial training setup where a generator tries to maximize a discriminator's error rate and a discriminator tries to correctly classify real versus generated samples. At the theoretical equilibrium the generator's output distribution matches the real data distribution exactly, though this equilibrium is difficult to reach reliably in practice. See 4.2. |
| **Diffusion model (forward / reverse process)** | A generative model built from a fixed forward process that gradually adds Gaussian noise to real data over many steps, and a learned reverse process that removes a bit of noise at each step. Running the trained reverse process starting from pure noise produces a new realistic sample. Explicit-density but only approximately so, trained via a variational bound. See 4.2. |
| **Latent diffusion** | Running a diffusion model's forward and reverse process inside a much smaller VAE-compressed latent space rather than directly on raw pixels, decoding back to pixels only at the end. The architecture behind Stable Diffusion, combining a VAE's compression with a diffusion model's denoising for practical high-resolution generation. See 4.2. |
| **Diffusion distillation (e.g., consistency models)** | A technique that trains a model to map a noisy input directly to a clean sample in a small handful of steps, or even one, rather than the full many-step reverse diffusion process, trading a small amount of quality for a large reduction in sampling cost. See 4.2. |
| **Greedy decoding** | A decoding strategy that always chooses the single highest-probability next token, with no lookahead. Deterministic and cheap, but prone, along with beam search, to repetitive, degenerate text, because maximizing likelihood at every step does not match how real human text is actually distributed. See 4.3. |
| **Beam search** | A decoding strategy that tracks the top k highest-probability partial sequences (the beam) at every step, expanding and re-pruning back to k candidates, approximating the single highest-probability full sequence. Shares greedy decoding's tendency toward repetitive, degenerate output. See 4.3. |
| **Temperature (decoding)** | A value the logits are divided by before the final softmax during decoding. Below 1, it sharpens the distribution toward greedy decoding; above 1, it flattens the distribution, giving lower-probability tokens more chance of being sampled at the cost of coherence. See 4.3. |
| **Top-k sampling** | A sampling strategy that restricts token choice to the k highest-probability tokens at each step, regardless of the shape of the distribution, then renormalizes and samples from that fixed-size pool. See 4.3. |
| **Nucleus (top-p) sampling** | A sampling strategy that restricts token choice to the smallest set of tokens whose cumulative probability exceeds a threshold p, then renormalizes and samples. Unlike top-k, its candidate pool size adapts to the distribution's shape at each step: small when the model is confident, larger when genuinely uncertain. See 4.3. |
| **Speculative decoding** | An inference-speed technique, orthogonal to which decoding strategy is used, where a small draft model proposes several tokens ahead and the full target model verifies them in one forward pass, accepting matches and substituting its own choice at the first mismatch. Provably preserves the target model's exact output distribution while reducing the number of expensive forward passes needed. See 4.3. |
| **Cross-attention conditioning (diffusion)** | Letting a diffusion model's denoising network attend, at every step of the reverse process, to an embedding of a conditioning signal such as a text prompt, so the prompt steers generation rather than the model producing an arbitrary sample from the training distribution. See 4.4. |
| **Classifier-free guidance** | A technique that sharpens a diffusion model's adherence to its conditioning without a separately trained classifier: the same model is trained both with the conditioning present and, some fraction of the time, with it randomly dropped, and at sampling time the result extrapolates away from the unconditional prediction and toward the conditional one. See 4.4. |
| **Spacetime patches (video diffusion)** | Representing video as patches spanning both a spatial region and a span of time together, rather than patches of a single still frame, letting a diffusion transformer model frame-to-frame temporal consistency directly instead of generating frames independently and stitching them together afterward. See 4.4. |
| **Neural audio codec** | A learned model that compresses raw audio into a sequence of discrete tokens (and reconstructs audio from them), playing the same structural role for audio that a tokenizer (3.5) plays for text. The foundation for treating speech generation as an autoregressive, token-based problem. See 4.4. |
| **Prefill / decode** | The two phases of LLM inference. Prefill processes an entire input prompt in one forward pass and is compute-bound, with cost growing roughly quadratically in prompt length due to self-attention (2.5). Decode generates output tokens one at a time and is memory-bandwidth-bound, dominated by reading an ever-growing cache at every step rather than by raw computation. See 4.5. |
| **KV cache** | Storing each generated token's key and value vectors so a later decode step can attend over the full prefix without recomputing it from scratch. Its size, and the memory traffic needed to read it, grows linearly with sequence length, making it the central resource constraint on decode. See 4.5. |
| **FlashAttention** | An IO-aware attention algorithm (Dao et al., 2022) that tiles the attention computation to stay within fast on-chip GPU memory, avoiding materializing the full attention matrix in slower memory. Produces an exact result, mathematically identical to standard attention, while sharply reducing memory reads and writes rather than approximating the computation. See 4.5. |
| **RoPE (Rotary Position Embedding)** | A relative position encoding (Su et al., 2021) that rotates query and key vectors as a function of position rather than adding a separate position vector, generalizing better to sequence lengths beyond those seen in training than earlier learned or fixed absolute position embeddings. See 4.5. |
| **ALiBi (Attention with Linear Biases)** | A position-encoding alternative (Press et al., 2021) that adds no positional embedding at all, instead biasing attention scores directly by a penalty proportional to the distance between positions, demonstrated to extrapolate to sequences considerably longer than those seen in training. See 4.5. |
| **Grouped-query attention (GQA)** | An attention variant (Ainslie et al., 2023) in which multiple query heads share a smaller number of key/value groups, rather than every head storing its own separate keys and values as in standard multi-head attention. Shrinks KV cache size directly, and existing multi-head checkpoints can be adapted into it rather than retrained from scratch. See 4.5. |
| **"Lost in the middle" (positional recall)** | The finding (Liu et al., 2023) that a language model's recall accuracy for information placed in a long context follows a U-shaped curve: strongest near the beginning or end, and weaker for information placed in the middle, even on sequences well within the model's supported length. A distinct problem from length extrapolation (RoPE, ALiBi above), since it concerns where within a supported context recall is reliable, not how long a context the model can process at all. See 4.5. |
| **Hallucination (intrinsic / extrinsic)** | Generated content that is false or unsupported, stated as confidently as accurate output. Ji et al. (2022/2023) split it into intrinsic hallucination, which directly contradicts a given source, and extrinsic hallucination, content the source can neither confirm nor deny, whether or not it happens to be true. See 4.6. |
| **Hallucination's statistical floor** | Kalai and Vempala's result (2023, STOC 2024) that even a perfectly calibrated model trained on entirely accurate data must still hallucinate at some baseline rate on facts that appeared only once or a handful of times in training, roughly tied to how many such singleton facts exist. Applies most strongly to arbitrary, rare facts, far less to systematic, learnable knowledge like arithmetic. See 4.6. |
| **Confident-guessing incentive** | The argument (Kalai, Nachum, Vempala, and Zhang, 2025) that hallucination persists in deployed systems partly because standard benchmark scoring is binary and treats a wrong, confident answer the same as an honest expression of uncertainty, statistically favoring guessing over calibrated abstention. See 4.6. |
| **SelfCheckGPT** | A black-box, sampling-based hallucination detector (Manakul, Liusie, and Gales, 2023) that samples a prompt multiple times and checks the mutual consistency of the responses, reasoning that a genuinely known fact tends to be reproduced consistently while a hallucinated detail is more likely to vary. Needs no model internals or external knowledge source. See 4.6. |
| **Semantic entropy** | A hallucination-detection refinement (Farquhar et al., Nature, 2024) that clusters sampled outputs by whether they mean the same thing rather than whether they are worded the same way, then measures entropy over those meaning-based clusters; high semantic entropy flags likely confabulation. See 4.6. |
| **Chain-of-Verification (CoVe)** | A mitigation technique (Dhuliawala et al., 2023) in which a model drafts an answer, independently generates verification questions targeting its own claims, answers those questions independently, and revises the original answer based on any inconsistencies found. See 4.6. |
| **Red-teaming (LLMs)** | Adversarially probing a model to elicit harmful outputs before deployment, so failure modes can be found and fixed in advance. Ganguli et al. (Anthropic, 2022) used large numbers of human red-teamers; Perez et al. (DeepMind, 2022) automated the process by using one language model to generate adversarial test cases against a target model. See 4.7. |
| **Runtime moderation classifier** | A classifier, often itself a fine-tuned LLM, that scores prompts and/or model outputs against a defined harm taxonomy at inference time, flagging or blocking risky content. Llama Guard (Inan et al., Meta, 2023) is a widely cited example, building on the classifier concept OpenAI's Moderation model established (Markov et al., 2022). See 4.7. |
| **Text watermarking (green list / red list)** | Embedding a statistical signal in generated text by, at each step, using a pseudorandom hash of preceding tokens to split the vocabulary into a green list and a red list, then softly biasing sampling toward the green list. Detection is a statistical test on the fraction of green-list tokens, needing the same hash/key but not the model's internals (Kirchenbauer et al., 2023). Degrades under paraphrasing; unreliable on very short text. See 4.7. |
| **SynthID (text / image / video)** | Google DeepMind's watermarking family. SynthID-Text (Dathathri et al., Nature, 2024) uses a key-seeded pairwise tournament over candidate tokens drawn from the model's own unmodified distribution, better preserving output quality than a green/red-list logit bias. SynthID for images and video (2023) embeds an imperceptible signal directly into pixel data via a trained model pair, robust to common transformations, with detection returning a confidence level rather than a binary certainty. See 4.7. |
| **C2PA / Content Credentials (provenance)** | A cryptographically signed manifest, per the C2PA standard (founded 2021 by Adobe, Microsoft, Truepic, Arm, Intel, and the BBC), attached to a piece of media recording its creation and edit history, including AI tool involvement. Tamper-evident, but metadata-based rather than embedded in the content itself, so it can be stripped by a screenshot, re-export, or re-encoding pipeline, unlike a watermark. See 4.7. |
| **Instruction tuning (FLAN)** | Fine-tuning a language model on a large mixture of tasks phrased as natural-language instructions (Wei et al., 2021), substantially improving zero-shot performance on held-out, unseen task types through generalization across instruction phrasing, not memorization of any single task's format. See 5.1. |
| **RLHF / InstructGPT** | A three-stage pipeline (Ouyang et al., 2022, previewed in 5.1, covered fully in Phase 7): supervised fine-tuning on human demonstrations, then a reward model trained on human preference rankings, then reinforcement learning using that reward model, aligning a model with actual user intent rather than only task format. Human evaluators preferred a 1.3B InstructGPT model's outputs over the 175B base GPT-3 model's. See 5.1. |
| **Few-shot example order sensitivity** | The finding (Lu et al., 2021) that permuting the order of the same few-shot examples, with none added, removed, or reworded, can swing a model's accuracy on the same task from near state-of-the-art to close to random chance. See 5.1. |
| **Few-shot bias and contextual calibration** | Zhao et al. (2021) identify majority-label bias, recency bias, and common-token bias in few-shot prompted models; their fix, contextual calibration, probes the model with a content-free input (e.g. "N/A") to estimate and cancel this bias, raising accuracy and reducing variance across example choices. See 5.1. |
| **Chain-of-thought (CoT) prompting** | Writing out intermediate reasoning steps in few-shot examples rather than jumping straight to a final answer (Wei et al., 2022), substantially improving multi-step reasoning. The benefit is scale-dependent: it "does not positively impact performance for small models, and only yields performance gains when used with models of approximately 100 billion parameters," with smaller models tending to produce "fluent but illogical chains of thought." See 5.2. |
| **Zero-shot chain-of-thought** | Appending a single phrase such as "Let's think step by step" before the model's answer, with zero worked reasoning examples in the prompt at all (Kojima et al., 2022), reliably eliciting step-by-step reasoning and producing large accuracy gains over a plain zero-shot prompt without requiring any prompt-design effort beyond the phrase itself. See 5.2. |
| **Self-consistency** | Sampling several independent reasoning paths for the same prompt via temperature or nucleus sampling, rather than committing to one greedily decoded chain-of-thought path, and taking a majority vote over the paths' final answers while discarding the reasoning text itself (Wang et al., 2022/2023). Improves accuracy over single-path CoT at the cost of running inference multiple times per question. See 5.2. |
| **Tree-of-thought** | Maintaining a tree of intermediate reasoning steps, self-evaluating how promising each partial path looks, and using a search strategy such as breadth-first or depth-first search with backtracking to abandon unpromising branches (Yao et al., 2023). Unlike chain-of-thought or self-consistency, it can revisit and abandon a reasoning path once started, at substantially higher inference cost. See 5.2 and 8.7. |
| **Least-to-most prompting** | Decomposing a problem into a sequence of simpler subproblems and solving them in order, feeding each subproblem's solution in as context for the next, rather than reasoning through an entire problem in one continuous pass (Zhou et al., 2022). Especially effective for generalizing to inputs harder than anything shown in the prompt's examples. See 5.2. |
| **Chain-of-thought faithfulness (or lack of it)** | The finding (Turpin et al., 2023) that a chain-of-thought explanation can be systematically unfaithful to what actually drove a model's answer: deliberately biasing an input can shift the model's answer while its stated reasoning never mentions the biasing feature, instead constructing a plausible-sounding rationale for whatever the bias produced. A CoT trace can still be a useful tool for eliciting better answers while remaining an unreliable explanation of why an answer was reached. See 5.2. |
| **Native function / tool calling** | An API primitive, distinct from prompting, in which the caller supplies one or more tool schemas (name, description, and a JSON Schema of parameters) alongside a prompt, and the model returns either a normal message or a structured call to a specific tool with typed arguments (OpenAI, June 2023; Anthropic's tool use, via an `input_schema` and a returned `tool_use` content block). Executing the tool and returning its result remain the calling application's responsibility. See 5.3 and 8.4. |
| **Constrained decoding (structured outputs)** | Restricting token sampling itself at each decoding step to only continuations consistent with a target JSON schema, via a context-free-grammar-style constraint over the model's vocabulary, rather than merely prompting the model to follow a schema. OpenAI's Structured Outputs mode (2024) reported 100% schema-valid outputs under this constraint, versus under 40% for an older model prompted without enforcement. Guarantees shape, never the correctness of the values themselves. See 5.3 (basics); full mechanism covered in 5.4. |
| **ReAct** | A prompting pattern (Yao et al., 2022) that interleaves reasoning traces, tool-use actions, and the observations those actions return, letting each reasoning step take a prior action's actual result into account rather than planning an entire action sequence blindly upfront. Raised task success by 34 percentage points on an interactive decision-making benchmark and reduced hallucinated claims relative to chain-of-thought prompting on knowledge-intensive QA. The conceptual ancestor of today's multi-step tool-calling agent loops. See 5.3, 8.3, and 8.7. |
| **tool_result and is_error** | The return leg of a native tool call: after the calling application executes a requested tool, it reports the outcome back to the model as a `tool_result` block carrying an explicit `is_error` flag plus a content field, rather than folding success or failure into free text the model has to interpret from tone or shape. `is_error` distinguishes a call rejected before execution, safe to retry after correction, from a call that executed and then failed, which is not automatically safe to retry. See 8.4. |
| **Parallel tool calls** | A single model turn that proposes more than one tool call at once, appropriate when the calls are independent of each other, rather than one call whose result the next call depends on. The calling application decides whether to execute the proposed calls concurrently or in sequence; the model's single turn only establishes that they do not need each other's results first. See 8.4. |
| **Gorilla / Berkeley Function-Calling Leaderboard** | Gorilla (Patil et al., 2023) fine-tunes a model specifically for API-calling accuracy, retrieving relevant API documentation at inference time to reduce hallucinated calls, and surpasses GPT-4 at writing correct API calls in its own evaluation. The same team's Berkeley Function-Calling Leaderboard (BFCL) evaluates function-calling accuracy across categories including single calls, choosing among multiple candidate functions, and parallel calls. See 5.3. |
| **Token masking (grammar-constrained decoding)** | The mechanism behind a hard structured-output guarantee: a target JSON Schema is compiled into a grammar, and at every decoding step the logits over the model's vocabulary are adjusted so any token that would violate the grammar is excluded before sampling (Geng et al., 2023; OpenAI, 2024). Guarantees structural validity, never the correctness of the values themselves. See 5.4. |
| **Tokenization-boundary problem** | The challenge that grammars are naturally defined over characters while models generate subword tokens, and the same string can tokenize more than one way (e.g. "[[[" as three tokens or one), so a purely character-level grammar cannot alone determine which token-level completions a model's vocabulary supports (Geng et al., 2023). Addressed by compiling a tokenizer-specific concrete grammar, or by precomputing a state-to-token index as Outlines does. See 5.4. |
| **Outlines (FSM-based constrained generation)** | A library (Willard and Louf, 2023) that compiles a regular expression or JSON Schema into a finite-state machine and precomputes an index mapping each state to its valid vocabulary subset, turning each decoding step into a fast lookup rather than a fresh parse, guaranteeing structural validity without retries. See 5.4. |
| **XGrammar** | A structured-generation engine (Dong et al., 2024) that splits a model's vocabulary into context-independent tokens, over 99% in practice, precomputed once, versus a small context-dependent remainder needing a runtime check, reporting up to roughly a 3x speedup on JSON-Schema mask computation and over 100x on more general context-free-grammar workloads versus earlier engines. See 5.4. |
| **Prompt injection** | Untrusted input interpreted by a model as an instruction rather than as inert data, allowing that input to override a developer's own instructions (Simon Willison, 2022), the same underlying shape of bug as a SQL injection attack. See 5.5. |
| **Indirect prompt injection** | Prompt injection that requires no malicious input from a user at all: an attacker plants instructions inside third-party content, such as a webpage, document, or email, that a model is merely expected to retrieve and read on a legitimate user's behalf (Greshake et al., 2023, demonstrated against a GPT-4-powered Bing Chat). See 5.5. |
| **Instruction hierarchy** | A training approach (Wallace et al., 2024, OpenAI) that establishes an explicit priority order among instructions reaching a model, system above user above third-party or tool content, so the model learns to selectively ignore a conflicting lower-privilege instruction. Reported to drastically increase robustness, even against attack types not seen during training. See 5.5. |
| **Privilege separation (for tool/retrieved content)** | An architectural pattern that converts retrieved or tool-returned content into a restricted, typed structure the surrounding application consumes as data, rather than concatenating raw text back into a prompt where a model could misread it as a new instruction. Applies the structured-output discipline of 5.3/5.4 to an application's input side. See 5.5. |
| **Guardrail frameworks (NeMo Guardrails, Llama Guard)** | External, model-independent layers that check or reshape content around a model rather than relying on what the model itself was trained to prioritize. NeMo Guardrails is an open-source toolkit defining programmable rails across input, dialog, retrieval, execution, and output stages; Llama Guard is a model fine-tuned specifically to classify prompts and responses against a safety taxonomy. See 5.5. |
| **Golden dataset** | A curated, versioned collection of representative inputs, usually paired with a reviewed definition of a correct response, that every candidate prompt version is run and re-run against before deployment. See 5.6. |
| **LLM-as-judge** | Using a model call to grade another model's output against a rubric at a scale no human review team could sustain. Zheng et al. (2023) found a strong judge model agreed with human preference about as often as humans agreed with each other, while documenting position bias, verbosity bias, and self-enhancement bias as recurring failure modes. See 5.6. |
| **G-Eval** | A judge-quality technique (Liu et al., 2023) in which the judge model first generates its own chain-of-thought of evaluation steps from the task description and criteria, then uses that reasoning to produce a structured, form-filled score, reporting a 0.514 Spearman correlation with human judgment on a summarization benchmark. See 5.6. |
| **Prompt versioning and diffing** | Treating a prompt edit as a commit with a visible diff and a tag, rather than an in-place overwrite, so a grading result can always be traced to an exact, reproducible prompt version. Implemented by tools such as LangSmith, PromptLayer, and Weights & Biases Weave. See 5.6. |
| **Automatic prompt optimization (APE, DSPy)** | Treating a prompt, or an entire multi-step pipeline of prompts, as an optimizable parameter rather than hand-tuned text. APE (Zhou et al., 2022) searches and scores candidate instructions with an LLM; DSPy (Khattab et al., 2023) compiles a pipeline's prompts and demonstrations via a "teleprompter" optimizer against a training set and a metric. See 5.6. |
| **LLM gateway** | A routing layer sitting between an app and multiple model providers, so an outage or rate limit at one provider triggers an automatic fallback to another rather than taking the app down. Distinct from per-request exponential backoff, which retries against the same provider that just failed. Implemented by tools such as LiteLLM and Portkey. See 5.7. |
| **Semantic cache** | A cache that embeds each incoming query and serves a stored response whenever a new query falls within a similarity threshold of one already answered, rather than requiring an exact text match. Implemented by tools such as GPTCache. See 5.7. |
| **Stateless conversation API** | The default behavior of chat completion APIs (OpenAI, Anthropic): a request carries no memory of prior turns, so the calling application, not the API, is responsible for resending the full conversation history with every new request. See 5.7. |
| **Orchestration layer** | The part of an LLM app that assembles a prompt, retrieved context, tools, and conversation history into one coherent request, and carries state across multiple calls. Named as a distinct layer in Bornstein and Radovanovic's a16z reference architecture (2023); LangChain and LlamaIndex are the best-known examples, both since repositioned toward agent frameworks. See 5.7. |
| **Retrieval-augmented generation (RAG)** | Grounding a model's response in retrieved, external documents passed into the prompt at query time, rather than relying only on knowledge baked into its weights at training time. Named and formalized by Lewis et al. (2020), who combine "a pre-trained seq2seq model" (parametric memory) with a retriever over a document index (non-parametric memory) specifically because a model's "ability to access and precisely manipulate knowledge is still limited." Best suited to answers that must be current, domain-specific, or citable. Covered at decision-framework level in 5.8; the retrieval pipeline itself (ingestion, chunking, reranking) is covered in full in Phase 6. |
| **Fine-tuning** | Further training a pretrained model's own weights on labeled examples of a target task, so a behavior, format, or narrow skill no longer needs to be re-explained in every prompt. Full fine-tuning updates every weight; parameter-efficient techniques such as LoRA (Hu et al., 2021) freeze the base weights and train a much smaller set of additional parameters instead. Best suited to a narrow, high-volume behavior expensive to keep re-explaining; cannot offer up-to-date knowledge or source citations on its own. See 5.8; the mechanics of full and parameter-efficient fine-tuning are covered in full in Phase 7. |
| **RAFT (Retrieval Augmented Fine-Tuning)** | Fine-tuning a model specifically to make better use of retrieved context: to distinguish a genuinely relevant retrieved passage from an irrelevant distractor, and to cite the passage it actually relied on (Zhang et al., 2024). A concrete example of combining RAG and fine-tuning rather than treating them as mutually exclusive. See 5.8. |
| **Parametric memory (vs. non-parametric memory)** | Parametric memory is knowledge compressed into a model's own weights during training: broad and genuinely useful (Petroni et al., 2019, documented "the surprisingly strong ability of these models to recall factual knowledge without any fine-tuning"), but frozen at the training cutoff, uncited, and unevenly learned. Non-parametric memory is an external, queryable corpus or index consulted at inference time, which can be updated, cited, and curated independently of the model. RAG pairs the two. See 6.1. |
| **Catastrophic forgetting** | The tendency of a neural network to lose previously learned knowledge while being trained on new information in sequence, unless the training procedure specifically protects the earlier knowledge (Kirkpatrick et al., 2017, who note "it has been widely thought that catastrophic forgetting is an inevitable feature of connectionist models"). The core reason naively retraining a model to refresh stale knowledge carries real risk. See 6.1. |
| **Localized factual associations (knowledge editing)** | The finding (Meng et al., 2022, ROME) that a specific fact in a transformer's weights corresponds to "localized, directly-editable computations" concentrated in middle-layer feed-forward modules, rather than a simple lookup table. Explains why directly editing one fact in a model, without corrupting nearby facts or general behavior, is a genuinely hard, still-active research problem. See 6.1. |
| **Embedding** | A fixed-size vector of numbers representing a piece of text, positioned so that texts with similar meaning land near each other in the vector space, regardless of the specific words each one uses. Traces to Mikolov et al.'s word2vec (2013) for individual words and Reimers and Gurevych's Sentence-BERT (2019) for whole sentences and passages. The foundation retrieval in RAG is built on. See 6.2. |
| **Approximate nearest neighbor (ANN) search** | Finding a vector within a small, controllable factor of the true closest match to a query vector, rather than the exact closest one, in exchange for search that stays fast and memory-efficient once a collection holds millions or billions of vectors. Proposed by Indyk and Motwani (1998) as a way around the curse of dimensionality, which leaves exact nearest-neighbor structures facing "little improvement over the brute-force algorithm" at scale. See 6.2. |
| **Curse of dimensionality** | Richard Bellman's 1957 term for how quickly a search space grows as dimensions are added to it, which is why classic indexing structures that work well in two or three dimensions stop helping once a vector space has hundreds or thousands of dimensions. The reason exact nearest-neighbor search does not scale, and the motivation behind approximate nearest neighbor search. See 6.2. |
| **HNSW (Hierarchical Navigable Small World)** | A graph-based approximate-nearest-neighbor algorithm (Malkov and Yashunin) that connects each vector to a handful of neighbors across sparse, long-range upper layers and dense, local lower layers, reported to allow "a logarithmic complexity scaling" for search. Tends to win on recall at a given latency, at the cost of the memory graph edges add. See 6.2. |
| **IVF (Inverted file index)** | A cluster-based approximate-nearest-neighbor approach that partitions a vector space into cells around a set of centroids, so a query searches only the cell it falls into plus a configurable number of neighboring cells, a count usually called `nprobe`. Simple to reason about and tune; raising `nprobe` trades speed for recall directly. See 6.2. |
| **Product quantization (PQ)** | A compression-based approximate-nearest-neighbor technique (Jegou, Douze, and Schmid, 2011) that splits each vector into subvectors and quantizes each one independently into a short code, refining distance estimates from those codes without reading full vectors from disk. The most memory-efficient of the major ANN families, demonstrated at billion-vector scale in a companion paper (Jegou, Tavenard, Douze, and Amsaleg). See 6.2. |
| **Cosine similarity vs. dot product** | Two ways of comparing embedding vectors: cosine similarity measures only the angle between two vectors, ignoring their length, while dot product grows with vector length as well as angle, which can let frequently-occurring or "popular" content dominate a ranking. When every vector is normalized to unit length, the two become proportional to each other. See 6.2. |
| **MTEB (Massive Text Embedding Benchmark)** | A standardized benchmark (Muennighoff et al., 2022) spanning "8 embedding tasks," "58 datasets," and "112 languages," built because embedding models were typically evaluated on one narrow task at a time. Its central finding, that "no particular text embedding method dominates across all tasks," is why choosing an embedding model is a benchmarking decision rather than a one-time pick of a leaderboard leader. See 6.2. |
| **Vector database** | The production system wrapped around an ANN index (HNSW, IVF, product quantization): insert, update, and delete support without a full rebuild, metadata filtering alongside similarity, multi-tenant isolation, and a concrete deployment model. Four common archetypes are fully managed serverless (e.g. Pinecone), self-hosted distributed (e.g. Milvus), added directly to an existing database (e.g. pgvector), and embedded or lightweight (e.g. Chroma). See 6.3. |
| **Metadata filtering** | Restricting a similarity search to results matching structured attributes, such as a tenant ID or access level, applied alongside the vector search itself rather than as a separate pass over the results. Qdrant builds its design around this, filtering on "any JSON payload" with a "rich set of conditions" combined with should, must, and must_not clauses. Often the deciding factor in whether a vector database is usable in a multi-tenant or access-controlled deployment. See 6.3. |
| **Hybrid search** | Running a dense vector search and a sparse, keyword-based search over the same query in parallel, then combining the two ranked result lists with a fusion algorithm. Catches both a semantic paraphrase and an exact term a purely dense or purely keyword search would miss on its own. See 6.3. |
| **Reciprocal rank fusion (RRF)** | A fusion algorithm for hybrid search that scores each document by summing 1 divided by (a constant plus its rank) across every ranked list it appears in, which "penalizes the documents that are ranked lower in the list." Does not require the underlying search methods' raw scores to be on comparable scales. Weaviate's default fusion method since v1.24 is a variant, relativeScoreFusion, that also preserves score differences. See 6.3. |
| **Ingestion (document elements)** | The stage that turns a raw file, a PDF, a scanned image, an HTML page, into structured content a chunker can work with: "extraction of structured content from raw, unstructured documents," including OCR for pages with no text layer and pulling tables out as tables rather than scrambled text. Output is broken into document elements using "deep understanding of document formats," not blind character counting. Content lost here, a flattened table, a skipped page, is unrecoverable downstream. See 6.4. |
| **Chunking strategies** | The several distinct techniques for splitting a document into embeddable units, each trading predictability, cost, and context differently: recursive character splitting (a fixed separator list, fast and predictable), semantic chunking (boundaries where embedding similarity between sentences drops), parent-document or small-to-big retrieval (small chunks indexed, larger parent context returned), and structure-aware chunking (never splitting a table row, code block, or list item). See 6.4. |
| **Cross-encoder** | A reranking model that scores a query and a single candidate document jointly, passing both through the same network together to output "a single score between 0 and 1 indicating how relevant the document is." Far more accurate than comparing two independently-encoded embeddings, and far too slow to run against more than a short shortlist, which is why it reranks rather than retrieves. See 6.4. |
| **Maximal Marginal Relevance (MMR)** | A selection method (Carbonell and Goldstein, 1998) that scores each retrieval candidate against both the query and the results already chosen, favoring "high marginal relevance" so a shortlist covers more of the answer space instead of returning near-duplicate results that all say the same thing. See 6.4. |
| **Grounding (citations)** | Tying each claim a model generates back to a specific source location, a character range in plain text or a page range in a PDF, instead of trusting the model's word for it. A citation feature that parses this at the API level is "significantly more likely to cite the most relevant quotes from documents than purely prompt-based approaches." See 6.4. |
| **HyDE (Hypothetical Document Embeddings)** | A query-rewriting technique where an instruction-following language model first "generate[s] a hypothetical document" that captures what a good answer would look like, and a contrastive encoder embeds that document instead of the original query. The encoder's "dense bottleneck" filters out any hallucinated details while grounding the search to real corpus content. Useful for short, vague, or jargon-light queries that embed poorly against detailed source text. See 6.5. |
| **GraphRAG** | A retrieval pattern that builds a second, structural index alongside a vector database: an LLM extracts entities and relationships into a knowledge graph, which is hierarchically clustered into communities with generated summaries. Global search reasons over community summaries for holistic questions about a whole corpus; local search fans out from a specific entity to its neighbors. Answers questions no single chunk documents on its own. See 6.5. |
| **Query decomposition** | Splitting a complex, multi-hop query into separate sub-questions before retrieval, retrieving for each sub-question independently, then reranking the merged candidate pool. Addresses questions that depend on connecting two or more separate facts, which a single retrieval pass over one blended query vector tends to answer only partially. See 6.5. |
| **Agentic RAG (ReAct / Self-RAG)** | Patterns that wrap the retrieve-rerank-generate cycle in a loop that can repeat rather than run once. ReAct interleaves reasoning and retrieval turn by turn, generating "verbal reasoning traces and text actions in an interleaved manner." Self-RAG trains a model to emit "reflection tokens" that decide when to retrieve "on-demand" and critique whether retrieved evidence actually supports a draft answer. See 6.5. |
| **Knowledge graph (property graph vs. RDF)** | "An organized representation of real-world entities and their relationships," with relationships "stored directly in the database rather than re-generating them using joins in queries" the way a relational database does. A labeled property graph attaches properties directly to nodes and edges and is queried with Cypher; an RDF triple store decomposes every fact into an atomic subject-predicate-object triple and is queried with SPARQL. See 6.6. |
| **Entity resolution (entity linking)** | The step that maps every mention of one real-world entity, however differently named across documents, to a single graph node: "we ideally want a single real-world entity to be represented with a single node." Moves from named-entity recognition (spotting mentions) to named-entity linking (mapping each mention to a shared target identifier). Skipping it fragments one entity into several disconnected nodes. See 6.6. |
| **Knowledge graph embeddings** | "Vector representations of entities and relationships in a knowledge graph, used to predict missing links." A different task from text embeddings (Ch. 6.2): a knowledge graph embedding represents an entity's position within the graph's own relationship structure, and its output is a prediction, not a retrieval, that needs verification before being treated as fact. See 6.6. |
| **Text2Cypher** | Using an LLM to generate a Cypher query directly from a natural-language question and the graph's schema, letting an agent "ground its insights in actual domain knowledge" rather than reading a pre-written summary. Depends on the model having "a clear understanding of the database schema," since a schema that is too large or unfamiliar can produce a query that fails or silently omits part of what it should match. See 6.6. |
| **Prompt caching** | Reusing an exact-match prefix of a prompt, up to a cache breakpoint, instead of reprocessing it. "Cache hits require 100% identical prompt segments...up to and including the block marked with cache control." A single changed character before the breakpoint is a full miss; a hit costs roughly a tenth of the base input price. See 6.7. |
| **Semantic caching** | Caching LLM responses by embedding similarity rather than exact match: a system that "employs embedding algorithms to convert queries into embeddings and uses a vector store for similarity search," returning a cached response for a query that merely resembles a past one. Achieves a much higher hit rate than exact-match caching, at the cost of a false hit when two differently-meant queries score above the similarity threshold. See 6.7. |
| **Tool-call caching** | Caching an agent's tool-call results, a problem about protecting systems and correctness more than saving tokens. "Idempotent tool calls are necessary but not sufficient" for safe caching, since "if the underlying data changes, your cached answer becomes a lie" regardless of how safely repeatable the call itself is. See 6.7. |
| **Precision@k / Recall@k** | Retrieval metrics scored against a known-relevant document set. Precision@k asks what fraction of the top-k retrieved documents were relevant; Recall@k asks what fraction of all relevant documents made it into the top k. Neither is sensitive to ranking order within the top k, which is what Mean Reciprocal Rank and NDCG add. See 6.8. |
| **Mean Reciprocal Rank (MRR)** | A ranking-aware retrieval metric: "the multiplicative inverse of the rank of the first correct answer: 1 for first place, 1/2 for second place, 1/3 for third place and so on," averaged across a set of queries. Rewards a retriever for placing the first relevant result early, independent of Precision@k or Recall@k. See 6.8. |
| **NDCG (Normalized Discounted Cumulative Gain)** | A ranking-aware retrieval metric comparing a ranked list's Discounted Cumulative Gain against the Ideal DCG, "the maximum achievable DCG with the same set of relevance scores but in the perfect ranking order." Scores the whole ranked list, not just the first relevant hit, rewarding relevant results that appear earlier. See 6.8. |
| **Faithfulness (Ragas)** | A Ragas metric measuring "how factually consistent a response is with the retrieved context," computed as the number of a response's claims supported by the retrieved context divided by its total number of claims. A response can score perfectly faithful and still be wrong if the retrieved context itself was incomplete or irrelevant, which is why Faithfulness is paired with retrieval-side metrics like Context Recall. See 6.8. |
| **Ingestion pipeline vs. query pipeline** | Two separate systems inside a RAG architecture, run on two separate clocks. The ingestion pipeline runs on a schedule, where "source documents are parsed, chunked, embedded, and stored in a vector or hybrid index"; the query pipeline runs per request, where "the system runs semantic and keyword search to surface the most relevant chunks from the index." A defect introduced during ingestion typically surfaces later as a query-time symptom rather than an ingestion-time error. See 6.9. |
| **GenAI observability** | A continuous production layer distinct from periodic evaluation: "conventional monitoring entails tracking predetermined metrics to assess system health and performance, while GenAI observability offers insights into the inputs and outputs of a workflow, along with every intervening step." Tracks retrieval signals like chunk attribution and chunk utilization, generation signals like context adherence, and system signals like latency, catching drift between scheduled evaluation runs. See 6.9. |
| **Context drift** | A risk invisible to standard RAG evaluation metrics: "a system with advanced context drift can maintain high faithfulness scores while producing answers that are organizationally wrong." Occurs in three layers: schema drift, where underlying data structure changes without a reindex; semantic drift, where a term's organizational meaning shifts while the indexed word stays the same; and staleness drift, where source documents move on while the index keeps serving an old version. See 6.9. |
| **Open Knowledge Format (OKF)** | Google Cloud's open specification for exporting internal knowledge as a directory of markdown files with YAML frontmatter, one file per concept, so that "OKF is not tied to any specific cloud, database, model provider, or agent framework." Gives every source system a common, minimal export shape instead of requiring a custom connector per source-consumer pair. See 6.10. |
| **OKF concept file / type field** | The unit of an OKF bundle: one markdown file representing one concept (a table, a metric, a playbook, an API), whose file path is its identity. `type` is the only field OKF actually requires; the rest of a concept's reserved frontmatter (title, description, resource, tags, timestamp) is optional structure on top of it. See 6.10. |
| **OKF bundle** | A directory of OKF concept files. Concepts reference each other with ordinary markdown links, turning a flat directory into a graph richer than the file system's own parent/child structure, though far less expressive than the property graphs or RDF triples covered in Chapter 6.6. A bundle can feed a Chapter 6.9 ingestion pipeline, or an agent can read one file directly for a narrow, well-scoped lookup. See 6.10. |
| **Form, not facts (fine-tuning)** | The thesis that fine-tuning reliably teaches a model style, format, and narrow behaviors, but not new facts, since "next token prediction loss on a tiny text...cannot change the internals of the neural networks knowledge base." A knowledge gap calls for RAG (Phase 6); a behavior gap is fine-tuning's actual target. See 7.1. |
| **Knowledge gap vs. behavior gap** | The diagnostic question this curriculum recommends asking before choosing among prompting, RAG, or fine-tuning: is the model missing a fact (a knowledge gap, solved by RAG) or failing to consistently perform a task it already knows (a behavior gap, solved by prompting first, then fine-tuning only if a real gap persists). See 7.1. |
| **Vendor-assisted fine-tuning vs. self-hosted PEFT** | Two paths to a fine-tuned model that diverged in 2026: a closed-model vendor's assisted-fine-tuning or custom-models program, a relationship rather than an on-demand API call, versus self-hosted parameter-efficient fine-tuning on an open-weight model, which stays fully self-serve regardless of any single vendor's access policy. See 7.1. |
| **LoRA (Low-Rank Adaptation)** | A parameter-efficient fine-tuning technique that freezes a model's pretrained weights and trains a small pair of low-rank matrices injected into each layer instead. Hu et al.: "LoRA can reduce the number of trainable parameters by 10,000 times and the GPU memory requirement by 3 times" versus full fine-tuning, while performing on-par or better and adding no extra inference latency once merged. See 7.2. |
| **QLoRA** | An extension of LoRA that fine-tunes through a 4-bit quantized (NormalFloat, NF4) copy of the frozen base model while still training full-precision LoRA adapters on top of it. Dettmers et al.: "reduces memory usage enough to finetune a 65B parameter model on a single 48GB GPU while preserving full 16-bit finetuning task performance." See 7.2. |
| **Intruder dimensions** | New, high-ranking singular vectors that appear in a weight matrix's singular value decomposition after LoRA fine-tuning but not after full fine-tuning, evidence that the two methods learn structurally different solutions even when they reach similar benchmark scores. Shown by causal intervention to cause localized forgetting where they appear. See 7.2. |
| **RLHF (Reinforcement Learning from Human Feedback)** | A two-stage alignment recipe following instruction tuning: train a reward model on human rankings of candidate outputs, then optimize the policy model against that reward model with reinforcement learning, typically PPO. Ouyang et al.: this is what took InstructGPT's 1.3B-parameter model past the 175B-parameter, unaligned GPT-3 in human evaluations. See 7.3. |
| **RLAIF (Reinforcement Learning from AI Feedback)** | RLHF's identical reward-model-plus-reinforcement-learning structure with an AI model supplying the preference comparisons instead of human reviewers. Lee et al.: "RLAIF can achieve performance on-par with using human feedback," and can even outperform a supervised fine-tuned baseline using an AI labeler the same size as, or the same checkpoint as, the policy itself. See 7.3. |
| **DPO (Direct Preference Optimization)** | An alignment method that removes RLHF's separate reward model and reinforcement-learning loop entirely, applying a single classification loss directly to chosen-versus-rejected preference pairs. Rafailov et al.: the language model being trained is "secretly a reward model" already, "allowing us to solve the standard RLHF problem with only a simple classification loss." See 7.3. |
| **DAPT / TAPT (domain-adaptive / task-adaptive pretraining)** | A second phase of self-supervised pretraining, no labels required, on unlabeled text from a target domain (DAPT) or from a task's own corpus (TAPT), run before task-specific fine-tuning. Gururangan et al.: "a second phase of pretraining in-domain...leads to performance gains," and "adapting to the task's unlabeled data...improves performance even after domain-adaptive pretraining," meaning the two stack rather than substitute for each other. See 7.4. |
| **Catastrophic forgetting** | The tendency of a neural network to lose earlier learned behavior while acquiring new behavior through further training. Kirkpatrick et al.: "it has been widely thought that catastrophic forgetting is an inevitable feature of connectionist models." A 2023 study of LLMs found it worsens, not improves, with scale: "as the model scale increases, the severity of forgetting intensifies." See 7.4. |
| **Elastic Weight Consolidation (EWC)** | A mitigation for catastrophic forgetting that estimates which weights were most important to a previously learned task, then penalizes further changes to those specific weights during training on a new task. Kirkpatrick et al.: works "by selectively slowing down learning on the weights important for" earlier tasks. See 7.4. |
| **Knowledge distillation** | Training a smaller student model to reproduce a larger teacher model's behavior, typically learning from the teacher's softened output distribution rather than raw labels alone. Hinton et al. built on Caruana et al.'s demonstration that it was possible to "compress the knowledge in an ensemble into a single model which is much easier to deploy." DistilBERT applied this during pretraining itself, reporting a model built to "reduce the size of a BERT model by 40%, while retaining 97% of its language understanding capabilities and being 60% faster." See 7.5. |
| **Quantization (model compression)** | Representing a model's weights with fewer bits (e.g. 4 or 8 instead of 16 or 32) without changing its architecture or weight count, typically applied after training. GPTQ: "can quantize GPT models with 175 billion parameters in approximately four GPU hours, reducing the bitwidth down to 3 or 4 bits per weight, with negligible accuracy degradation." See 7.5. |
| **Pruning (model compression)** | Removing individual weights or structured blocks of weights from a trained model because they contribute little to its output, reducing memory and compute needed at inference. SparseGPT: "large-scale generative pretrained transformer (GPT) family models can be pruned to at least 50% sparsity in one-shot, without any retraining, at minimal loss of accuracy." See 7.5. |
| **MMLU (general-capability benchmark)** | A broad multiple-choice benchmark used to check whether a fine-tune regressed capabilities outside its own training task, distinct from a task-specific held-out eval. Hendrycks et al.: MMLU "covers 57 tasks including elementary mathematics, US history, computer science, law, and more," and performing well requires "extensive world knowledge and problem solving ability" across unrelated subjects. See 7.6. |
| **LLM-as-judge** | Using a strong LLM to score or compare another model's open-ended outputs instead of, or alongside, human evaluators. Zheng et al.: "Strong LLM judges like GPT-4 can match both controlled and crowdsourced human preferences well, achieving over 80% agreement," the same level of agreement between two humans, though the same study documents position, verbosity, and self-enhancement biases the judge is subject to. See 7.6. |
| **Benchmark contamination** | When a benchmark's own text has leaked into a model's training data, so a high score reflects memorization rather than genuine capability, invalidating the score until ruled out. A contamination study found "ChatGPT and GPT-4 demonstrated an exact match rate of 52% and 57%, respectively, in guessing the missing options" on MMLU, a rate consistent with leakage rather than reasoning over an unfamiliar question. See 7.6. |
| **Multi-adapter serving (S-LoRA style)** | Serving many fine-tuned LoRA adapters from one shared base-model deployment instead of merging each adapter into its own full copy of the base model. S-LoRA: "Unified Paging uses a unified memory pool to manage dynamic adapter weights with different ranks and KV cache tensors with varying sequence lengths," and "can improve the throughput by up to 4 times and increase the number of served adapters by several orders of magnitude." See 7.7. |
| **Training/serving skew** | When the code preparing a model's input diverges between training and production, so a model that scored well offline performs worse live for reasons that have nothing to do with the model's weights, such as a drifted prompt template or a tokenizer version mismatch. Zinkevich's guidance: "re-use code between your training pipeline and your serving pipeline whenever possible." See 7.7. |
| **Shadow deployment and canary release** | Two stages for exposing a new model to real traffic with escalating risk. A shadow deployment sends it the same production traffic without ever showing a user its output; Fowler: a team can "send the same production traffic to gather data on how the shadow model performs before promoting it." Canary release follows, exposing "a small subset of users" first: "a technique to reduce the risk of introducing a new software version in production by slowly rolling out the change" before a full rollout, with rollback, if needed, "simply to reroute users back to the old version until you have fixed the problem." See 7.7. |
| **PEAS (Performance measure, Environment, Actuators, Sensors)** | A four-part specification for describing any agent's task environment: what it is measured against, what world it acts in, what it can change, and what it can perceive. Notice it says nothing about how the agent decides, which is why the same specification applies unchanged whether the decide step is hand-coded or an LLM. See 8.1. |
| **Rational agent (Russell and Norvig)** | An agent that, at every step, selects the action expected to do best against its performance measure. Russell and Norvig: "an ideal rational agent should do whatever action is expected to maximize its performance measure, on the basis of the evidence provided by the percept sequence and whatever built-in knowledge the agent has." Rationality is relative to a chosen performance measure and a percept sequence, not a guarantee of a correct outcome. See 8.1. |
| **Weak notion of agency (Wooldridge and Jennings)** | A hardware or software system defined by four properties: autonomy, social ability, reactivity, and pro-activeness. Wooldridge and Jennings: "pro-activeness: agents do not simply act in response to their environment, they are able to exhibit goal-directed behaviour by taking the initiative." Predates LLM-based multi-agent systems by decades; deep treatment of coordinating LLM agents under this same lens is in Phase 11. See 8.1. |
| **Short-term vs. long-term memory (agent memory)** | The two-level way to think about what an LLM agent remembers: short-term memory is whatever currently fits in the context window, fast to use because reasoning can read it directly, but bounded in size and gone once the window clears or the session ends; long-term memory is external storage, unlimited in practical size and durable across sessions, but reachable only through a deliberate retrieval step that brings it back into the context window before reasoning can use it. See 8.2 and 8.5. |
| **Long-term memory architectures (MemGPT, Generative Agents)** | Two example designs for giving an LLM agent memory that outlives its context window. Packer et al.'s MemGPT pages information between the context window and a larger external store, "drawing inspiration from hierarchical memory systems in traditional operating systems." Park et al.'s Generative Agents instead keeps "a comprehensive record of the agent's experience" that gets retrieved and "recursively synthesized into higher- and higher-level reflections that guide behavior." Named here as examples of the same underlying idea; compared in depth in 8.5. See 8.2. |
| **Virtual context management (MemGPT)** | MemGPT's core mechanism: treating an LLM's context window like an operating system treats RAM, paging data between an editable in-prompt working context and two external stores, recall storage (a message database) and archival storage (arbitrary-length text), moved by function calls the model itself issues rather than by a fixed background process. Eviction from the context window itself is a separate, judgment-free capacity trigger (the 'flush token count'). See 8.4 (the underlying function-calling mechanism) and 8.5. |
| **Retrieval score (recency + importance + relevance)** | Generative Agents' formula for deciding what to pull back into context: three normalized signals, an exponential-decay recency score, a model-rated 1-10 importance score, and an embedding-similarity relevance score, combined as a weighted sum. No signal wins by default; a recent but unimportant memory can outscore an old but highly relevant one depending on the weights chosen. See 8.5. |
| **Reflection (Generative Agents)** | A periodic synthesis step triggered when accumulated importance scores cross a threshold (150 in the original implementation), prompting the model over its 100 most recent memories to generate a small number of higher-level insights, which are themselves stored as new, retrievable memories. Distills many specific episodic memories into fewer general ones rather than summarizing on a fixed schedule. See 8.5. |
| **Working, episodic, semantic, and procedural memory (CoALA taxonomy)** | A four-part memory taxonomy, borrowed by Cognitive Architectures for Language Agents (Sumers et al., 2023) from the older Soar cognitive architecture. Working memory is the context window itself; semantic memory holds durable facts about the world (what a RAG vector store typically contains); episodic memory holds specific past events at specific times (what a memory stream typically contains); procedural memory is the rules that determine behavior, closest to an LLM agent's weights, system prompt, and code. See 8.5. |
| **Context engineering (vs. prompt engineering)** | Prompt engineering is writing and organizing an LLM's instructions for optimal outcomes; context engineering is the broader discipline of curating and maintaining the optimal set of tokens present during inference, everything that lands in the context window, not only the prompt itself. Treats context as a finite resource with diminishing marginal returns rather than something to maximize. See 8.6. |
| **Context rot** | The empirical finding that a model's ability to accurately recall information from its context degrades as the number of tokens in that context grows, shown by needle-in-a-haystack benchmarks even when the added tokens are inert filler unrelated to the target fact. Attributed to self-attention's n-squared pairwise token relationships, an 'attention budget' every added token competes for. See 8.6. |
| **Compaction (context management)** | Summarizing a conversation nearing its context window limit and reinitiating a new, smaller context window from that summary, rather than letting history grow without bound. Trades verbatim detail for headroom; risk compounds across repeated passes, since a second compaction summarizes what a first pass already compressed rather than the original turns. See 8.6. |
| **Structured note-taking (agentic memory)** | An agent regularly writing notes to persistent storage outside its context window, pulled back in only when later needed. Distinct from compaction because a note was never part of what a compaction pass compresses, so it survives repeated compaction cycles intact rather than depending on a summarization step judging it worth keeping each time. See 8.6. |
| **Sub-agent architecture (context isolation)** | Delegating a focused task to a specialized sub-agent with its own clean context window, rather than having one agent accumulate an entire project's history. Only a summary of the sub-agent's result crosses back to the main agent, keeping the main agent's own context spent on coordination rather than on every sub-task's intermediate steps. See 8.6. |
| **Toolformer** | Schick et al.'s approach to training "a model to decide which APIs to call, when to call them, what arguments to pass, and how to best incorporate the results," so that language models "can teach themselves to use external tools via simple APIs and achieve the best of both worlds...". An early demonstration that tool use can be learned rather than only hand-engineered. See 8.2 and 8.4. |
| **Plan-and-Solve prompting** | A prompting method (Wang et al., 2023) that "consists of two components: first, devising a plan to divide the entire task into smaller subtasks, and then carrying out the subtasks according to the plan." Unlike an agent loop, the plan is generated once, upfront, with no built-in mechanism for revising it once a subtask's actual result is known. See 8.3 and 8.7. |
| **Reflexion (verbal reinforcement learning)** | A framework (Shinn et al., 2023) for improving an LLM agent across multiple attempts at a task without updating any weights. Three components, an Actor that "generates text and actions," an Evaluator that "scores the outputs produced by" the Actor, and a Self-Reflection model that "generates verbal reinforcement cues," let the agent "verbally reflect on task feedback signals" and carry that reflection into its next attempt. Distinct from ReAct: Reflexion revises strategy between whole attempts, not between steps within one attempt. See 8.3 and 8.7. |
| **Plan-and-execute (agent architecture)** | An agent architecture (LangChain) built from two distinct components: a planner that "prompts an LLM to generate a multi-step plan to complete a large task," and executor(s) that "accept the user query and a step in the plan and invoke 1 or more tools to complete that task." After each step executes, "the agent is called again with a re-planning prompt," deciding whether to finish or revise the remaining plan. Combines an upfront deliberative plan with reactive, per-step re-planning, unlike either Plan-and-Solve (no revision) or ReAct (no upfront plan). See 8.7. |
| **Graph of Thoughts (GoT)** | A reasoning framework (Besta et al., 2023) that models an LLM's intermediate thoughts as vertices in an arbitrary graph rather than a tree, with edges as dependencies between them. Because a graph vertex can have more than one incoming edge, GoT supports operations a tree cannot: "combining arbitrary LLM thoughts into synergistic outcomes," "distilling the essence of whole networks of thoughts," and "enhancing thoughts using feedback loops." Reported "increasing the quality of sorting by 62% over ToT, while simultaneously reducing costs by >31%." See 5.2 and 8.7. |
