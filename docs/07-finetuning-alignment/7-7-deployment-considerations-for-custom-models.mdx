## TL;DR

A fine-tuned model that has passed Chapter 7.6's evaluation gate still is not ready for every user at
once. Two decisions shape how safely it gets there. The first is how it gets served: merging a LoRA
adapter into the base model gives one tenant maximum throughput with no added latency, but that stops
scaling once there is more than one fine-tune to serve. S-LoRA's authors motivate their alternative this
way: once a team is "scaling the fine-tuning of a base model for numerous tasks, such as personalized
assistants, which could involve thousands or millions of users, the associated training and serving costs
can become substantial." Part of that cost is architectural: "directly merging the models requires
maintaining many copies of the full language model." Their alternative keeps adapters unmerged and pools
them behind one base deployment, reporting it "can improve the throughput by up to 4 times and increase
the number of served adapters by several orders of magnitude." The second decision is how the rollout
itself proceeds: a shadow deployment lets a team "send the same production traffic" to the new model "to
gather data on how the shadow model performs before promoting it," with zero user-facing risk, and a
canary release then exposes a small share of real users first, with a rollback plan ready that is "simply
to reroute users back to the old version until you have fixed the problem."

## High-Level Explanation

Deploying a fine-tuned model is not the same problem as deploying a fixed piece of software, because the
artifact under consideration was validated against a set of eval scores, not against the exact traffic it
is about to see. Getting a validated model safely in front of real users means making three separate
decisions well. The first is architectural: whether to merge the fine-tune's adapter weights into the base
model as a single deployable artifact, or to keep the adapter separate and serve it dynamically alongside
potentially many other adapters sharing one base model, a choice that changes both cost and operational
complexity as the number of fine-tunes grows. The second is about consistency: the exact preprocessing,
prompt template, and tokenizer that produced good eval scores during training have to be the same ones
running at serving time, or a model that looked fine in Chapter 7.6's evaluation harness can quietly
perform worse in production for reasons that have nothing to do with the fine-tune itself. The third is
about how the rollout proceeds once the first two are settled: exposing the new model to a shadow copy of
production traffic before any real user sees it, then ramping up real traffic gradually with a rollback
plan ready, rather than switching every user over at once.

## Deep-Dive Explanation

**How a fine-tuned model gets served changes the deployment math as much as how it was trained, and the
choice comes down to merging the adapter into the base model or keeping it separate and serving many
adapters dynamically.** Chapter 7.2 covered LoRA's own case for the merged path: once training finishes,
an adapter's low-rank matrices can be folded directly into the base model's weights, adding no extra
inference latency at all. That works well for a single fine-tune serving all of its own traffic. It works
less well the moment an organization has more than one fine-tune to serve. As the authors of S-LoRA
explain, once a team is "scaling the fine-tuning of a base model for numerous tasks, such as personalized
assistants, which could involve thousands or millions of users, the associated training and serving costs
can become substantial." Part of that cost is architectural: "directly merging the models requires
maintaining many copies of the full language model," one full deployment per fine-tune. S-LoRA's answer is
to keep every adapter unmerged and serve them from one shared base-model deployment instead: "Unified
Paging uses a unified memory pool to manage dynamic adapter weights with different ranks and KV cache
tensors with varying sequence lengths." To make that shared deployment fast, its serving engine batches
requests that carry entirely different adapters together, describing the approach as one where "we batch
the computation of the base model and then employ custom CUDA kernels to execute the additional xAB for
all adapters separately," relying on "custom CUDA kernels that support batching LoRA computations with
varying ranks and sequence lengths in a non-contiguous memory layout." Because no adapter's weights get
folded into a private copy of the base model, "this avoids weight duplication and enables batching of the
more costly xW operation," and the reported gain is concrete: S-LoRA "can improve the throughput by up to
4 times and increase the number of served adapters by several orders of magnitude" compared with prior
LoRA-serving approaches. The trade-off is straightforward once stated: merge when one fine-tune needs to
run at its absolute fastest for one purpose; keep adapters separate when many distinct fine-tunes need to
share infrastructure economically.

**A custom model can be correct in the eval harness and wrong in production for reasons that have nothing
to do with the model itself, if the code preparing its input diverges between training and serving.**
This is not a problem invented by fine-tuning; Zinkevich's widely used engineering guidance for production
ML puts it plainly: "the best way to make sure that you train like you serve is to save the set of
features used at serving time, and then pipe those features to a log to use them at training time," and
more directly still, to "re-use code between your training pipeline and your serving pipeline whenever
possible." For a fine-tuned language model, the same failure shows up as a prompt template that changed
between the fine-tuning script and the serving stack, a tokenizer version mismatch, or a chat-formatting
difference that silently reshapes every input the model sees, none of which would show up by re-reading
the model's weights, only by comparing what actually reaches the model at each stage. The same guidance
also has a rule for the moment right before a model ships at all: "do sanity checks right before you
export the model. Specifically, make sure that the model's performance is reasonable on held out data,"
which is precisely what Chapter 7.6's evaluation gate exists to satisfy for a fine-tuned model
specifically, not a generic reminder to be careful, but a concrete, scored check that has to pass before
deployment questions even begin.

**Passing Chapter 7.6's evaluation gate is necessary before a fine-tuned model reaches production traffic,
but it is not sufficient, because an offline eval set is never a perfect stand-in for what real traffic
actually sends the model.** The lowest-risk way to close that gap is a shadow deployment. Martin Fowler's
writing on continuous delivery for machine learning describes it directly: a team can "deploy the new
model side-by-side with the current one, as a shadow model, and send the same production traffic to
gather data on how the shadow model performs before promoting it," with no user ever seeing the shadow's
output. Once a shadow run looks healthy, canary release is the next step. Fowler's separate writing on
canary release defines it as "a technique to reduce the risk of introducing a new software version in
production by slowly rolling out the change to a small subset of users before rolling it out to the
entire infrastructure and making it available to everybody." The setup looks similar to a
BlueGreenDeployment in that "you start by deploying the new version of your software to a subset of your
infrastructure, to which no users are routed," and then, once the team is satisfied, "you can start
routing a few selected users to it." If anything looks wrong at any stage, the exit Fowler describes is
deliberately simple: "the rollback strategy is simply to reroute users back to the old version until you
have fixed the problem," which only works quickly if the previous version is still deployed and warm, not
archived somewhere that takes an hour to restore. Keeping track of which version is currently live and
which one rollback would revert to is itself a discipline worth naming: Fowler's continuous-delivery
writing frames each fine-tuned model "as an artifact that needs to be versioned and deployed to
production," which turns "what do we roll back to" from a question someone has to remember the answer to
into a fact a model registry can just answer.

## Hands-On: Build a Canary Rollout Simulator with an Automatic Rollback Gate

Chapter 7.6 built a harness that scores a model's accuracy on a small multiple-choice eval set, before and
after a fine-tune. This reuses that same scoring method, but runs it at each stage of a simulated canary
ramp and adds the one piece Chapter 7.6 did not need: an automatic decision about whether to keep ramping
traffic toward the new model or roll it back to the champion.

**Step 1: Load a champion model and define a small sample standing in for production requests.** The
champion is the model currently serving all traffic; nothing about it changes during this exercise.

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "distilgpt2"
tokenizer = AutoTokenizer.from_pretrained(model_name)
champion_model = AutoModelForCausalLM.from_pretrained(model_name)
champion_model.eval()

eval_sample = [
    {"question": "The chemical symbol for water is", "choices": {"A": "H2O", "B": "CO2", "C": "NaCl", "D": "O2"}, "answer": "A"},
    {"question": "The largest planet in the solar system is", "choices": {"A": "Earth", "B": "Jupiter", "C": "Mars", "D": "Venus"}, "answer": "B"},
    {"question": "The author of Romeo and Juliet is", "choices": {"A": "Dickens", "B": "Shakespeare", "C": "Austen", "D": "Twain"}, "answer": "B"},
    {"question": "The capital of Japan is", "choices": {"A": "Seoul", "B": "Beijing", "C": "Tokyo", "D": "Bangkok"}, "answer": "C"},
    {"question": "The freezing point of water in Celsius is", "choices": {"A": "0", "B": "32", "C": "100", "D": "-10"}, "answer": "A"},
    {"question": "The gas plants absorb for photosynthesis is", "choices": {"A": "Oxygen", "B": "Nitrogen", "C": "Carbon dioxide", "D": "Hydrogen"}, "answer": "C"},
]
```

**Step 2: Score each candidate model the same way Chapter 7.6 did, by the log-probability of its answer
letter.** This is the "quality signal" that a real rollout would collect from shadow and canary traffic;
here it runs against the same fixed sample at every stage.

```python
def score_choices(model, tokenizer, item):
    prompt = item["question"] + "\n"
    for letter, text in item["choices"].items():
        prompt += f"{letter}. {text}\n"
    prompt += "Answer:"
    input_ids = tokenizer(prompt, return_tensors="pt").input_ids
    with torch.no_grad():
        logits = model(input_ids).logits
    next_token_logits = logits[0, -1, :]
    scores = {}
    for letter in item["choices"]:
        token_id = tokenizer.encode(" " + letter, add_special_tokens=False)[0]
        scores[letter] = next_token_logits[token_id].item()
    return max(scores, key=scores.get)

def accuracy(model, tokenizer, eval_set):
    correct = sum(score_choices(model, tokenizer, item) == item["answer"] for item in eval_set)
    return correct / len(eval_set)

champion_accuracy = accuracy(champion_model, tokenizer, eval_sample)
print(f"champion accuracy: {champion_accuracy:.2%}")
```

**Step 3: Build a challenger by fine-tuning a copy of the champion on narrow domain text, the same
no-replay setup Chapter 7.4 used to demonstrate forgetting.** This challenger is deliberately built to
have regressed on the general sample, so the rollback gate below has something real to catch.

```python
import copy

domain_texts = [
    "The claimant's policy excludes coverage for pre-existing conditions disclosed at binding.",
    "Under the indemnity clause, the insurer's liability is capped at the sum insured on the schedule.",
    "Subrogation rights transfer to the insurer upon settlement of the claim in full.",
]

def fine_tune(model, tokenizer, texts, steps=30, lr=5e-5):
    model.train()
    optimizer = torch.optim.AdamW(model.parameters(), lr=lr)
    for step in range(steps):
        text = texts[step % len(texts)]
        input_ids = tokenizer(text, return_tensors="pt").input_ids
        loss = model(input_ids, labels=input_ids).loss
        loss.backward()
        optimizer.step()
        optimizer.zero_grad()
    model.eval()
    return model

challenger_model = copy.deepcopy(champion_model)
challenger_model = fine_tune(challenger_model, tokenizer, domain_texts, steps=30)

challenger_accuracy = accuracy(challenger_model, tokenizer, eval_sample)
print(f"challenger accuracy: {challenger_accuracy:.2%}")
```

**Step 4: Ramp the challenger through canary stages, re-checking for regression against the champion at
each one, and roll back automatically the moment the drop crosses a threshold.** A real rollout would
score fresh live traffic sampled at each stage, so an early stage could pass while a later one, seeing a
different slice of traffic, fails. This simulation re-checks the same fixed sample at every stage instead,
to keep the comparison exact and the mechanism visible; one consequence of that simplification is that
with a fixed challenger, the check can only ever fire at the first stage it reaches or never fire at all,
not partway through a ramp.

```python
canary_stages = [0.05, 0.25, 1.00]
rollback_threshold_pp = 15.0  # max allowed drop, in percentage points, before rolling back

def run_canary_rollout(champion_acc, challenger_acc, stages, threshold_pp):
    for stage_pct in stages:
        drop_pp = (champion_acc - challenger_acc) * 100
        print(f"canary stage {stage_pct:.0%}: challenger accuracy {challenger_acc:.2%} "
              f"({drop_pp:+.1f} pp vs. champion)")
        if drop_pp > threshold_pp:
            print(f"rollback triggered at {stage_pct:.0%}: rerouting all traffic back to the champion")
            return "rolled_back", stage_pct
    print("canary ramp completed: full traffic now on the challenger; it becomes the new champion")
    return "shipped", 1.00

outcome, stage_reached = run_canary_rollout(
    champion_accuracy, challenger_accuracy, canary_stages, rollback_threshold_pp
)
print(f"outcome: {outcome} at stage {stage_reached:.0%}")
```

With a large enough drop from the narrow, no-replay fine-tune, the rollback triggers at the very first
canary stage this simplified check runs, before the challenger ever reaches more than a sliver of traffic.
A production system scoring fresh traffic at each stage could instead let that same regression through an
early stage and only catch it once the canary reaches a slice of traffic that exposes it. Either way, the
mechanism is the point: the same regression Chapter 7.4 discussed as catastrophic forgetting and Chapter
7.6 measured with a before-and-after eval score becomes, here, a live rollout decision made automatically,
not a number someone has to remember to check by hand.
