## TL;DR

Chapter 7.1 established when to fine-tune. This chapter covers how, and specifically why almost nobody
in 2026 fine-tunes a model the way the term originally meant: updating every one of its weights. The
paper that changed that, Hu et al.'s "LoRA: Low-Rank Adaptation of Large Language Models," is direct
about the problem it set out to solve: "as we pre-train larger models, full fine-tuning, which retrains
all model parameters, becomes less feasible." Their fix freezes the pretrained weights entirely and
trains a small pair of low-rank matrices injected into each layer instead, and the reduction is not
incremental: "compared to GPT-3 175B fine-tuned with Adam, LoRA can reduce the number of trainable
parameters by 10,000 times and the GPU memory requirement by 3 times," while performing "on-par or
better than fine-tuning in model quality." QLoRA pushed the same idea further by fine-tuning through a
quantized copy of the base model, reporting that it "reduces memory usage enough to finetune a 65B
parameter model on a single 48GB GPU while preserving full 16-bit finetuning task performance." These
are not the only parameter-efficient technique, adapter modules predate LoRA and add "within 0.4% of the
performance of full fine-tuning, adding only 3.6% parameters per task," where "fine-tuning trains 100%
of the parameters per task" by contrast. But parameter-efficient fine-tuning (PEFT) is not simply a
cheaper way to reach the same destination: recent research analyzing the actual weight matrices LoRA and
full fine-tuning produce found "LoRA and full fine-tuning yield weight matrices whose singular value
decompositions exhibit very different structure," meaning the two methods learn genuinely different
solutions even when their benchmark scores match. This chapter covers the mechanics of low-rank
adaptation, why quantization stacks on top of it without destroying it, where adapters and prefix-tuning
fit alongside LoRA, and the real cases where full fine-tuning's higher cost still buys something PEFT
cannot.

## High-Level Explanation

Think of a pretrained model's weights as a finished, enormous reference library, correct enough to be
useful for almost anything, too large and too expensive to rewrite from scratch every time one department
needs it to talk differently. Full fine-tuning is rewriting every book in that library to reflect a new
department's needs: thorough, but the storage cost and the printing cost are the size of the whole
library, every single time, for every single department. Parameter-efficient fine-tuning is something
closer to slipping a thin insert into the spine of each relevant book, small enough to produce and store,
easily removed or swapped for a different department's insert, and yet capable of redirecting how the
book reads without a single original page being reprinted. LoRA is the most widely used version of that
insert: instead of touching the model's original weight matrices at all, it adds a small, trainable
low-rank pair of matrices alongside them, and only that small pair gets updated during training.

## Deep-Dive Explanation

**Full fine-tuning stopped scaling before parameter-efficient techniques existed to replace it.** The
LoRA paper names the exact problem: "as we pre-train larger models, full fine-tuning, which retrains all
model parameters, becomes less feasible," and it is specific about why: "using GPT-3 175B as an
example... deploying independent instances of fine-tuned models, each with 175B parameters, is
prohibitively expensive." Every downstream task fine-tuned this way needs its own full-sized copy of the
model, stored and served independently. LoRA's fix freezes the pretrained weights entirely and injects a
pair of small, trainable low-rank matrices into each layer of the transformer, so training only ever
touches that pair. The resulting numbers are not a modest improvement: "compared to GPT-3 175B fine-tuned
with Adam, LoRA can reduce the number of trainable parameters by 10,000 times and the GPU memory
requirement by 3 times." Despite training a tiny fraction of the parameters, LoRA "performs on-par or
better than fine-tuning in model quality on RoBERTa, DeBERTa, GPT-2, and GPT-3," with a further practical
advantage: unlike some earlier adapter approaches, it adds "no additional inference latency," since the
low-rank update can be merged back into the original weights before serving.

**QLoRA stacks quantization underneath LoRA without sacrificing the fine-tune's quality.** Dettmers et
al.'s QLoRA fine-tunes through a 4-bit quantized copy of the frozen base model while still training
full-precision LoRA adapters on top of it, and the memory savings compound directly with LoRA's own: it
"reduces memory usage enough to finetune a 65B parameter model on a single 48GB GPU while preserving full
16-bit finetuning task performance." Three specific techniques make that possible: "4-bit NormalFloat
(NF4), a new data type that is information theoretically optimal for normally distributed weights,"
"double quantization to reduce the average memory footprint by quantizing the quantization constants,"
and "paged optimizers to manage memory spikes" during training. The model QLoRA produced, Guanaco,
"outperforms all previous openly released models on the Vicuna benchmark, reaching 99.3% of the
performance level of ChatGPT while only requiring 24 hours of finetuning on a single GPU." QLoRA is the
reason a single consumer or workstation-class GPU can fine-tune a model that would otherwise need a
multi-GPU server just to hold in memory, let alone train.

**LoRA is the most widely adopted parameter-efficient technique, but adapters came first, and the
underlying principle is the same one Hugging Face's PEFT library states directly.** Houlsby et al.'s
2019 adapter-tuning paper predates LoRA and inserts small trainable modules between existing transformer
layers rather than alongside the weight matrices themselves; on the GLUE benchmark, adapters "attain
within 0.4% of the performance of full fine-tuning, adding only 3.6% parameters per task," where "by
contrast, fine-tuning trains 100% of the parameters per task." Hugging Face's own framing of why this
matters generalizes past any one technique: "PEFT approaches only fine-tune a small number of (extra)
model parameters while freezing most parameters of the pretrained LLMs, thereby greatly decreasing the
computational and storage costs," and "this also overcomes the issues of catastrophic forgetting, a
behaviour observed during the full finetuning of LLMs." The storage difference alone is enormous at
scale: "`bigscience/mt0-xxl` takes up 40GB of storage and full fine-tuning will lead to 40GB checkpoints
for each downstream dataset whereas using PEFT methods it would be just a few MBs," with one concrete
adapter checkpoint totaling "just 19MB."

**PEFT is not simply a cheaper way to reach the same destination as full fine-tuning; it finds a
genuinely different solution.** A 2024 analysis of the actual weight matrices each method produces put
this precisely: studying the singular value decomposition of trained weights, the authors "find that LoRA
and full fine-tuning yield weight matrices whose singular value decompositions exhibit very different
structure: weight matrices trained with LoRA have new, high-ranking singular vectors, which we call
intruder dimensions, while those trained with full fine-tuning do not." The same research found that
"LoRA forgets less than full fine-tuning" overall, a genuine PEFT advantage consistent with Hugging
Face's catastrophic-forgetting framing above, but a more specific finding complicates the "PEFT is just
cheaper full fine-tuning" mental model directly: examining the intruder dimensions LoRA introduces, the
authors found "they cause forgetting" exactly where they appear. Two methods reaching similar benchmark
scores are not proof the underlying solutions are equivalent, and for a task that needs the model's
behavior to generalize well outside the fine-tuning distribution, or a domain shift large enough that a
low-rank update genuinely cannot represent the needed change, full fine-tuning's higher cost still buys
something a rank-limited update structurally cannot.

## Hands-On: Fine-Tune a Small Model with LoRA

The fastest way to see why LoRA's parameter count is so much smaller is to print it. This walkthrough
fine-tunes a small open-weight model using Hugging Face's `peft` and `transformers` libraries, the same
libraries the self-hosted path from Chapter 7.1 depends on.

**Step 1: Install the libraries and load a small base model.**

```bash
pip install transformers peft datasets accelerate
```

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "distilgpt2"  # a small model, easy to run on a single GPU or CPU
base_model = AutoModelForCausalLM.from_pretrained(model_name)
tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token  # distilgpt2 has no pad token by default
```

**Step 2: Define a LoRA configuration and wrap the model with it.** `r` is the rank of the injected
low-rank matrices, the single most important LoRA hyperparameter; a smaller `r` means fewer trainable
parameters and a more compressed update.

```python
from peft import LoraConfig, get_peft_model, TaskType

lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=8,
    lora_alpha=16,
    lora_dropout=0.05,
    target_modules=["c_attn"],  # the attention projection layers in GPT-2-family models
)

peft_model = get_peft_model(base_model, lora_config)
```

**Step 3: Print the trainable-parameter count, the number that makes LoRA's case on its own.**

```python
peft_model.print_trainable_parameters()
# trainable params: 147,456 || all params: 82,060,032 || trainable%: 0.1797
```

Fewer than 150,000 of the model's 82 million parameters are trainable, under 0.2%, directly matching the
order of magnitude Hugging Face's own PEFT documentation reports for a similarly-configured model.

**Step 4: Fine-tune on a small labeled dataset using the standard `Trainer` API, unchanged from a full
fine-tuning run.** The only difference from a full fine-tune's training code is which model object gets
passed in; the training loop itself does not need to know it is only updating a small adapter. A handful
of example strings is enough to see the mechanics work end to end; a real fine-tune would load a curated
dataset here instead, per the sizing guidance from Chapter 7.1.

```python
from datasets import Dataset
from transformers import TrainingArguments, Trainer, DataCollatorForLanguageModeling

examples = [
    "Trade note: client requested a limit order review before market close.",
    "Trade note: position flagged for compliance review pending manager sign-off.",
    # ...50-100 curated examples in a real fine-tune, per Chapter 7.1's thresholds
]
raw_dataset = Dataset.from_dict({"text": examples})
train_dataset = raw_dataset.map(
    lambda batch: tokenizer(batch["text"], truncation=True, padding="max_length", max_length=32),
    batched=True,
)
data_collator = DataCollatorForLanguageModeling(tokenizer=tokenizer, mlm=False)

training_args = TrainingArguments(
    output_dir="./lora-output",
    per_device_train_batch_size=4,
    num_train_epochs=3,
    learning_rate=2e-4,
    logging_steps=10,
)

trainer = Trainer(
    model=peft_model,
    args=training_args,
    train_dataset=train_dataset,
    data_collator=data_collator,
)
trainer.train()
```

**Step 5: Save only the adapter, not the whole model.** This is the checkpoint-size difference from the
Deep-Dive section made concrete: saving a LoRA adapter produces a few megabytes, not a full multi-gigabyte
model checkpoint.

```python
peft_model.save_pretrained("./lora-adapter")
# ls -lh ./lora-adapter
# adapter_config.json   adapter_model.safetensors   (a few MB total, not a full model copy)
```

The same adapter directory can later be loaded back onto the original frozen base model with
`PeftModel.from_pretrained(base_model, "./lora-adapter")`, or merged directly into the base weights with
`peft_model.merge_and_unload()` before serving, which is exactly what removes the extra inference latency
the Deep-Dive section described.

  MERGED --> SERVE[Inference: no extra latency, Hu et al.]

The same diagram explains why QLoRA does not sacrifice fine-tune quality for memory savings: quantization
only ever touches the frozen path, never the trainable low-rank pair, so the update itself is still
learned and applied at full precision regardless of what precision the frozen base is stored in.
