## TL;DR

Constrained decoding guarantees schema-valid output by masking the model's own vocabulary at
every decoding step, not by asking nicely: a target JSON Schema or regular expression is compiled
into a grammar, and at each step only the tokens that keep the output on a path consistent with
that grammar are left available to sample from, everything else is excluded before sampling even
happens (Geng et al., 2023; OpenAI, 2024). Because grammars are naturally defined over characters
while models generate subword tokens, a real implementation has to solve a tokenization-boundary
problem: the same string can tokenize multiple ways, so the grammar has to be reasoned about at the
token level, not just the character level (Geng et al., 2023). Outlines (Willard and Louf, 2023)
formalizes this by compiling a schema or regex into a finite-state machine and precomputing which
tokens are valid from each state, guaranteeing structural validity without any retries. XGrammar
(Dong et al., 2024) makes this fast enough for production by precomputing which tokens can be
checked independent of context, reporting large speedups over earlier engines. None of this
touches semantic correctness: OpenAI's own documentation states plainly that a model using
Structured Outputs "may still make mistakes within the values of the JSON object," a limitation no
grammar can fix, and the first request against a new schema typically pays a real, if since-cached,
compilation cost.

## High-Level Explanation

Picture filling out a crossword instead of writing an open-ended paragraph. In a crossword, every
square already constrains what can go there: a letter that would make a word invalid, or that
doesn't fit the space, simply cannot be written down in the first place, not because someone checks
your answer afterward and rejects it, but because the grid itself makes the wrong letter physically
inadmissible at that square. Prompting a model to produce valid output and then checking it
afterward is like writing a paragraph and having an editor cross out mistakes; constrained decoding
is like the crossword grid itself, ruling out an invalid next character before it can ever be
written. The catch is that a crossword grid only enforces that the letters spell real words in the
right pattern, not that the words themselves are the right answer to the clue; a schema-valid tool
call is exactly the same, structurally guaranteed but not automatically correct.

## Deep-Dive Explanation

**The core mechanism: masking logits against a grammar.** A target JSON Schema is first compiled
into a context-free grammar describing exactly which token sequences are valid completions. OpenAI
describes this directly: "we convert the supplied JSON Schema into a context-free grammar... After
every token, our inference engine will determine which tokens are valid to be produced next based
on the previously generated tokens and the rules within the grammar." Concretely, this means
computing a mask over the model's entire vocabulary at each step, one entry per possible token,
zeroing out (or setting to negative infinity) the logits of any token that would make the output
diverge from a schema-valid completion, before the sampling step that normally follows raw logits
ever runs. Geng et al.
([*Grammar-Constrained Decoding for Structured NLP Tasks without Finetuning*](https://arxiv.org/abs/2305.13971),
2023, EMNLP) describe this as an incremental parser that, given what has been generated so far,
returns the set of next allowed tokens, pruning the probability distribution to that set before any
token is chosen.

**The tokenization-boundary problem.** Grammars are naturally defined over characters, but models
generate subword tokens produced by a tokenizer such as BPE, and the same string can be tokenized
more than one way. Geng et al. give a concrete example: the string `"[[["` might be tokenized as
three separate single-bracket tokens or as a single combined token, and a grammar that only reasons
about characters cannot directly tell which token boundaries the model's own vocabulary actually
supports. Their solution compiles an abstract, character-level grammar down to a tokenizer-specific
concrete grammar, the same relationship as compiling a high-level language down to a particular
machine's assembly. Outlines' engineering work independently describes the same issue, calling it
the prompt boundary problem, and addresses it by precomputing a mapping from each finite-state-machine
state directly to the valid next tokens and the state each leads to, so the token-level mask is
looked up rather than recomputed from characters at every step.

**Outlines: compiling a schema into a finite-state machine.** Willard and Louf
([*Efficient Guided Generation for Large Language Models*](https://arxiv.org/abs/2307.09702), 2023)
formalize constrained generation as transitions between the states of a finite-state machine built
directly from a regular expression or JSON Schema, with an index mapping each state to the subset
of the model's vocabulary that is valid from that state. Because this index is built once per
schema rather than recomputed per token from scratch, looking up the valid token set at generation
time becomes a fast hashmap lookup rather than a fresh parse, and the resulting guarantee is
structural: the output is claimed to match the target structure without needing any retries,
malformed-output handling, or post-hoc repair.

**XGrammar: making grammar-constrained decoding fast enough for production.** Dong et al.
([*XGrammar: Flexible and Efficient Structured Generation Engine for Large Language Models*](https://arxiv.org/abs/2411.15100),
2024) observe that naively walking a grammar's automaton for every token in a large vocabulary at
every decoding step is expensive at production scale. Their key optimization splits the vocabulary
into tokens whose validity can be precomputed independent of context, reportedly over 99% of
tokens in practice, versus a small remaining set of context-dependent tokens that still need a
runtime check, caching the precomputed results in what they call an adaptive token mask cache and
overlapping the remaining grammar computation with the GPU's own token-generation work rather than
blocking on it. Reported results include up to roughly a 3x speedup on JSON-schema mask computation
and over 100x on more general context-free-grammar workloads compared with earlier engines, with
larger end-to-end generation speedups compounding on top of that.

**What none of this guarantees: correct values.** A grammar or finite-state machine constrains
shape, never content. OpenAI states this directly in its own documentation: "Structured Outputs
doesn't prevent all kinds of model mistakes. For example, the model may still make mistakes within
the values of the JSON object (e.g., getting a step wrong in a mathematical equation)." A perfectly
schema-valid response can still contain a wrong number, a hallucinated identifier, or an internally
inconsistent set of fields, because nothing in the grammar has any notion of whether a value is
actually correct, only whether it is the right type in the right place. Catching this class of
error remains a job for evaluation and verification, not a job a tighter grammar can ever take over.

**The constraint is not free.** Compiling a schema into its token-level grammar representation is
itself a real computation, and OpenAI's own documentation acknowledges that the first request
against a new schema typically incurs additional latency, often under ten seconds but potentially up
to a minute for a more complex schema, before the compiled grammar is cached for reuse on subsequent
requests with the same schema. Grammar engines can also have performance-sensitive edge cases in how
a grammar is written, for instance an inefficiently expressed repetition pattern can force far more
automaton states to be tracked than a more compact equivalent expression would, an issue documented
in llama.cpp's own grammar tooling. None of this changes the guarantee constrained decoding provides,
but it means the guarantee has a cost that a system design has to account for, particularly the very
first time a new schema is used.
