## TL;DR

A single call to a model API is a prototype, not a product. Bornstein and Radovanovic's widely
cited reference architecture for LLM applications (a16z, June 2023) named the layers that
sit around that call once an app has real users: an orchestration framework to assemble prompts,
tools, and conversation history; an LLM cache to avoid paying for the same question twice; an LLM
gateway to keep the app running when a single model provider has an outage; a logging and
observability layer to trace what a multi-step request actually did; and a validation layer to
catch a bad output before it reaches a user, the guardrail discipline covered in 5.5. Two API-level
facts shape all of this: chat completion APIs are stateless per request, so the calling application,
not the API, is responsible for resending conversation history every turn, and both OpenAI and
Anthropic explicitly recommend exponential backoff for handling rate-limit errors rather than
naive immediate retries. Streaming a response token by token, over server-sent events, reduces how
long a user waits before seeing anything, at the real cost of making that partial output harder to
moderate before it reaches them. None of this is retrieval or multi-step autonomous behavior yet,
those are Phase 6 and Phase 8 territory, but a first LLM app that skips this scaffolding does not
survive contact with real traffic.

## High-Level Explanation

Picture a restaurant built around one excellent chef. The chef alone is not a restaurant: someone
has to take orders and hand them to the kitchen, the kitchen needs a way to avoid recooking a dish
that was just made for the table next door, there has to be a backup supplier if today's usual one
runs out of a key ingredient, a manager needs a log of what went out and when in case a customer
complains, and someone has to taste a dish before it leaves the kitchen rather than trusting every
plate is fine by default. None of those roles cook the food. They are what turns a talented cook
into a restaurant that can serve a dining room on a busy night without falling over. A model API is
the chef. Everything in this chapter is the rest of the restaurant.

## Deep-Dive Explanation

**The a16z reference architecture.** Bornstein and Radovanovic's *Emerging Architectures for LLM
Applications* (a16z, June 2023) is the most widely cited map of what a production LLM application
stack actually contains, drawn from what they observed across "AI startups and sophisticated tech
companies." Their diagram lays the stack out in three stages, data preprocessing and embedding,
prompt construction and retrieval, and prompt execution and inference, with named layers at each
stage: contextual data pipelines and a vector database feeding an embedding model; an orchestration
layer (their examples: LangChain, LlamaIndex) that, in their words, "abstract[s] away many of the
details of prompt chaining; interfacing with external APIs...retrieving contextual data from vector
databases; and maintaining memory across multiple LLM calls"; an LLM cache sitting in front of the
model call itself; a logging and LLMops layer that can "log, track, and evaluate LLM outputs"; a
validation layer; and, at the base, the LLM APIs themselves, split into proprietary and open-weight
rows, sitting on top of cloud infrastructure. This chapter's scope is the layers that apply before
your app has a retrieval pipeline of its own, orchestration, caching, the gateway, observability,
and validation. Data pipelines and vector databases are Phase 6's subject.

**Orchestration: what it abstracted in 2023, and where it has moved since.** In the 2023 framing
this reference architecture describes, an orchestration framework's job was composing a sequence of
model calls, tools, and retrieved context into one coherent request, and carrying conversation
memory across turns, exactly the "prompt chaining...memory across multiple LLM calls" role quoted
above. Two of the best-known frameworks illustrate the same underlying job from different starting
points: LangChain's original framing centered on chaining LLM calls together with tools and memory,
while LlamaIndex described itself as a "data framework" whose job was connecting an LLM to a
developer's own data through connectors, indices, and a retrieval interface. Both projects have
since repositioned toward building autonomous agents rather than single-pass chains, a shift worth
noting here because it previews exactly where this course goes in Phase 8; the orchestration role
this chapter describes, assembling one request well, is the foundation that multi-step agentic
orchestration is built on top of, not a replacement for it.

**Chat APIs are stateless: your app owns the conversation.** Neither OpenAI's Chat Completions
pattern nor Anthropic's Messages API remembers a conversation between requests. Anthropic states
this directly: "The Messages API is stateless, which means that you always send the full
conversational history to the API. You can use this pattern to build up a conversation over time."
OpenAI's documentation describes the same default: "each text generation request is independent and
stateless," with multi-turn behavior implemented by the calling application appending prior messages
to each new request. OpenAI has since added an optional server-managed alternative, a
`previous_response_id` parameter and a Conversations API that let a caller chain responses without
resending full history, but the default, and the pattern every calling application needs to
understand first, is that history management is the app's job, not the API's.

**Streaming: faster to first token, harder to moderate.** Both major providers stream a response
incrementally over server-sent events rather than returning it all at once. OpenAI's own rationale
is direct: "Streaming responses lets you start printing or processing the beginning of the model's
output while it continues generating the full response," trading total completion time for a much
shorter wait before anything appears. The same OpenAI guidance names the cost of that choice
plainly: "streaming the model's output in a production application makes it more difficult to
moderate the content of the completions, as partial completions may be more difficult to evaluate."
A validation layer built to check one complete response, the pattern covered in 5.5, has to be
redesigned to work incrementally, or accept that it is only ever checking what has streamed so far,
if the app streams at all.

**Reliability at the single-request level: rate limits and backoff.** A 429 response means a rate
limit was hit, and both providers are explicit that the fix is not an immediate retry. OpenAI: "Note
that unsuccessful requests contribute to your per-minute limit, so continuously resending a request
won't work," recommending exponential backoff instead, waiting briefly after a failure and
increasing the delay after each subsequent one. Anthropic's guidance is the same in substance: their
official SDKs "automatically retry transient failures (such as connection errors, rate limits, and
5xx server errors) with exponential backoff...honoring the retry-after header when present." This is
a single-provider concern: it handles a request that failed against the provider you are already
using. It does not help if that provider is down entirely.

**Reliability across providers: the LLM gateway pattern.** A gateway sits in front of the model
call and solves a different problem than backoff: routing to more than one provider so an outage at
one does not take down the app. LiteLLM describes its own role as "a single, unified interface to
call 100+ LLM providers...using the OpenAI format," deployable as a library or as a standalone proxy
offering "load balancing" and provider-agnostic routing. Portkey's gateway documents the fallback
behavior explicitly: "Fallback to another provider or model on failed requests using the LLM
gateway. You can specify the errors on which to trigger the fallback," alongside its own automatic
retry logic with exponential backoff. Where per-request backoff handles a transient failure against
one provider, a gateway is what keeps an app answering when that provider is unavailable outright.

**Cutting cost with a cache that understands meaning, not just exact text.** An ordinary cache only
helps when a later request is byte-for-byte identical to an earlier one, which is rare for natural
language. GPTCache's semantic cache instead embeds each incoming query, stores it in a vector index,
and serves a cached response whenever a new query falls within a similarity threshold of one already
answered, exactly the embedding-and-similarity-search mechanism covered in Phase 3 applied to
requests instead of documents. The project's own framing states the motivation directly: as an
application's traffic grows, "the expenses related to LLM API calls can become substantial,"
alongside slower response times, and its cache exists to serve a repeated or near-duplicate question
from storage instead of paying for a fresh model call every time.

**Seeing what actually happened: observability and tracing.** A multi-step request, several tool
calls, an orchestration step, a retrieved context, can fail or drift in ways that are invisible
without a trace of what each step actually returned. This is a different concern from 5.6's
prompt-versioning tools, which compare prompt versions before deployment; observability tools trace
what already happened to live traffic. LangSmith's own description is direct: it lets a team
"instrument your LLM application, investigate traces, and monitor performance in production."
Langfuse frames its role similarly, tracking "LLM calls and other relevant logic in your app such as
retrieval, embedding, or agent actions," so a complex request's actual path can be inspected after
the fact rather than reconstructed from scattered logs. Helicone bundles the same observability role
with gateway functionality, describing itself as tracking "cost, latency, quality, and more" across
a request's full lifecycle.

**The layer this chapter is not re-explaining.** A validation or guardrail layer, checking a
response before it reaches a user and treating retrieved or tool-returned content as data rather
than instruction, was covered in full in 5.5 and is not repeated here beyond noting where it sits:
last, right before a response leaves the app, and complicated in exactly the way the streaming
section above describes when the app streams.
