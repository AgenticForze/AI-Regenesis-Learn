## TL;DR

Asking a model to "output JSON" purely through prompt wording gives no guarantee it actually will:
the result can arrive wrapped in prose, missing a field, or using the wrong type. Native tool and
function calling, introduced by OpenAI in June 2023 and by Anthropic's tool use feature, is a
distinct API primitive: the caller supplies one or more tool schemas alongside the prompt, and the
model returns a structured call to a specific tool with typed arguments, or a plain response if no
tool is needed. OpenAI's Structured Outputs mode (2024) goes a step further, using constrained
decoding to restrict token sampling at each step to only what a target JSON schema allows,
reporting 100% schema-valid outputs in its own evaluations versus under 40% for prompting alone.
None of this guarantees the values inside a schema-valid call are correct: a syntactically perfect
tool call can still name the wrong tool or hallucinate a plausible-looking argument. The ReAct
pattern (Yao et al., 2022) interleaves reasoning with tool actions and their observations across
multiple steps, the conceptual ancestor of today's agent tool-calling loops, and Gorilla (Patil et
al., 2023) showed that fine-tuning a model specifically for API-calling accuracy, together with
retrieval over the available API pool, meaningfully reduces hallucinated calls.

## High-Level Explanation

Picture three ways to get a colleague to fill out a form. The first is to describe the form in
words and ask them to write back "in the format of the form," hoping they remember every field, use
the right units, and do not add a paragraph of commentary around the edges. The second is to hand
them the actual form: a fixed set of labeled boxes, one per field, so there is a specific place for
each answer and no ambiguity about structure, though they could still write the wrong thing in a box
that expects a number. The third is to hand them the form printed on paper that physically has no
room to write outside the boxes and rejects a letter typed into a numeric field before it is even
submitted. Tool calling adds a further piece: instead of writing an answer at all, the colleague is
handed a small set of labeled buttons, each wired to a specific real action, like "look up account
balance" or "check current inventory," and pressing one hands over the exact inputs that action
needs, rather than describing in prose what should happen.

## Deep-Dive Explanation

**The naive approach: asking for JSON in the prompt, and where it breaks.** The simplest way to get
structured output is to describe the desired shape in the prompt itself, for instance "respond only
with a JSON object containing fields x and y," and hope the model complies. This works often enough
to be tempting, and fails in familiar ways: the model wraps the JSON in a sentence of commentary,
produces a subtly malformed object such as a trailing comma or an unescaped quote, fills a field with
the wrong type, or simply omits a field it was not confident about. None of these failures are rare
edge cases; they are the direct motivation OpenAI and Anthropic each cite for building native
alternatives, since a downstream system parsing this output has to defensively handle a family of
malformed responses no schema enforcement was ever applied to.

**Function and tool calling as a distinct API primitive.** OpenAI introduced function calling in
June 2023: the caller passes one or more function schemas, each with a name, a description, and a
JSON Schema of expected parameters, alongside the normal prompt. The model can then respond either
with a normal message or with a request to call a specific function with specific, typed arguments,
leaving the actual execution of that function to the calling application. Anthropic's tool use
feature follows the same shape: tools are defined with an `input_schema` written as JSON Schema, and
a model that decides to use one returns a `tool_use` content block carrying the tool's name and its
structured input, with the API response's stop reason indicating a tool call is being requested
rather than a finished answer. In both cases, the decision to call a tool and the values used to call
it come from the model, but the wiring between "get called" and "produce a real effect" belongs to
the surrounding application, not the model itself.

**Constrained decoding: a stronger guarantee than either of the above.** OpenAI's Structured Outputs
mode, released in 2024, does not merely ask the model to follow a schema, it constrains token
sampling itself: at each decoding step, the set of candidate next tokens is restricted to only those
that keep the output on a path consistent with the target JSON schema, using a context-free-grammar
style constraint over the model's vocabulary (a mechanism this chapter previews and 5.4 covers in
full depth). OpenAI reported 100% schema-valid outputs across its evaluations for its newer model in this mode,
compared with under 40% for its older gpt-4-0613 model prompted to produce the same schema without
enforcement, and about 93% for that same newer model prompted without enforcement at all,
illustrating that even a substantially improved base model still falls meaningfully short of a hard
guarantee without decoding-time constraints, and that the constraint itself, not just newer model
capability, is what closes the remaining gap.

**A schema-valid call is not the same as a correct call.** Constraining the grammar of an output
guarantees its shape, not its content. A tool call can be perfectly well-formed JSON, naming a real
tool with arguments of the right type, and still be wrong: the wrong tool for the situation, or a
plausible-looking argument value the model effectively hallucinated because nothing in the decoding
constraint checks whether that value is actually correct. This is a semantic problem, not a syntactic
one, and no amount of schema enforcement resolves it; catching it requires evaluation, in the sense
this curriculum returns to when covering evaluation and observability for LLM applications, not a
tighter grammar.

**Multi-step tool use: the ReAct pattern.** Many real tasks need more than one tool call before a
final answer is possible, for instance looking something up, then reasoning about the result, then
looking up something else. ReAct (Yao et al.,
[*ReAct: Synergizing Reasoning and Acting in Language Models*](https://arxiv.org/abs/2210.03629),
2022, ICLR 2023) formalizes this as an interleaved loop of reasoning traces, actions, and the
observations those actions return, letting the model's next reasoning step take the actual result of
a prior action into account rather than planning an entire sequence of actions blindly upfront. On
an interactive decision-making benchmark, this interleaving raised task success by 34 percentage
points over a comparable baseline, and separately reduced hallucinated, unsupported claims relative
to chain-of-thought prompting on knowledge-intensive question answering. Today's native tool-calling
APIs are the direct infrastructure for running exactly this kind of loop: call a tool, feed its
result back as an observation, let the model decide the next action, and repeat until it produces a
final answer instead of another tool call.

**Fine-tuning specifically for API-calling accuracy.** Gorilla (Patil et al.,
[*Gorilla: Large Language Model Connected with Massive APIs*](https://arxiv.org/abs/2305.15334),
2023) takes a different angle: rather than relying purely on a general-purpose model's in-context
ability to pick the right API and fill it in correctly, it fine-tunes a model specifically on
API-calling behavior, retrieving relevant API documentation at inference time to keep the model
grounded in APIs it may not have memorized precisely. This measurably reduces hallucinated API calls
compared to prompting a general-purpose model directly, and the same team's Berkeley
Function-Calling Leaderboard now evaluates function-calling accuracy across categories including
single calls, choosing among multiple candidate functions, and issuing several calls in parallel,
reflecting that "can this model call a function correctly" is now treated as a benchmarkable
capability in its own right rather than an incidental side effect of general capability.
