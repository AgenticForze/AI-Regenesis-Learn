## TL;DR

Every model in this curriculum from Phase 2 onward, from a small MLP to a full Transformer, computes
on numbers, not text. **Tokenization** is the process of breaking raw text into a sequence of
discrete units (words, sub-words, or characters), each assigned an integer ID from a fixed
vocabulary. **Embeddings** then replace each ID with a dense vector of learned numbers, so that
tokens used in similar contexts end up with similar vectors. This is the bridge between "the
customer's account was overdrawn" as a string of characters and the numeric tensor a neural network
actually consumes. The useful property that falls out of this is **vector semantics**: once words
live in a vector space, similarity, analogy, and even simple arithmetic between word meanings become
geometric operations, like measuring the angle between two arrows, rather than symbolic rules.

## High-Level Explanation

Think of a vocabulary as a phone book: every distinct token gets one fixed entry, and the tokenizer's
job is to look up which entries a piece of text touches, in order. A **tokenizer** first normalizes
text (lowercasing, in some pipelines, splitting punctuation) and then splits it into tokens according
to some segmentation rule. Each token is looked up in a vocabulary table to get an integer **token
ID**. That ID alone is not useful to a neural network, an ID of 4,521 is not "more" or "less" than
an ID of 12, the numbers are arbitrary labels. So a second table, the **embedding matrix**, maps each
token ID to a dense vector of, typically, a few hundred to a few thousand real numbers. The
embedding matrix is learned: during training, tokens that tend to appear in similar contexts are
pushed toward similar vectors, purely as a side effect of the model's training objective, with no
one hand-labeling any word's meaning.

The payoff for doing this well is that the resulting vectors are not arbitrary: words used in similar
ways cluster together in the vector space, and the relationships between clusters can themselves be
meaningful, which is what "vector semantics" refers to.

## Deep-Dive Explanation

**Why not just use the raw token ID, or a one-hot vector?** A one-hot vector (a vector of all zeros
except a single 1 at the position of that token's ID) is the most literal numeric encoding of "which
token is this," and it is a dead end for two mechanical reasons. First, its dimensionality equals
vocabulary size, commonly 30,000 to over 100,000 entries for a subword vocabulary (3.5), so it is
extremely high-dimensional and almost entirely zeros (sparse). Second, and more importantly, the
cosine similarity (see the 1.8 glossary entry) between any two distinct one-hot vectors is always
exactly 0, they are orthogonal by construction, so a one-hot encoding has no way to represent that
"dog" and "puppy" are related while "dog" and "spreadsheet" are not. Every token is equally
(un)related to every other token.

**The distributional hypothesis.** The theoretical basis for fixing this dates to linguist J.R.
Firth's 1957 observation, often paraphrased as "a word is characterized by the company it keeps."
Operationally: if two tokens tend to occur in similar surrounding contexts across a large corpus,
they probably have related meanings, even if a model is never given an explicit definition of either
word. Chapter 3.2 covers the specific training objectives (Word2Vec's skip-gram and CBOW) that turn
this hypothesis into a concrete learning algorithm; this chapter's job is the representation that
results, not yet the training procedure that produces it.

**The embedding matrix as a lookup table.** Formally, an embedding matrix is E element of R^(V x d),
where V is vocabulary size and d is the embedding dimension (a design choice, commonly 128 to 4096
depending on model scale). Token ID i maps to the vector in row i of E, written E_i. Mathematically,
this is identical to multiplying E^T by the one-hot vector for token i, E^T * onehot(i) = E_i, but no
real implementation performs that matrix multiply: since exactly one entry of the one-hot vector is
nonzero, frameworks implement embedding lookup as a direct array index into E, which is why it is
called an embedding "lookup" rather than an embedding "projection." E starts randomly initialized and
is updated by gradient descent (2.2) like any other model parameter: only the rows corresponding to
tokens that actually appeared in a training batch receive a gradient update on that step.

**Vector semantics and analogical structure.** Once training pushes similar-context tokens toward
similar vectors, a further, less obvious property tends to emerge: differences between vectors can
themselves encode a consistent relationship. The canonical illustration is
vec(king) - vec(man) + vec(woman) is approximately equal to vec(queen): the vector offset from
"man" to "king" (roughly, "add royalty") is similar to the offset from "woman" to "queen." This is
not designed into the embedding space by any explicit rule, it is an emergent consequence of training
tokens to satisfy co-occurrence statistics across a large corpus, and it holds approximately, as a
statistical tendency over many analogy pairs, not as an exact guarantee for any single example.

**Cosine similarity versus dot product, and why it matters here.** Two tokens' relatedness is
usually scored with cosine similarity, x . y / (||x|| ||y||), rather than the raw dot product x . y
(1.8). The reason is specific to embeddings: a token's vector norm ||x|| tends to correlate with how
frequently that token appeared during training, so the raw dot product conflates "these two tokens
are similar in meaning" with "these two tokens are both common." Dividing by both norms cancels
magnitude and isolates direction, which is what carries the meaning.

```python
# Illustrative: an embedding lookup is an array index, and cosine similarity
# isolates direction. No training loop here, this is only the representation.
import numpy as np

vocab = {"dog": 0, "puppy": 1, "spreadsheet": 2}
# A tiny, hand-set embedding matrix (V=3 tokens, d=4 dims) standing in for
# what training would actually learn from a real corpus.
E = np.array([
    [0.9, 0.1, 0.0, 0.2],   # dog
    [0.8, 0.2, 0.1, 0.1],   # puppy: close to "dog"
    [0.0, 0.9, 0.8, 0.9],   # spreadsheet: far from both
])

def embed(token):
    return E[vocab[token]]   # a lookup, not a matmul

def cosine_sim(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

print(cosine_sim(embed("dog"), embed("puppy")))         # high similarity
print(cosine_sim(embed("dog"), embed("spreadsheet")))    # low similarity
```

**A limitation this chapter deliberately leaves open.** The embedding matrix above assigns exactly
one vector per token, regardless of the sentence it appears in: "bank" gets the same vector in
"river bank" and "bank account." This is the defining limitation of **static embeddings**, and it is
the problem chapter 3.2 exists to solve with contextual embeddings.
