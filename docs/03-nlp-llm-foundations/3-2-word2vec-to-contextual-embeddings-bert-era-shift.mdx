## TL;DR

Chapter 3.1 introduced the embedding matrix but left open how it is actually trained, and flagged its
central limitation: one fixed vector per token regardless of context. **Word2Vec** (Mikolov et al.,
2013) answered the training question first, turning the distributional hypothesis into a concrete,
efficient prediction task, and became the default way to produce **static embeddings** for years.
The context limitation remained until representations shifted from a fixed lookup table to a
**function of the whole input sequence**: first ELMo's bidirectional LSTMs (2018), then, decisively,
BERT's bidirectional Transformer encoder (2018-2019). A **contextual embedding** is not looked up, it is
computed fresh for every occurrence of a token from its surrounding words, which is why "bank" gets
different vectors in "river bank" and "bank account" once a model actually reads the sentence around
it.

## High-Level Explanation

Word2Vec trains embeddings with a deliberately simple task: given a word in a large corpus, predict
the words that tend to appear near it (or the reverse, predict a word from its neighbors). Getting
good at this narrow prediction task forces the model to organize its embedding space so that
words with similar neighbors end up with similar vectors, exactly the distributional hypothesis
from 3.1, now turned into something a gradient descent optimizer can actually train against. No
document ever needs to be labeled by hand; the "labels" are just other words already sitting next to
each other in ordinary text.

Static embeddings from Word2Vec (or the related GloVe) were a major advance over one-hot vectors,
but they share a blind spot: once trained, a word's vector is fixed, looked up the same way every
time that word appears. **Contextual embeddings** remove that constraint by not storing a per-word
vector at all. Instead, a model reads an entire sentence and computes each token's representation
based on every other token in it. The same written word can therefore land at different points in
vector space depending on what surrounds it, which is exactly what "bank" needs.

## Deep-Dive Explanation

**Skip-gram, formally.** Word2Vec's most-cited variant, skip-gram, slides a window across a corpus
and, for each center word w_t, tries to predict each nearby context word w_(t+j) within the window.
The training objective maximizes the average log probability of the true context words appearing
near each center word, over the whole corpus:

```
maximize (1/T) * sum over t of [ sum over context positions j of log P(w_(t+j) | w_t) ]
```

where P(w_(t+j) | w_t) is itself a softmax over the entire vocabulary using the center word's current
embedding. CBOW (Continuous Bag of Words) is the mirror-image objective: average the context words'
embeddings and predict the single center word from that average. Skip-gram tends to do better on
rare words (each rare word gets its own dedicated prediction rather than being averaged into a
context), while CBOW trains faster and does slightly better on frequent words; both were introduced
in the same Mikolov et al. 2013 paper, [*Efficient Estimation of Word Representations in Vector
Space*](https://arxiv.org/abs/1301.3781).

**Negative sampling: making the softmax tractable.** A softmax over a 100,000-word vocabulary,
recomputed for every training example, is expensive. Word2Vec's practical trick, **negative
sampling**, reframes prediction as a much cheaper binary classification: for each true
(center word, context word) pair, sample a handful of random "negative" words that did not actually
appear in that context, and train the model to score the true pair higher than the sampled negatives,
rather than normalizing over the full vocabulary every step (Mikolov et al.,
[*Distributed Representations of Words and Phrases and their Compositionality*](https://arxiv.org/abs/1310.4546),
NeurIPS, 2013). This is a genuinely different mechanism from 3.1's embedding lookup: it is what makes
the lookup table's values converge to something meaningful in the first place. A separate line of
analysis (Levy and Goldberg,
[*Neural Word Embedding as Implicit Matrix Factorization*](https://proceedings.neurips.cc/paper/2014/hash/feab05aa91085b7a8012516bc3533958-Abstract.html),
NeurIPS, 2014) showed that skip-gram with negative sampling is implicitly factorizing a matrix of
pointwise mutual information (PMI) values shifted by a constant (log of the number of negative
samples), connecting Word2Vec's predictive framing back
to older, explicitly count-based methods like Latent Semantic Analysis.

**Why a fixed vector cannot represent a context-dependent meaning, mechanically.** Skip-gram and CBOW
both train exactly one row of the embedding matrix per vocabulary word; every occurrence of "bank" in
the training corpus contributes gradient updates to the same row, so the row converges to something
like a weighted average of all the contexts "bank" appeared in. There is no mechanism in this training
setup that could produce two different vectors for the same word, the architecture only has one
row to give it.

**The architectural shift: representations as a function of the sequence.** ELMo (Peters et al.,
[*Deep contextualized word representations*](https://arxiv.org/abs/1802.05365), 2018) broke this
constraint first, running a bidirectional LSTM (2.4) over the whole sentence and using its
hidden states, which depend on every word the LSTM has processed, as the token representations,
combined across the LSTM's layers with learned weights. BERT (Devlin et al.,
[*BERT: Pre-training of Deep Bidirectional Transformers for Language Understanding*](https://arxiv.org/abs/1810.04805),
2019) replaced the LSTM with a bidirectional Transformer encoder (2.5): every token attends to every
other token in the sequence in both directions simultaneously (not sequentially, as an LSTM does),
so each token's output representation is a learned function of the entire surrounding sentence in one
pass. Chapter 3.3 covers BERT's specific masked language modeling training objective in depth; this
chapter's point is architectural, a stack of self-attention layers computes a representation per
token per occurrence, rather than retrieving one from a fixed table.

**Layers specialize, empirically.** Probing studies on BERT's internal layers (Tenney, Das, and Pavlick,
[*BERT Rediscovers the Classical NLP Pipeline*](https://arxiv.org/abs/1905.05950), ACL 2019) found
that earlier Transformer layers tend to encode more syntactic information (part-of-speech, syntactic
dependencies) while later layers encode more semantic and task-specific information. This is an
empirical property of how the layers organize during training, not something explicitly designed
into the architecture, and it is why practitioners often extract representations from a specific
middle-to-late layer rather than only the final layer when using a pretrained model's contextual
embeddings for a downstream task.

```python
# Illustrative: the same tokenizer input, "bank", produces one fixed row from a
# static embedding table, versus a representation from a contextual encoder that
# depends on the full sequence. This shows the *shape* of the difference, not a
# runnable BERT forward pass (which chapter 3.4 covers architecturally in full).
static_embedding_table = {"bank": [0.12, -0.44, 0.81]}  # one row, used every time

def static_lookup(word):
    return static_embedding_table[word]  # identical for every occurrence

def contextual_lookup(sentence_tokens, target_index, encoder):
    # `encoder` is a stand-in for a bidirectional Transformer encoder (2.5):
    # it consumes the WHOLE token sequence and returns one vector per position,
    # each depending on every other token in `sentence_tokens`.
    all_vectors = encoder(sentence_tokens)
    return all_vectors[target_index]  # varies by sentence, even for the same word

print(static_lookup("bank"))  # identical for "river bank" and "bank account"
# contextual_lookup(["river", "bank"], 1, encoder) would differ from
# contextual_lookup(["bank", "account"], 0, encoder), because the surrounding
# tokens passed into `encoder` are different in each call.
```
