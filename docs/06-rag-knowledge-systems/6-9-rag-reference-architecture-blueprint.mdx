## TL;DR

Every chapter in this phase built one piece: chunking and embeddings, vector search, reranking and advanced
retrieval patterns, knowledge graphs, caching, evaluation. None of those pieces on their own is a system,
and a demo that strings them together for a single happy-path query is not the same thing as a production
architecture. This chapter is the blueprint that assembles the pieces and names the two systems most teams
conflate: an ingestion pipeline that runs on its own cadence, "source documents are parsed, chunked,
embedded, and stored in a vector or hybrid index with associated metadata," and a query pipeline that runs
per request, where "the system runs semantic and keyword search to surface the most relevant chunks from
the index." Teams that treat these as one system inherit failure modes that a demo never surfaces: "retrieval
recall tells you whether the right chunk was in the top-k results. It does not tell you whether the LLM used
it faithfully," multi-hop questions break single-shot retrieval because answering them correctly needs
several distinct documents rather than one, and a fixed evaluation set that scored well once tends to follow
one familiar pattern, where teams "build a fixed eval set, run it, get 0.82 faithfulness, ship, and never
look at it again," while cost, latency, and observability get treated as an afterthought. There is a risk evaluation metrics do not catch at all: "context drift is
invisible to standard RAG evaluation metrics. A system with advanced context drift can maintain high
faithfulness scores while producing answers that are organizationally wrong." This chapter lays out the full
blueprint: the ingestion pipeline, the query pipeline, the observability layer that watches both, and the
governance and feedback loop that keeps the whole thing from silently drifting out of correctness.

## High-Level Explanation

Think of the difference between a single finished room and a building's actual blueprint. A demo RAG system
is one finished room: someone picked a chunk size, an embedding model, and a vector store, wired them
together, and it answers a handful of test questions correctly. A blueprint is what a contractor actually
needs to build the whole building: where the plumbing runs separately from the electrical, which systems get
inspected on which schedule, what happens when a pipe bursts at 2am, and who gets called. This chapter is
that blueprint for a RAG system. It names the ingestion pipeline as its own system, built and inspected on
its own schedule, separate from the query pipeline that runs live every time a user asks a question, and it
adds the two things a single finished room never needs: an observability layer that watches both systems
continuously, and a governance and feedback loop that catches problems neither system's own metrics would
ever surface on their own.

## Deep-Dive Explanation

**The ingestion pipeline and the query pipeline are two different systems with two different failure modes,
and treating them as one system is where most production RAG architectures start to go wrong.** The
ingestion pipeline runs on its own cadence, sometimes continuously, sometimes on a schedule: "source
documents are parsed, chunked, embedded, and stored in a vector or hybrid index with associated metadata."
Everything covered in this phase's earlier chapters about chunking strategy, embedding model choice, and
knowledge graph construction lives here, and its correctness is judged by whether the index it produces is
complete, current, and well-structured. The query pipeline runs per request, on a completely different
clock: "at query time, the system runs semantic and keyword search to surface the most relevant chunks from
the index," then reranks, generates, and possibly loops through an agentic pattern or a graph query. A bug
in ingestion, a chunking change that silently degrades retrieval quality, does not show up as an ingestion
error, it shows up days later as a query-pipeline symptom that looks like a retrieval or generation problem,
which is exactly why the two need separate monitoring even though they feed one another.

**A demo hides exactly the failure modes that sink a production RAG system, because a demo never runs long
enough or broadly enough to hit them.** A retrieval step can look correct while the generation step still
fails, since "retrieval recall tells you whether the right chunk was in the top-k results. It does not tell
you whether the LLM used it faithfully," a gap Chapter 6.8's Faithfulness metric exists specifically to
catch. Chunking decisions absorb far more engineering attention than they return: "chunking occupies an outsized
amount of engineering time relative to the ROI it delivers." A single-shot retrieval strategy has its own,
separate limit, and it breaks the moment a question needs more than one document to answer. A multi-hop
question needing both a policy-change document and a separate financial report is exactly the case
single-shot retrieval was never built to handle, which is the gap Chapter 6.5's query decomposition
addresses.
Evaluation itself can silently go stale: a team that builds "a fixed eval set, run[s] it, get[s] 0.82
faithfulness, ship[s], and never look[s] at it again" has evaluation infrastructure that stopped doing its
job the moment production traffic diverged from that fixed set. And the parts that feel boring get skipped
until they are expensive: teams can spend "months optimizing faithfulness from 0.78 to 0.86 while running a
pipeline with 6-second P95 latency," solving the metric that gets attention while ignoring the one that
actually determines whether anyone can use the system.

**Observability is a distinct layer from evaluation, watching the system continuously rather than scoring it
periodically, and it needs its own metrics.** The distinction matters: "conventional monitoring entails
tracking predetermined metrics to assess system health and performance, while GenAI observability offers
insights into the inputs and outputs of a workflow, along with every intervening step." A production
observability layer tracks retrieval-specific signals, "Chunk Attribution indicates the chunks used for
generating the response, facilitating debugging," and "Chunk Utilization measures the utilization of
retrieved information in generating responses, aiding in the optimization of retrieval strategies," alongside
generation-specific signals like Context Adherence, which "measures the extent to which the model's response
aligns with the provided context," and system-level signals like latency and resource utilization that a
periodic evaluation run would never catch between test cycles. None of this replaces the Ragas-style metrics
from Chapter 6.8; it runs continuously in production where those metrics run periodically against a fixed
set, catching the drift that happens in the gap between evaluation runs.

**Governance and a feedback loop close the blueprint, catching a risk that evaluation metrics cannot see at
all: the index itself quietly becoming wrong.** "Context drift is invisible to standard RAG evaluation
metrics. A system with advanced context drift can maintain high faithfulness scores while producing answers
that are organizationally wrong," because faithfulness only checks whether a response matches its retrieved
context, not whether that context is still true. The risk shows up in layers: schema drift, where the
structure of the underlying data changes without the index being rebuilt to match; semantic drift, where a
term's meaning shifts within the organization even though the word itself hasn't changed; and staleness
drift, where the source documents themselves move on while the index keeps serving the old version.
Governance is what catches this: "governing a RAG system means applying the same access controls, data
quality standards, lineage tracking, and ownership accountability to the retrieval layer that you apply to
the rest of your data estate." And because "production RAG systems aren't static," every correction a user
or reviewer makes is a signal that belongs somewhere, "every query, correction, and feedback signal is an
opportunity to improve retrieval quality," which only happens if the query pipeline's observability layer
actually routes that signal back into the ingestion pipeline's next update rather than letting it evaporate.

None of the four layers is optional in a production system, even though a demo only ever exercises the
query pipeline. The ingestion pipeline can be as simple as a nightly rebuild for a small, slow-moving corpus,
and governance can be as light as a single person reviewing drift reports monthly, but skipping a layer
entirely, rather than sizing it to the system's actual risk, is how a demo's failure modes make it all the
way to production.
