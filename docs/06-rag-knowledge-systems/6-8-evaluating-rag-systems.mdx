## TL;DR

Every chapter so far in this phase has built a piece of a RAG or agentic pipeline: embeddings, vector
search, chunking, reranking, graph queries, caching. None of that tells you whether the pipeline you built
actually works, and "it feels better" is not a metric. This chapter covers the two families of metrics that
answer that question and the framework that ties them together. Retrieval metrics score the search half of
the system against a known-relevant set: Precision@k and Recall@k score whether the right documents came
back at all, while ranking-aware metrics like Mean Reciprocal Rank score "the multiplicative inverse of the
rank of the first correct answer" and Normalized Discounted Cumulative Gain rewards relevant results more
for appearing near the top of the list. Generation metrics score the other half, whether the model's answer
actually reflects what was retrieved. Ragas, a framework that "put[s] forward a suite of metrics which can
be used to evaluate these different dimensions without having to rely on ground truth human annotations,"
defines Faithfulness as the fraction of a response's claims that "can be supported by the retrieved
context," and pairs it with Context Precision, Context Recall, and Answer Relevancy to score the retrieval
and generation halves of a RAG system separately rather than judging the final answer as one opaque unit.
Most of these generation metrics lean on an LLM as the judge doing the scoring, which introduces its own
failure mode: judges have a measurable "verbosity bias" that "rewards longer answers even when shorter ones
deliver better accuracy," and even a strong judge model "aligns with human preferences over 80% of the
time," leaving a real error rate that a team has to catch some other way. This chapter walks through both
metric families, the Ragas framework that operationalizes them, and where automated evaluation still needs a
human in the loop.

## High-Level Explanation

Think of a newsroom fact-checking a story before it runs. Two different questions get asked, and they are
not the same question. Did the researcher pull the right source documents for this story at all, and did
they pull enough of them? That is a retrieval question, checkable against a list of documents that should
have turned up. Separately: does the finished article actually say what those source documents say, or did
the writer embellish, misquote, or draw a conclusion the sources don't support? That is a generation
question, checkable by reading the article against the sources it cites. A newsroom that only checks one of
these can still publish a false story, either because the researcher missed the right sources, or because
the writer wandered away from good ones. Evaluating a RAG system means running both checks, on every answer,
automatically, instead of trusting that a fluent-sounding response is a correct one.

## Deep-Dive Explanation

**Retrieval metrics score the search half of the pipeline against a set of documents already known to be
relevant.** Precision@k asks, of the k documents retrieved, how many were actually relevant, while Recall@k
asks, of all the relevant documents that exist, how many made it into the top k. A system can score well on
one and poorly on the other: a retriever that returns exactly one, perfectly relevant document at k=10 has
perfect precision and terrible recall if five relevant documents exist. Neither metric cares about order
within the top k, which is what ranking-aware metrics add. Mean Reciprocal Rank scores how early the first
relevant result appears: it is "the multiplicative inverse of the rank of the first correct answer: 1 for
first place, 1⁄2 for second place, 1⁄3 for third place and so on," averaged across a set of queries, so a
system that reliably places the right answer first scores close to 1.0 even if it never looks past that
point. Normalized Discounted Cumulative Gain generalizes this to graded relevance and to caring about the
whole ranked list, not just the first hit: it compares actual Discounted Cumulative Gain, "the total item
relevance in a list" discounted by a logarithm of each item's rank position, against the Ideal DCG, "the
maximum achievable DCG with the same set of relevance scores but in the perfect ranking order," so a system
that places its most relevant results first scores near 1.0 and one that buries them scores low even with
identical documents in the result set.

  <figcaption>Precision and recall count what was retrieved; Mean Reciprocal Rank and NDCG also score where in the ranking it landed.</figcaption>
</figure>

**Ragas evaluates the generation half without requiring a human-labeled correct answer for every query.**
The framework was introduced as "a framework for reference-free evaluation of Retrieval Augmented Generation
(RAG) pipelines," built because evaluating a RAG system is "challenging" along several separate dimensions
at once: "the ability of the retrieval system to identify relevant and focused context passages, the ability
of the LLM to exploit such passages in a faithful way, or the quality of the generation itself." Rather than
folding all of that into one pass/fail judgment, Ragas scores each dimension with its own metric. Faithfulness
measures "how factually consistent a response is with the retrieved context," and the scoring mechanism
decomposes the response into individual claims and checks each one against the retrieved context: a
response with two claims where both are supported by context scores 1.0, and a response where one of two
claims is contradicted by the context, such as getting a date wrong, scores 0.5. A response can be entirely
faithful to its context and still be wrong, if the context itself was bad, which is exactly why faithfulness
is paired with metrics that score the retrieval side too.

<figure>
  <img
    src={require('@site/static/img/illustrations/6-8-faithfulness-scoring.svg').default}
    alt="A diagram showing the faithfulness scoring process: a generated response is decomposed into individual claims, each claim is checked against the retrieved context to determine whether it is supported, and the faithfulness score is calculated as the number of supported claims divided by the total number of claims in the response."
  />
  <figcaption>Faithfulness decomposes a response into individual claims and scores the fraction the retrieved context actually supports.</figcaption>
</figure>

**Context Precision and Context Recall extend the retrieval-metric idea into Ragas's reference-free
setting, and Answer Relevancy scores whether the response addresses the question at all.** Context
Precision "evaluates the retriever's ability to rank relevant chunks higher than irrelevant ones for a given
query," "calculated as the mean of the precision@k for each chunk in the context," so an irrelevant chunk
sitting above a relevant one drags the score down even if every relevant chunk is present somewhere in the
list. Context Recall works the other direction: it "measures how many of the relevant documents...were
successfully retrieved," decomposing a reference answer into individual claims and checking whether the
retrieved context supports each one, because "higher recall means fewer relevant documents were left out."
Answer Relevancy scores a different failure mode entirely, a response that is faithful to its context but
doesn't actually answer the question asked: it works by generating several artificial questions the response
would answer, then scoring "the cosine similarity between the embedding of the user input and the embedding
of each generated question," so a verbose, evasive, or off-topic response scores low even if every sentence
in it happens to be true.

<figure>
  <img
    src={require('@site/static/img/illustrations/6-8-context-precision-recall.svg').default}
    alt="A diagram contrasting two retrieval failure modes with the same total content in the corpus: a low Context Precision case, where a relevant chunk is present but ranked below an irrelevant one, versus a low Context Recall case, where a relevant chunk needed to answer the question was never retrieved at all."
  />
  <figcaption>Context Precision penalizes a relevant chunk ranked too low; Context Recall penalizes a relevant chunk that never made it into the retrieved set at all.</figcaption>
</figure>

**Most of these generation-side metrics run on an LLM acting as the judge, and that judge has its own,
well-documented failure modes that an evaluation pipeline has to account for.** A judge model exhibits
"verbosity bias," which "rewards longer answers even when shorter ones deliver better accuracy," and
"position bias," which "causes judges to favor responses appearing first or last in comparisons, independent
of quality," along with "self-preference bias," which "appears when a judge scores outputs from its own
model family and inflates scores." None of these make LLM-as-judge scoring useless, but they cap how much a
single automated score can be trusted on its own: even a strong judge "aligns with human preferences over
80% of the time," and the remaining gap "means thousands of misclassified outputs slipping through
validation or triggering false alerts" at production scale. Teams that rely on these metrics for a
regression gate, blocking a deploy if scores drop, pair the automated scores with periodic human spot-checks
and track agreement between the two, rather than trusting the automated number in isolation forever.

None of these metrics replace each other, and none of them alone certifies a RAG system is production-ready.
A pipeline that retrieves perfectly but generates unfaithfully fails users just as badly as one that
generates faithfully from the wrong documents; catching either failure mode requires scoring both halves
separately, on every change, not just reading a handful of example outputs and deciding they look fine.
