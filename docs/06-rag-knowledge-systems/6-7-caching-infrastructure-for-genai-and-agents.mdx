## TL;DR

Every chapter so far in Phase 6 has assumed a request runs the full pipeline: embed, retrieve, rerank,
generate, maybe a graph query or an agentic loop on top. None of that is free, and a surprising fraction of
it is repeated work. This chapter covers three distinct layers of caching that avoid paying for that
repetition twice, each with a different match requirement and a different risk profile. Prompt caching
works at the token level: "prompt caching optimizes your API usage by allowing resuming from specific
prefixes in your prompts," checking whether "a prompt prefix, up to a specified cache breakpoint, is
already cached from a recent query" and reusing it if so, but only when "cache hits require 100% identical
prompt segments" up to that breakpoint, an exact-match mechanism that reduces the price of a cache read to
roughly a tenth of the base input price. Semantic caching relaxes that exact-match requirement: it
"employs embedding algorithms to convert queries into embeddings and uses a vector store for similarity
search," returning a cached response for a query that merely resembles a past one rather than matching it
exactly, because "using an exact match approach for LLM caches is less effective due to the complexity and
variability of LLM queries, resulting in a low cache hit rate." That flexibility is also where the danger
lives: two queries can sit at a similarity score of 0.91 in embedding space while meaning opposite things,
and "for triage it is malpractice" to treat them as interchangeable. Tool-call caching is a third,
different problem again, less about saving tokens and more about protecting systems and correctness: an
idempotent tool call is "necessary but not sufficient" for safe caching, because "if the underlying data
changes, your cached answer becomes a lie" regardless of how safely repeatable the call itself is. This
chapter walks all three: what each one caches, what it costs to get wrong, and how they compose in a real
GenAI or agent system.

## High-Level Explanation

Think of three different reasons a busy help desk might not redo work it already did. If the exact same
question comes in twice in a row, word for word, the desk doesn't research it again, it just reads back the
answer it already wrote down, that is prompt caching: fast, cheap, and safe only because the question was
identical. If a question comes in that sounds a lot like one from an hour ago but isn't quite the same
wording, a helper might be tempted to reuse that earlier answer, but they had better check the two
situations actually match before doing so, that is semantic caching, powerful precisely because it catches
paraphrases, and risky for the same reason. And if a colleague asks the desk to look something up in a
system that changes over time, a price, an inventory count, an account balance, remembering the last answer
forever would eventually mean handing out information that used to be true, that is the tool-call caching
problem: a lookup can be perfectly safe to repeat and still unsafe to remember.

## Deep-Dive Explanation

**Prompt caching reuses the exact tokens a model already processed, not an approximation of them.** The
mechanism is a prefix match: "the system checks if a prompt prefix, up to a specified cache breakpoint, is
already cached from a recent query. If found, it uses the cached version, reducing processing time and
costs. Otherwise, it processes the full prompt and caches the prefix once the response begins." A developer
marks where that prefix ends: "marking a block with cache_control writes exactly one cache entry: a hash of
the prefix ending at that block," and the guidance for placing it is specific, "place cache_control on the
last block whose prefix is identical across the requests you want to share a cache." The requirement behind
all of this is strict: "cache hits require 100% identical prompt segments, including all text and images up
to and including the block marked with cache control," a single changed character anywhere in that prefix
is a cache miss, not a partial credit. The economics reward getting this right: cache write tokens cost a
multiple of the base input price, but "cache read tokens are 0.1 times the base input tokens price," a
90% discount on every token that gets reused, and by default "the cache has a 5-minute lifetime," refreshed
for free on every use, with an optional longer window "if you find that 5 minutes is too short."

  <figcaption>A single changed token anywhere before the cache breakpoint turns a cheap cache read back into a full-price cache write.</figcaption>
</figure>

**Semantic caching trades prompt caching's exact-match guarantee for a much higher hit rate, and inherits
a correctness risk in return.** Rather than matching tokens, it matches meaning: a semantic cache "employs
embedding algorithms to convert queries into embeddings and uses a vector store for similarity search on
these embeddings," using a similarity evaluator that "uses various strategies to determine the similarity
between the input request and the requests from the Vector Store." The motivation is straightforward: exact
matching rarely fires twice on real user traffic, since "using an exact match approach for LLM caches is
less effective due to the complexity and variability of LLM queries, resulting in a low cache hit rate,"
while "semantic caching identifies and stores similar or related queries, thereby increasing cache hit
probability," with projects built around the idea claiming order-of-magnitude gains, cutting API costs and
cutting response latency dramatically when a hit fires. The risk sits in exactly what makes it powerful: two
symptom descriptions, "my left arm hurts" and "my right arm hurts," can score a 0.91 similarity in a
general-purpose embedding space, close enough to clear a loose threshold while describing two different
conditions entirely, a mismatch a medical use case cannot tolerate. Time compounds the same problem: "what
is the current interest rate?" asked yesterday and today are semantically identical and factually
different, so a permissive cache will happily serve last month's number at a similarity score of 1.0.
Tuning the threshold is a real risk-benefit tradeoff, not a knob with one correct setting, since the right
value depends on what a false hit actually costs in a given domain, and teams that take this seriously run
a new threshold against real traffic in shadow mode before ever letting it serve a live response.

  <figcaption>A similarity score close to the threshold cannot distinguish a true paraphrase from two different questions that merely use similar words.</figcaption>

**Tool-call caching is a different problem from either token or semantic caching: it is about protecting
systems and correctness, not primarily about saving tokens.** An agent that calls the same external tool
with the same arguments repeatedly, in a long-running workflow, generates real cost beyond API pricing:
"tool calls often dominate token usage indirectly by expanding context windows with raw data," so caching a
call's result keeps that raw data from bloating every subsequent turn of the conversation. But whether a
cached tool result is safe to reuse depends on more than whether the call itself is safe to repeat:
"idempotent tool calls are necessary but not sufficient" for caching, because "a read-only database query
might be idempotent, but if the underlying data changes, your cached answer becomes a lie." The fix has to
account for more than the literal arguments passed to a tool: a cache key built only from arguments treats
"what is today's exchange rate" as cacheable forever, when what actually needs to vary is not the arguments
but the moment the call happens, since the cache key must capture not just arguments but intent, including
whatever about the call is time-sensitive or context-dependent. Getting this wrong in either direction has a
cost: caching too aggressively serves stale data as if it were current, and caching too conservatively
throws away real savings on calls that genuinely never change, like a deterministic calculation with no
external dependency at all.

<figure>
  <img
    src={require('@site/static/img/illustrations/6-7-tool-call-cache-freshness.svg').default}
    alt="A diagram showing an agent's tool-call cache decision: a tool call whose result is a deterministic calculation with no external dependency is safe to cache indefinitely, a tool call against a slowly-changing external system is safe to cache for a bounded time-to-live, and a tool call against a rapidly-changing external system, such as a live price or an active incident status, is unsafe to cache at all regardless of how idempotent the call itself is."
  />
  <figcaption>Idempotency answers whether a call is safe to repeat; it says nothing about whether its cached answer is still true.</figcaption>
</figure>

**The three layers compose rather than compete, because each one caches a different kind of repetition.**
A single request in a RAG or agentic system can pass through all three: a long, mostly-static system prompt
and a stable set of retrieved documents are prime candidates for prompt caching's exact-match reuse; the
user-facing question in front of that static context is a candidate for semantic caching if the domain can
tolerate its risk; and any tool call the pipeline makes along the way needs its own, separate decision about
whether the world underneath that call changes fast enough to make caching it a bad idea. Designing a
caching strategy is less about picking one of these three and more about deciding, for each piece of a
request, which kind of repetition it actually represents, and matching the cache to that.

## Reference Architecture

<ArchitectureDiagram
  title="Where each caching layer sits in a RAG or agent request"
  mermaid={`
flowchart TD
  REQ[Incoming request: system prompt, documents, user question] --> PCACHE{Prompt cache: is the static prefix identical to a recent request?}
  PCACHE -->|hit, ~10% of base price| RETRIEVE[Retrieval + reranking, Ch. 6.4]
  PCACHE -->|miss, full price, cache the prefix| RETRIEVE
  RETRIEVE --> SCACHE{Semantic cache: does this question resemble a recent one above threshold?}
  SCACHE -->|hit| RESPONSE[Return cached response]
  SCACHE -->|miss| GEN[Generation]
  GEN --> TOOL{Agent needs a tool call?}
  TOOL -->|yes| TCACHE{Tool-call cache: safe to reuse given data volatility?}
  TCACHE -->|hit| RESULT[Reuse cached tool result]
  TCACHE -->|miss or unsafe| LIVE[Execute live tool call]
  RESULT --> ANSWER[Final answer]
  LIVE --> ANSWER
  TOOL -->|no| ANSWER
`}
  components={[
    {name: 'Prompt cache', responsibility: 'Sits at the token level, before the model processes a request, reusing an exact-match static prefix at a fraction of its original cost.'},
    {name: 'Semantic cache', responsibility: 'Sits before retrieval and generation, short-circuiting the entire pipeline when a question resembles a recent one closely enough, with a threshold tuned to the domain\'s tolerance for a false hit.'},
    {name: 'Tool-call cache', responsibility: 'Sits at each individual tool call an agent makes, deciding per-call whether the underlying data is stable enough to reuse rather than re-fetch.'},

None of these layers replace the pipeline built across this phase, they decide how often that pipeline
actually has to run. A production system tunes each layer independently: an aggressive TTL and a loose
similarity threshold where a false hit is cheap, and no caching at all, or a very short TTL, exactly where
one is not.
