## TL;DR

Chapter 6.9's ingestion pipeline assumed a source of documents to parse, chunk, embed, and index, but it
never addressed a problem that sits one layer earlier: most organizational knowledge lives in fragmented
systems that were never built to be read by anything outside themselves, metadata catalogs, wikis, shared
drives, code comments, docstrings, each with its own API or its own way of being opened. "Every agent
builder is solving the same context-assembly problem from scratch, every catalog vendor is reinventing the
same data models, and the knowledge itself is locked behind whichever surface created it." The Open
Knowledge Format, introduced by Google Cloud in 2026, is an attempt to fix that at the format level rather
than the tooling level: "OKF v0.1 represents knowledge as a directory of markdown files with YAML
frontmatter, with a small set of agreed-upon conventions that let wikis written by different producers be
consumed by different agents without translation." Each concept, a table, a dataset, a metric, a playbook, a
runbook, an API, becomes one markdown file identified by its own file path, carrying "the small set of
structured fields that need to be queryable: type, title, description, resource, tags, and timestamp," and
the files link to each other with ordinary markdown links, which turns a flat directory into something
closer to a graph of relationships than a simple parent-child file hierarchy. A bundle of OKF documents needs
nothing more than plain markdown files to work, so it opens in any editor, renders on GitHub, and packages as
an ordinary tarball, and because "OKF is not tied to any specific cloud, database, model provider, or agent
framework," an ingestion pipeline built for one organization's OKF bundle needs no custom connector to read
another's. This chapter covers what OKF actually specifies, what it deliberately leaves out, and where it
fits relative to a wiki, a proprietary catalog API, and the knowledge graphs from Chapter 6.6.

## High-Level Explanation

Think of the difference between a library that lends you a book in whatever binding, font, and shelving
system it happens to use internally, and a library that has agreed, along with every other library in the
country, to describe every book with the same handful of fields on the same kind of card: title, author,
subject, location. You do not need a special adapter to walk into a different library and find what you
need, because the description format is shared even though every library's actual collection, building, and
staff are completely different. OKF is that shared card catalog format for organizational knowledge. It does
not tell a company how to run its wiki, its BigQuery catalog, or its code repository, it just gives every
one of those systems a common, minimal way to export what they know, one markdown file per concept, so that
any agent or ingestion pipeline that understands OKF can read any organization's exported knowledge without
being built specifically for that organization's tools.

## Deep-Dive Explanation

**The problem OKF targets is not a missing tool, it is a missing shared format.** Most organizational
knowledge already exists somewhere: the schema behind a table, what a metric actually means to the business,
the runbook for an incident, the join path between two systems. The trouble is that it exists in mutually
unreadable places, spread across metadata catalogs with their own APIs, wikis and shared drives, code
comments and docstrings, so nothing outside the system that created a piece of knowledge can read it without
custom integration work. Every team building an agent against that knowledge ends up solving the same
integration problem in isolation, "every agent builder is solving the same context-assembly problem from
scratch, every catalog vendor is reinventing the same data models," which means the cost of connecting a new
knowledge source to a new agent framework gets paid again and again rather than once. OKF does not try to
replace any of those underlying systems, a wiki stays a wiki and a catalog stays a catalog, it defines a
minimal export shape those systems can all target, so the integration cost gets paid once per source rather
than once per source-consumer pair.

**An OKF bundle represents each piece of knowledge as exactly one markdown file, identified by its own file
path.** A bundle is a directory of markdown files, one per concept, and a concept can be almost anything an
organization wants to capture: a table, a dataset, a metric, a playbook, a runbook, an API. Each concept gets
exactly one file, and that file's path in the directory is its identity, there is no separate ID scheme to
maintain. A concept file opens with YAML frontmatter carrying a small, fixed set of fields, for example:

```yaml
---
type: BigQuery Table
title: Orders
description: One row per completed customer order.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, revenue]
timestamp: 2026-05-28T14:30:00Z
---
```

followed by a markdown body carrying whatever free-text explanation, schema notes, or examples the concept
needs. The directory structure itself carries meaning too, a `tables/` folder groups table concepts, a
`metrics/` folder groups metric concepts, and an `index.md` at each level can summarize what that folder
contains, but nothing about OKF requires a database, an API server, or a specific vendor's tooling to produce
or consume it.

**Of the reserved fields, only one is actually required on every concept, and it is the one that makes
filtering and governance possible without reading every file's prose.** "OKF requires exactly one thing of
every concept: a type field." Everything else in the reserved vocabulary, "the small set of structured
fields that need to be queryable: type, title, description, resource, tags, and timestamp," is there to
support the same kind of structured filtering a database column would support, without requiring a database:
an ingestion pipeline can decide to pull only concepts whose type is `BigQuery Table`, or only ones tagged
`sales`, or only ones updated after a given timestamp, using nothing more than a directory walk and a YAML
parser. This is deliberately less expressive than a real schema or ontology, and that is the point: the
format asks for the minimum structure that makes bulk automated processing possible, and leaves everything
else, the actual meaning of a concept, to the markdown body a human or a model can read directly.

**Concepts reference each other the same way any markdown document references another, and that turns a flat
directory of files into something closer to a graph.** Concepts link to each other with ordinary markdown
links, and those links turn a flat directory into a graph of relationships richer than the parent-child
structure the file system alone would imply. A table's concept file can note a foreign key relationship with
an ordinary link, `FK to [customers](/tables/customers.md)`, and that link is both human-readable prose and a
machine-traceable edge at the same time. This is a much lighter mechanism than the property graphs or RDF triple stores from
Chapter 6.6, OKF has no query language, no schema validation, and no dedicated storage engine, but it costs
nothing to adopt beyond writing markdown, and for many organizations it is enough structure to make relevant
concepts discoverable without standing up a graph database at all. A team that outgrows what markdown links
can express can still migrate the same concepts into a full knowledge graph later, since the concepts and
their relationships are already identified.

OKF sits upstream of everything built in this phase. It does not replace the ingestion pipeline, the vector
index, or the retrieval and generation steps, it changes how many different, incompatible source systems an
ingestion pipeline has to write a custom connector for. A source that exports a valid OKF bundle needs no
special-case code at all, it looks like every other OKF bundle to the pipeline that consumes it.

## Hands-On: Build Your First OKF Bundle

Everything above is easier to believe once you have actually written one of these bundles yourself. Nothing
here needs a cloud account, a database, or a special SDK, just a text editor and, if you want to parse it
back out, a few lines of Python. Fifteen minutes gets you a working bundle and a script that filters it.

**Step 1: Create the directory.** An OKF bundle is just a folder. Start small, one concept type is enough to
begin with.

```bash
mkdir -p sales/tables
```

**Step 2: Write your first concept file.** Every concept is one markdown file: YAML frontmatter on top, a
free-text body underneath. Create `sales/tables/orders.md`:

```markdown
---
type: BigQuery Table
title: Orders
description: One row per completed customer order.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, revenue]
timestamp: 2026-05-28T14:30:00Z
---

# Orders

One row per completed order. Grain: order_id.
```

That is a complete, valid concept on its own. `type` is the one field OKF actually requires, everything
else in the frontmatter is there to make filtering possible later.

**Step 3: Add a second concept and link it.** This is where OKF starts to feel different from a plain
document dump. Create `sales/tables/customers.md`, and reference the first file with an ordinary markdown
link:

```markdown
---
type: BigQuery Table
title: Customers
description: One row per known customer account.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=customers
tags: [sales]
timestamp: 2026-05-28T14:30:00Z
---

# Customers

One row per customer. Referenced by [orders](./orders.md) via `customer_id`.
```

Two files, one link. That link is the entire relationship, no schema registration, no separate edges table.

**Step 4: Walk the bundle and parse it back out.** This is the fifteen-line script that makes the rest of
this chapter concrete. It needs `pyyaml` (`pip install pyyaml`):

```python
from pathlib import Path
import yaml

def load_concepts(bundle_root: Path):
    concepts = []
    for md_file in sorted(bundle_root.rglob("*.md")):
        text = md_file.read_text()
        if not text.startswith("---"):
            continue
        _, frontmatter, body = text.split("---", 2)
        meta = yaml.safe_load(frontmatter) or {}
        meta["path"] = str(md_file)
        meta["body"] = body.strip()
        concepts.append(meta)
    return concepts

concepts = load_concepts(Path("sales"))
print(f"loaded {len(concepts)} concepts")
for c in concepts:
    print(f"  {c['type']:<16} {c['title']:<12} {c['path']}")
```

Running it against the two files from steps 2 and 3 prints:

```
loaded 2 concepts
  BigQuery Table   Customers    sales/tables/customers.md
  BigQuery Table   Orders       sales/tables/orders.md
```

**Step 5: Filter by type, the way an ingestion pipeline would.** Add one line to the script above:

```python
tables = [c for c in concepts if c.get("type") == "BigQuery Table"]
```

`tables` is now exactly the input an ingestion pipeline needs, a list of dicts with a title, a description,
and a body, ready to chunk and embed the same way Chapter 6.9 handles any other document source. Scale this
same fifteen-line pattern up to a bundle with hundreds of concepts across several types, and the filter line
is the only thing that changes: swap `"BigQuery Table"` for whatever type the pipeline actually needs next.

That is the whole mechanism. Everything in the rest of this phase, chunking, embedding, retrieval,
generation, caching, evaluation, runs unchanged once a bundle like this one is what feeds it.
