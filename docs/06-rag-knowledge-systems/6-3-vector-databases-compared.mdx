## TL;DR

Chapter 6.2 covered how an embedding gets compared to another and how algorithms like HNSW, IVF, and
product quantization avoid scanning every vector to find the closest ones. None of that is a product on
its own. A vector database is what wraps an ANN index with everything a production system actually
needs around it: inserting and deleting vectors without rebuilding the whole structure, filtering by
metadata alongside similarity, isolating one tenant's data from another's, and surviving a restart. Four
deployment archetypes cover most of what teams actually reach for. Fully managed, serverless systems
like Pinecone separate storage from compute entirely, storing vectors in "immutable files called slabs"
in "distributed object storage that provides virtually unlimited scalability." Self-hosted, distributed
systems like Milvus take a similar disaggregation and put it on infrastructure a team runs itself,
splitting "stream processing into Streaming Node and batch processing into Query Node and Data Node."
Systems like pgvector add vector search directly to a database many teams already run, trading some
raw performance for the ability to keep vectors and relational data in the same ACID-compliant store.
And embedded systems like Chroma run in-process or as a lightweight local server, built on the
observation that "object storage is an order of magnitude cheaper than a replicated set of SSDs," a
tradeoff worth making in exchange for higher per-request latency. Metadata filtering, the kind Qdrant
builds around a "rich set of conditions" combined with `should`, `must`, and `must_not` clauses, and
hybrid search, which fuses dense vector results with sparse keyword results, often matter as much as
which ANN algorithm sits underneath. Benchmarking projects like VectorDBBench measure queries per
second, P99 latency, recall, and cost together for exactly this reason: a system that wins on one axis
routinely loses on another. This chapter builds a selection framework around those axes rather than
naming one winner.

## High-Level Explanation

Chapter 6.2 explained how to file a book by the ideas inside it rather than its title, and how to find
the nearest shelf-neighbors quickly once a library holds millions of books. This chapter is about the
library building itself. Does it let patrons check a book out, replace it with a revised edition, or
remove it entirely, without re-shelving the whole collection? Can a librarian restrict which patrons see
which books, the way a hospital restricts one department's records from another's? Can a patron search
by the exact words in a title as well as by which shelf-neighborhood a topic lives in? And critically,
does the building come pre-built, staffed, and maintained by someone else, or does a team have to
construct and run it themselves? A vector database is the answer to all of those questions bundled
together, and different products answer them differently enough that the choice is rarely close to
arbitrary.

## Deep-Dive Explanation

**A vector database is the ANN index from Chapter 6.2, plus everything a production system needs around
it.** HNSW, IVF, and product quantization are algorithms for finding nearby vectors quickly. None of them
say anything about what happens when a document gets updated, when a query needs to exclude everything
that is not owned by the current tenant, when the index needs to survive a process restart, or when two
different clients need to query the same collection at once without stepping on each other. A vector
database is the software layer that answers those questions, and the answers it gives, more than the ANN
algorithm it happens to use internally, are usually what decide which product a team reaches for.

**Fully managed, serverless systems separate storage from compute entirely.** Pinecone's architecture
organizes data into "immutable files called slabs" held in "distributed object storage that provides
virtually unlimited scalability and high availability," with write and read paths that "scale
independently based on demand" so that heavy writes never slow down concurrent queries. New writes land
in an in-memory structure first, then get organized into slabs using "fast indexing techniques" while
small, which later get merged "into larger slabs that use more sophisticated methods" as they grow,
"amortiz[ing] the cost of more expensive indexing" over time. A query checks that in-memory structure for
anything not yet durable, then fans out to query executors that search their assigned slabs, typically
cached in memory or on local SSD, with the underlying object storage as a slower fallback. The appeal of
this model is that a team writes essentially no infrastructure code; the cost is that the infrastructure
is somebody else's, running wherever that vendor's regions happen to be.

**Self-hosted, distributed systems bring similar disaggregation to infrastructure a team runs itself.**
Milvus takes a comparable approach, "fully disaggregated storage and compute layers" that "enable
horizontal scaling of compute nodes," but deploys it on a team's own Kubernetes cluster rather than a
vendor's managed service. It separates workloads by kind rather than treating them as one monolithic
job: "by separating stream processing into Streaming Node and batch processing into Query Node and Data
Node, Milvus achieves high performance while meeting real-time processing requirements simultaneously."
Worker nodes stay "stateless thanks to separation of storage and computation," which is what makes
horizontal scale-out and disaster recovery straightforward to automate. Under the hood, Milvus builds on
the same algorithmic building blocks Chapter 6.2 covered directly, "Faiss, HNSW, DiskANN, and SCANN,"
rather than reinventing them. The appeal here is control: a team decides where the data lives, how it
scales, and what it costs at the infrastructure level, at the price of actually operating that
infrastructure.

**A third path adds vector search directly to a database many teams already run.** pgvector is a
PostgreSQL extension, not a separate system, which means vectors can live in the same tables as the
relational data they describe, queried with ordinary SQL joins and covered by the same ACID guarantees
and point-in-time recovery Postgres already provides. It supports the two index families Chapter 6.2
introduced: HNSW, which "has better query performance than IVFFlat, in terms of speed-recall tradeoff,
but has slower build times and uses more memory," and IVFFlat, which trades some recall for faster
construction and a smaller memory footprint. The tradeoff is bluntly practical: a team keeps its existing
operational tooling, backup strategy, and access controls, and gives up the specialized performance and
horizontal scale a purpose-built vector database is designed for. For a system already running Postgres
with vector search as one feature among many rather than the whole point, that tradeoff is often an easy
one to accept.

**A fourth path skips server infrastructure entirely.** Chroma is built to run embedded, in-process
inside an application, or as a lightweight local server, positioning it for prototyping, local-first
applications, and small-scale deployments where standing up a distributed system would be overkill. Its
design leans on the same object-storage economics that shape Pinecone's architecture: "object storage is
an order of magnitude cheaper than a replicated set of SSDs, and has incredibly high parallel
throughput," at the cost of higher per-request latency than an in-memory or SSD-backed system, so a
system built around object storage from the start can serve much larger collections per dollar than one
that assumes everything stays resident in memory. A team can start
with Chroma running embedded during development and, if the workload outgrows that, move to a managed or
self-hosted deployment without changing how the application queries it.

**Metadata filtering is not a footnote to vector search, it is often the deciding factor in whether a
result is even usable.** A search for "the nearest similar support ticket" is close to meaningless if it
can return a ticket from a different customer's account. Qdrant builds its whole design around this,
attaching "any JSON payload to your vectors" and filtering on it "using a rich set of conditions, keyword
matching, full-text, numeric ranges, geo-locations, and more, combined with `should`, `must`, and
`must_not` clauses." That filtering happens alongside the vector search itself, not as a separate pass
over the results, which is what keeps a heavily filtered query from silently returning fewer results
than expected. Qdrant also applies quantization, the same family of techniques Chapter 6.2 covered as
product quantization, to cut memory use "by up to 97%" while letting a team "tune the trade-off between
search speed and precision" directly. A vector database without expressive, efficient filtering is
unusable the moment a real deployment needs multi-tenancy, access control, or any constraint tighter
than "anywhere in the whole collection."

**Combining vector search with keyword search often beats either one running alone.** Dense vectors are
good at matching meaning even when the wording differs, but weak at forcing an exact match on a specific
term; sparse, keyword-based search, typically scored with an algorithm like BM25, is the reverse. Hybrid
search runs both "in parallel" and hands the two result sets "to a fusion algorithm, such as Reciprocal
Rank Fusion," which scores each document by summing `1 / (k + rank)` across the lists it appeared in, a
formula that "penalizes the documents that are ranked lower in the list" without needing the two search
methods' raw scores to be on comparable scales in the first place. Weaviate's own example makes the case
concretely: searching for "how to catch an Alaskan Pollock," dense vectors correctly disambiguate "catch"
as the fishing sense of the word, while sparse search anchors the exact phrase "Alaskan Pollock" that a
purely semantic match might drift away from. Hybrid search "significantly improves the user experience
by reducing the need for perfectly phrased queries" while still rewarding a query that does use the
exact right term.

**Comparing vector databases means weighing several axes at once, not chasing a single speed number.**
VectorDBBench, an open benchmark maintained by Zilliz, measures queries per second, P99 latency, recall,
serial search latency, and behavior under continuous data ingestion, and reports comparisons at matched
cost points rather than in isolation, because raw throughput on its own says little about whether a
system is actually a good fit. A database tuned for the highest possible recall is rarely the one with
the lowest latency at the same cost, and a system that performs well on a static, pre-loaded dataset can
behave very differently once vectors are being written continuously in production. The honest answer to
"which vector database is fastest" is that it depends on which axis, and at what cost, a specific
workload actually cares about most.
