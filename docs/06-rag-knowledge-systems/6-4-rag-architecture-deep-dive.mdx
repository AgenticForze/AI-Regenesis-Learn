## TL;DR

Chapter 6.3 covered the vector database: a system that stores embeddings and answers similarity queries
at scale. That database only earns its keep because of everything that happens before a document ever
reaches it and everything that happens after a query leaves it. Before storage, ingestion turns a raw
file, a PDF, a scanned form, an HTML page, into structured content a chunker can actually work with,
tools built for this stage describe their job as "extraction of structured content from raw, unstructured
documents," followed by cleaning and a chunking pass built on "deep understanding of document formats"
rather than blind character counting. Chunking itself is not one technique but several, each trading
accuracy against complexity differently. Recursive character splitting tries a list of separators in
order, by default `["\n\n", "\n", " ", ""]`, falling back to a smaller unit only when a larger one does
not fit. Semantic chunking instead compares the embedding similarity of consecutive sentences and places
a boundary wherever that similarity drops past a configurable percentile threshold. Parent-document
retrieval, sometimes called small-to-big, resolves a real tension directly: "you may want to have small
documents, so that their embeddings can most accurately reflect their meaning," but "you want to have
long enough documents that the context of each chunk is retained," so it indexes small chunks for
accurate matching and returns their larger parent documents once one is found. After retrieval narrows
millions of vectors to a shortlist, most production systems add a second, slower pass: a cross-encoder
reranker feeds the query and each candidate through the same network together and outputs "a single score
between 0 and 1 indicating how relevant the document is," a step too expensive to run over an entire
collection but cheap over the roughly 100 candidates retrieval already produced. Where that reranked
evidence lands in the final prompt matters too: a 2023 study by researchers at Stanford, UC Berkeley, and
Samaya AI found that "performance is often
highest when relevant information occurs at the beginning or end of the input context," and
"significantly degrades when models must access relevant information in the middle of long contexts, even
for explicitly long-context models." Generation is the last stage and the one users actually see:
assembling retrieved chunks into a prompt, instructing the model to answer only from what it was given,
and grounding every claim in a specific passage so a user can verify it rather than take it on faith, the
way citation features return "the exact passages that support each claim." This chapter walks the whole
pipeline in order: ingestion, chunking, retrieval, reranking, and generation.

## High-Level Explanation

Chapters 6.2 and 6.3 built the library: a system that files books by meaning and finds the nearest
shelf-neighbors to a query almost instantly. This chapter is about everything that happens before a book
reaches that shelf and everything that happens after a patron finds one. A book has to be broken into
readable, catalogable pieces before it can be shelved at all, that is ingestion and chunking. Once a
patron's question turns up a stack of promising pages, a good librarian does not hand over the whole
stack; they skim it more carefully, keep the pages that actually answer the question, and put the most
important ones on top, that is reranking. And a librarian who actually answers the question does not just
point at a shelf, they write an answer and note, passage by passage, exactly which page supports which
sentence, that is generation. Ingestion and chunking decide what gets filed and how finely; retrieval and
reranking decide what gets read and in what order; generation decides what the patron actually walks away
with.

## Deep-Dive Explanation

**Ingestion turns a raw file into something a chunker can work with.** A PDF, a scanned form, an HTML
export, and a Word document do not share a format, and none of them arrive as clean text. Tools built for
this stage, such as Unstructured, describe their job as "extraction of structured content from raw,
unstructured documents": parsing PDFs and scanned images, including OCR for pages with no text layer at
all, pulling tables out as tables rather than scrambled text, and cleaning the result by "removing
unwanted content" that would otherwise pollute an embedding. The output is not raw text either; it is
broken into what these tools call document elements, using "deep understanding of document formats to
partition documents into semantic units" rather than counting characters. Get this stage wrong, a table
flattened into unreadable text, a scanned page skipped entirely, and every later stage inherits the
damage: an embedding model can only encode what ingestion managed to extract in the first place.

**Chunking decides how finely a document gets sliced, and different strategies solve different
problems.** The simplest approach, recursive character splitting, tries a list of separators in order and
falls back to a smaller one only when a larger one does not produce a chunk that fits: the default list is
`["\n\n", "\n", " ", ""]`, so a splitter tries to break on paragraph boundaries first, then lines, then
words, and only cuts mid-word as a last resort. It is fast, predictable, and knows nothing about meaning,
a paragraph boundary is not always a topic boundary. Semantic chunking works differently, comparing the
embedding similarity between consecutive sentences and placing a boundary wherever that similarity drops
past a "breakpoint percentile threshold," so a chunk boundary tracks an actual shift in subject rather
than a fixed character count, at the cost of an embedding call per sentence and an output size that is
no longer predictable ahead of time. Parent-document retrieval, sometimes called small-to-big, sidesteps
the tradeoff between chunk size and embedding accuracy directly: "you may want to have small documents,
so that their embeddings can most accurately reflect their meaning. If too long, then the embeddings can
lose meaning," but "you want to have long enough documents that the context of each chunk is retained."
The fix is to index small chunks and store a pointer back to something larger: retrieval "first fetches
the small chunks but then looks up the parent IDs for those chunks and returns those larger documents,"
so a search matches on a precise, focused embedding while generation still receives the surrounding
paragraph or section that gives that match its context. A fourth approach, structure-aware chunking,
builds directly on what ingestion already identified: rather than cutting purely on length or meaning, it
respects the element boundaries ingestion produced, never splitting a table row, a code block, or a list
item across two chunks even when a length-based splitter would.

**Retrieval narrows millions of chunks to a shortlist, and diversity matters as much as raw similarity.**
Chapters 6.2 and 6.3 covered the mechanics: an ANN index turns a query embedding into a fast, approximate
search over everything the vector database holds, typically returning the top few dozen or few hundred
candidates ranked by similarity alone. Pure similarity ranking has a blind spot, though: the top ten
results for a broad query can all be near-duplicates of each other, each individually relevant but none
adding anything the others did not already say. Maximal Marginal Relevance addresses this directly by
scoring each candidate not just against the query but against what has already been selected: "a document
has high marginal relevance if it is both relevant to the query and contains minimal similarity to
previously selected documents." The method's original paper illustrates the problem with a search for
airline-disaster coverage that returns dozens of near-identical articles about the same crash, arguing
that "perfect precision, therefore, may prove insufficient in meeting user needs" when every result says
the same thing. A tunable parameter controls the balance directly, weighting pure relevance against
redundancy avoidance, so a system can decide how much variety a shortlist actually needs before it moves
on to reranking.

**Reranking is retrieval's second, more careful pass, and it changes both which results survive and where
they land.** Retrieval is built for speed: comparing a query embedding against millions of stored vectors
has to be fast, which is exactly why it uses a bi-encoder that embeds the query and every document
independently, ahead of time. A cross-encoder reranker gives up that independence on purpose: the query
and a single candidate document are "passed simultaneously to [a] transformer network, which then outputs a
single score between 0 and 1 indicating how relevant the document is for the given query." That joint
pass is far more accurate, since the model can directly compare query and document, and far too slow to
run against a whole collection, "scoring thousands or millions of (query, document)-pairs would be rather
slow," so it only ever runs against the shortlist retrieval already narrowed things down to, often around
100 candidates. Cohere's Rerank product packages exactly this step: given a query and a list of documents,
it "indexes the documents from most to least semantically relevant to the query," returning a
`relevance_score` for each and a `top_n` parameter to cap how many survive. Where those survivors land in
the final prompt is its own problem: language models show a measured, consistent pattern where
"performance is often highest when relevant information occurs at the beginning or end of the input
context" and "significantly degrades" for information placed in the middle, "even for explicitly
long-context models," so a reranker's job is not just picking the best evidence but placing it where a
model is most likely to actually use it.

**Generation is the stage a user actually sees, and grounding turns a fluent answer into a verifiable
one.** Everything upstream exists to hand the model a small, well-ordered set of passages instead of an
entire knowledge base, and generation is where those passages get assembled into a prompt alongside the
user's question and instructions to answer only from what was provided. A fluent answer is not
automatically a correct one: the model can still blend, misattribute, or invent a detail that sounds
consistent with the retrieved text without actually being supported by it. Grounding features close that
gap by tying each claim back to a specific source location instead of trusting the model's word for it.
Citations-style features, for example, are built to "ground [a model's] responses in your source
documents," returning "the exact passages that support each claim" alongside precise location data, a
character range for plain text, a page range for a PDF, so a user can check any claim against its source
directly rather than trusting the response wholesale. Parsing citations this way at the API level, rather
than through prompting alone, is "significantly more likely to cite the most relevant quotes from
documents than purely prompt-based approaches," which makes grounding a property of the pipeline itself
rather than a hope about how carefully the model happened to follow instructions.

This chapter completes the mechanical pipeline from a raw document to a grounded answer. Chapter 6.5
picks up more advanced patterns built on top of it: hybrid search variations, HyDE, GraphRAG, and agentic
RAG, where retrieval itself becomes something a model can reason about and repeat rather than a single
fixed step.
