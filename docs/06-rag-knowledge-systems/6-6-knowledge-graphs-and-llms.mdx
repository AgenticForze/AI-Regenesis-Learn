## TL;DR

Chapter 6.5 used a knowledge graph as one ingredient in GraphRAG: an LLM read a corpus, built a graph,
clustered it into communities, and reasoned over community summaries. This chapter goes underneath that
pattern to the graph itself. A knowledge graph, at its core, is "an organized representation of real-world
entities and their relationships," where relationships are "stored directly in the database rather than
re-generating them using joins in queries" the way a relational database does. Two structural conventions
dominate how that representation gets built: RDF triple stores decompose every fact into a
subject-predicate-object triple and are queried with SPARQL, while labeled property graphs attach
properties directly to nodes and relationships and are queried with Cypher, and "because of the atomic
decomposition of the data and RDF, you typically have longer patterns when you perform queries" against a
triple store than against a property graph. Building a graph from raw text now typically means instructing
an LLM with a schema, "you can specify a schema with allowed nodes and relationships, as well as properties
and additional extraction instructions," and the model returns the result as "structured JSON" a graph
database can store directly. That extraction creates a problem the mechanical pipeline from Chapter 6.4
never had to face: the same person can appear as different name variants across different documents, and
entity resolution exists specifically because "we ideally want a single real-world entity to be represented
with a single node." Once a graph exists, two very different techniques let a model use it beyond reading
it: knowledge graph embeddings, vector representations of entities and relationships, "used to predict
missing links," and Text2Cypher, which translates a plain-language question directly into a graph query so
an agent can "ground its insights in actual domain knowledge" rather than retrieving a pre-written summary.
This chapter walks all four: a knowledge graph's structure, how one gets built, why entity resolution is a
genuine engineering problem, and the two distinct ways a model interacts with a graph once it exists.

## High-Level Explanation

Chapters 6.2 and 6.3 filed facts by meaning: a query finds whatever sits nearest to it in embedding space,
with no explicit notion of how any two facts relate to each other. A knowledge graph files facts by
relationship instead: not just that a fact exists, but exactly which other facts it connects to, and how. A
relational database captures relationships too, but computes them on the fly by joining tables together at
query time; a knowledge graph draws the connections once, when the data goes in, and stores them as
first-class parts of the graph itself, so following a chain of relationships several hops deep is a
traversal rather than a cascade of joins. Building a graph from a pile of documents means teaching a model
to read text the way an analyst reads a case file: pull out who and what is mentioned, decide how they
relate, and, critically, notice when two mentions in different documents are actually the same person or
thing. Once that graph exists, it can be used two different ways: a model can query it directly, the way an
analyst pulls a specific record, or a separate model can learn the graph's own patterns well enough to
guess at connections nobody ever wrote down.

## Deep-Dive Explanation

**A knowledge graph stores relationships as data, not as something computed at query time.** The core
definition is simple: "a knowledge graph is an organized representation of real-world entities and their
relationships," where "nodes denote and store details about entities, such as people, places, objects, or
institutions," and "relationships link two nodes together: they show how the entities are related." A
relational database can represent the same facts, but "since the relationships reside in the code rather
than with the dataset, each application and data use must have its own implementation." A native graph database instead keeps
relationships "stored directly in the database rather than re-generating them using joins in queries," so a
query that needs to follow several relationships in sequence, who reports to whom, who approved what, which
regulation cites which prior ruling, traverses stored edges instead of recomputing a chain of joins each
time. A schema, described as "a framework...that organizes nodes and relationships according to fundamental
concepts essential to the use cases at hand," gives that structure consistent meaning across the whole
graph rather than letting every document invent its own vocabulary for the same kind of relationship.

**Two structural conventions dominate how a knowledge graph actually gets built and queried.** RDF triple
stores decompose every fact into its smallest possible unit: "the subject will be a resource, or a node in
the graph. The predicate will represent an edge, a relationship, and the object will be another node or a
literal value." This is, in a real sense, "a complete atomic decomposition of our data": nothing is
attached directly to a node, everything is its own triple, queried with SPARQL. Labeled property graphs
take a different approach, where "both the nodes and relationships have an internal structure," meaning
properties can attach directly to a node or an edge rather than becoming separate triples of their own,
queried with Cypher. The practical consequence of that structural choice shows up at query time: "because
of the atomic decomposition of the data and RDF, you typically have longer patterns when you perform
queries" against a triple store than the equivalent property-graph query. Neither convention is strictly
better; RDF's atomic structure suits data that needs to interoperate across many independently-built graphs
using shared vocabularies, while a property graph's more compact structure suits a single system optimized
for fast, deeply-chained traversal.

**Building a graph from unstructured text now typically means instructing an LLM with a schema rather than
hand-coding extraction rules.** Modern extraction pipelines can be "instructed with detailed prompts
(instructions, examples, schema, existing entities, output formatting) to extract, and de-duplicate entities
and relationships from unstructured text," returning "structured information...in a structured JSON format"
that "can be stored in a graph database like Neo4j and linked back to the source documents." Rather than
letting the model invent whatever entity and relationship types it feels like on a given page, "you can
specify a schema with allowed nodes and relationships, as well as properties and additional extraction
instructions," constraining the model's output to a fixed, known vocabulary the rest of the graph already
uses. A full construction pipeline is more than one extraction call: it typically chains together a data
loader, a text splitter, a chunk embedder, a schema builder, a lexical graph builder, an entity and relation
extractor, a knowledge graph writer, and an entity resolver, each stage doing one part of the job of turning
a folder of documents into a single connected structure.

**Entity resolution exists because the same real-world thing rarely appears under the same name twice.** A
document might refer to one person as a full name, a title and surname, and a first name alone across three
different paragraphs, and a plain entity-recognition pass treats all three as separate mentions with no
inherent link between them. The problem this creates is direct: "we ideally want a single real-world entity
to be represented with a single node. We really don't want to have three different nodes representing the
same entity." The fix moves from recognition to linking: "to go from name entity recognition to name entity
linking means that we aggregate the name entity recognition to first recognize all the entities, and then
map those entities to a target knowledge base." A common version of this maps every mention to an external
reference like Wikipedia, aiming for a result where "even though we have three different titles of texts
for [a given person], they would all link to the same entity on Wikipedia," and that shared identifier becomes the one node every
mention actually resolves to. Skip this step, and a graph ends up with duplicate, disconnected nodes for
the same entity, each holding only a fraction of what the source documents actually said about it.

**Knowledge graph embeddings turn a graph's structure into something a model can use to predict connections
nobody entered.** Once a graph exists, "knowledge graph embeddings are vector representations of entities
and relationships in a knowledge graph, used to predict missing links and facilitate machine learning
tasks." The motivation is practical: "machine learning algorithms work better with numerical data. When we
turn entities and relations into embeddings, we can feed this data into machine learning models to perform
tasks like link prediction." This is a different job from the embeddings covered in Chapter 6.2: those
embeddings represent the meaning of a chunk of text for similarity search, while a knowledge graph embedding
represents an entity's position within the graph's own structure of relationships, trained so that patterns
the graph already contains generalize to relationships it does not. A graph that knows a country is located
in a continent, and knows enough other countries and continents to have learned that pattern generally, can
predict a plausible location for a country whose containment relationship was simply never entered, a
prediction, not a retrieval, and one that needs verification before it is treated as fact.

**Text2Cypher lets an LLM query a knowledge graph directly instead of only ever reading a pre-written
summary of it.** Rather than retrieving a document that describes a fact, an agent can generate the graph
query that looks the fact up directly: "Text2Query includes any query generation by an LLM from natural
language, such as Text2SQL and Text2Cypher," and "Cypher is the primary query language used with graph
databases," so an agent can "generate a database query that addresses user input." The appeal is direct
grounding: "allowing an AI agent to generate and execute database queries enables it to ground its insights
in actual domain knowledge," which "reduces the risk of hallucination" in a way that reading a possibly
outdated summary cannot guarantee. This comes with its own failure modes, though: "query generation...
specifically requires agents to also have a clear understanding of the database schema," and "large schema
sizes may also impact the agent's ability to accurately generate database queries as it can overload the
context and confuse the LLM." An agent also has to handle "domain-specific jargon," abbreviations and names
with a particular meaning inside one organization's graph, and "as the complexity of the question or task
increases, so does the chance that the generated query will fail or not return the desired information."
Text2Cypher trades the risk of an outdated retrieved summary for the risk of a malformed or subtly wrong
query, not a free upgrade over retrieval, a different set of failure modes to design around.

Knowledge graph embeddings and Text2Cypher are not competing techniques, they answer different questions.
Embeddings predict a relationship nobody entered; Text2Cypher retrieves a relationship that is already
there. A production system might use the graph from Chapter 6.5's GraphRAG pipeline for holistic
questions, Text2Cypher for a specific, well-scoped lookup, and embeddings only where an actual prediction,
clearly labeled as such, is the point.
