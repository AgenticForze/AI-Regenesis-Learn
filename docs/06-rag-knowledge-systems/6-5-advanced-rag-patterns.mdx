## TL;DR

Chapter 6.3 introduced hybrid search, fusing dense vector results with sparse keyword results, and
Chapter 6.4 walked the full mechanical pipeline from ingestion through chunking, retrieval, reranking, and
grounded generation. Both chapters still treat the query and the index as fixed: whatever a user types is
what gets embedded and searched, once, against whatever got chunked and stored. This chapter covers three
patterns that change those assumptions, each aimed at a failure mode the mechanical pipeline cannot fix on
its own. Hypothetical Document Embeddings (HyDE) addresses a query that is too short or too differently
worded from the documents that would answer it: rather than embedding the query directly, an
"instruction-following language model (e.g. InstructGPT)" first generates "a hypothetical document" that
captures what a good answer would look like, and an "unsupervised contrastively learned encoder (e.g.
Contriever)" embeds that hypothetical document instead, so the search runs against something shaped like an
answer rather than a terse question, with this second step grounding "the generated document to the actual
corpus, with the encoder's dense bottleneck filtering out the incorrect details." GraphRAG addresses
questions no single chunk can answer at all: instead of indexing only chunks, it builds an "LLM-generated
knowledge graph" from the entities and relationships in a source dataset, applies "hierarchical clustering
of the graph using the Leiden technique" to detect communities, and summarizes each one, enabling a global
search "for reasoning about holistic questions about the corpus by leveraging the community summaries"
alongside a local search "for reasoning about specific entities by fanning-out to their neighbors and
associated concepts."
Agentic RAG addresses questions a single retrieval pass, however well reranked, cannot resolve on its own:
an LLM can decompose a complex query into sub-questions and retrieve for each one separately, interleave
reasoning and retrieval the way ReAct does, generating "verbal reasoning traces and text actions in an
interleaved manner," or learn, as Self-RAG does, to retrieve "on-demand" and critique its own output using
"special tokens, called reflection tokens." None of these patterns replace the pipeline Chapter 6.4
covered; each one wraps around it, changing what gets searched, what gets indexed, or how many times
retrieval runs before an answer gets generated.

## High-Level Explanation

The librarian from Chapters 6.1 through 6.4 is fast, thorough, and diligent, but takes a question
completely literally and searches exactly once. Advanced RAG patterns give that librarian more judgment.
Sometimes a patron cannot phrase their question well, they know roughly what they want but not the words a
source document would actually use, so an experienced librarian imagines what a good answer would sound
like and goes looking for something that resembles that imagined passage instead of the patron's exact
words, that is HyDE. Sometimes a question is not about any single page at all but about how the whole
collection connects, who is related to whom, which events cluster together, so the librarian keeps a
separate map of those connections and reasons over the map rather than skimming shelf by shelf, that is
GraphRAG. And sometimes one trip to the stacks is not enough: the librarian might split a big question
into a few smaller ones and search for each in turn, narrate their reasoning out loud while alternating
between thinking and searching, or bring back a first stack of pages, glance at it critically, and decide
whether it actually supports an answer before deciding to go find more, that is agentic RAG.

## Deep-Dive Explanation

**HyDE rewrites the query into something that looks like an answer before it ever gets embedded.** A short
or ambiguous query embeds poorly because its vector sits far from the vectors of the longer, more
detailed passages that would actually answer it, a mismatch retrieval alone cannot fix. HyDE addresses this
by generating a stand-in first: "given a query, HyDE first zero-shot instructs an instruction-following
language model (e.g. InstructGPT) to generate a hypothetical document." That document is not meant to be
factually reliable on its own, the source paper is explicit that it "captures relevance patterns but is
unreal and may contain false details." What makes the method work is the second step: rather than
searching with the hypothetical document's text, an "unsupervised contrastively learned encoder (e.g.
Contriever) encodes the document into an embedding vector," and that vector "identifies a neighborhood in
the corpus embedding space, where similar real documents are retrieved based on vector similarity." The
paper frames this step as grounding: "this second step ground the generated document to the actual corpus,
with the encoder's dense bottleneck filtering out the incorrect details." A hallucinated fact in the
hypothetical document rarely survives into retrieval, because the encoder was never trained to preserve
fine factual detail, only the broad relevance pattern a real matching passage would share.

**GraphRAG builds a second index, a knowledge graph, for questions no single chunk was ever going to
answer.** Chunk-based retrieval, however it is chunked or reranked, answers questions about what a specific
passage says. It struggles with questions about how many passages relate to each other across an entire
collection. GraphRAG's construction phase has an LLM read the source data and build structure from it: "the
LLM processes the entire private dataset, creating references to all entities and relationships within the
source data, which are then used to create an LLM-generated knowledge graph." That graph then gets
organized, not searched flat: the system will "perform a hierarchical clustering of the graph using the
Leiden technique" and then "generate summaries of each community and its constituents from the bottom-up,"
producing pre-written summaries of what each cluster of related entities is actually about. Retrieval
against this structure comes in two forms suited to two different question shapes: global search is built
"for reasoning about holistic questions about the corpus by leveraging the community summaries," while
local search is built "for reasoning about specific entities by fanning-out to their neighbors and
associated concepts." A flat chunk index has no equivalent of either: it can return passages that mention
an entity, but it has no summarized notion of the community that entity belongs to, and no way to answer a
question about the shape of the whole dataset rather than a specific passage within it.

**Query decomposition breaks a multi-hop question into pieces a single retrieval pass could never resolve
together.** A question that depends on connecting two or more separate facts, what changed between two
filings, which of several vendors triggered a specific clause, embeds as one vector that is a blend of
several different information needs, and a single retrieval pass over that blended vector tends to surface
passages related to only the most dominant part of the question. Decomposition addresses this at the
question level rather than the index level: "an LLM decomposes the original query into sub-questions," and
then "passages are retrieved for each sub-question" independently, so each retrieval pass targets one clear
information need instead of a blend of several. The results are not simply concatenated; "the merged
candidate pool is reranked to improve the coverage and precision of the retrieved evidence," using the
reranking mechanics Chapter 6.4 already covered, but now applied across candidates pulled from several
different searches rather than one. The overall effect, as the authors put it, is that "question
decomposition effectively assembles complementary documents, while reranking reduces noise and promotes
the most relevant passages before answer generation," pairing a technique that improves coverage with one
that improves precision rather than relying on either alone.

**ReAct interleaves reasoning and retrieval instead of running them as two separate, one-shot stages.**
Standard RAG reasons once, retrieves once, and generates once, in that fixed order. ReAct instead "enables
language models to generate both verbal reasoning traces and text actions in an interleaved manner," so a
model can think, search, read what came back, think again, and search differently, repeating that cycle as
many times as the question actually requires. The two halves reinforce each other in different directions:
reasoning helps the model decide what to search for next, described as "the synergy between reasoning and
acting" that lets the model "perform dynamic reasoning to create, maintain, and adjust high-level plans for
acting," while what comes back from a search feeds back into that reasoning, "interacting with the external
environments...to incorporate additional information into reasoning." A single fixed retrieval pass has no
way to notice that its first search returned the wrong thing and try again with a better query; a ReAct
loop can, because reasoning and retrieval keep taking turns until the model's own reasoning trace decides
it has enough.

**Self-RAG goes a step further and trains the model to decide when to retrieve and to critique what it
retrieves and generates.** Rather than retrieving a fixed number of passages on every query regardless of
whether the query needs them, Self-RAG uses "special tokens, called reflection tokens" so the model
"adaptively retrieves passages on-demand," skipping retrieval for a question it can already answer and
retrieving, sometimes repeatedly, for one that needs external evidence. The same reflection mechanism
extends past the retrieval decision into self-critique: the model "generates and reflects on retrieved
passages and its own generations," scoring whether a retrieved passage is actually relevant and whether its
own draft answer is actually supported by what it retrieved, rather than assuming both are fine by default.
Because these judgments are expressed as tokens the model itself produces, "generating reflection tokens
makes the LM controllable during the inference phase, enabling it to tailor its behavior to diverse task
requirements," which means the retrieve-then-critique behavior is something the model learned rather than a
fixed rule bolted onto the pipeline from the outside.

Every pattern in this chapter is additive: none of them requires abandoning the ingestion, chunking,
retrieval, reranking, or grounding mechanics Chapter 6.4 established. A production system might use none of
these patterns, one, or several together, HyDE rewriting a vague query, a GraphRAG index sitting beside the
vector database for holistic questions, and a Self-RAG-style critique step deciding whether either one's
output actually supports an answer before it reaches the user.
